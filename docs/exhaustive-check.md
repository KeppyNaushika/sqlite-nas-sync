# 有界網羅検査（`npm run explore`）

収束の正しさを「**この範囲には反例が無い**」という事実として確かめる道具。
`tools/` にある。
ライブラリ（`src/`）にもテスト（`__tests__/`）にも含まれない。

## なぜ要るか

`__tests__/convergence-properties.test.ts` は fast-check による**乱数**の性質テストで、不具合を見つける網としては優秀だった。
だが「直った」の判定には向かない。

- 乱数は「ある」は示せても「無い」は示せない。
  失敗率3%の族に「10回連続通過」は偶然で約73%起こり、実際に誤った「直った」報告が3回続いた
- 判定に要る本数が統計で決まり、38,400ケース・約25分かかっていた
- 生成器は操作の**種類**を均等に選ぶので、単純な操作ばかり繰り返し引き、特定の組み合わせは滅多に引かない。
  同じ小さい形を何度引いても重複排除しない

この道具は**範囲を有限に区切り、その中を乱数なしで漏れなく試す**。

さらに、1回の実行の中の一致だけでは原理的に見えない「**同じアプリ操作なのに、同期のタイミングが違うと結果が違う**」も数える（下の「性質」の3）。
実証（本物のコード）: ① a が g1 を t1 で作る、② b が g2 を t1 で作る、③ b が g2 を t2 に変える。
①② → 同期 → ③ → 同期 では g2=t2 だけが残り、①②③ → 同期 では g1=t1, g2=t2 が残る。
どちらも全端末は一致しているので、一致の検査では見えない。

**案A（`docs/rows-table-design.md`）では、これは違反ではない。**
`_sns_ts` の引き上げ（§1.2.1）があるので、他端末の版を取り込んだあとに、より古い時刻でその行を書くと、取り込んでいなかった場合より強い版になる。
したがって挟み方の検査は**件数の記録**にし、代表例を1つだけ「（強）が破れた形の観察」として出力の末尾に添える（§8.1・§9.25）。
探索は止めない。

## 使い方

```sh
npm run explore                                   # 既定の範囲（下の表）
npm run explore -- --depth 4 --workers 8          # 深さと並列度を変える
npm run explore -- --tables accounts --formats 0,1
npm run explore -- --clients 3 --tables users --ids 1 --depth 4
npm run explore -- --self-test 200                # 削減手の前提を確かめてから探索する
npm run explore -- --depth 3 --oracle rows-d1     # 参照実装（案A の意味の定義）と見え方を突き合わせる
npm run explore -- --help                         # 引数の一覧
```

`npm run explore` は `tsc -p tools/tsconfig.json` で検査器と `src/` を `node_modules/.cache/explore/` へコンパイルしてから走らせる（`tsx` などは使わない。依存を増やさないため）。
駆動するのは**そのとき作業ツリーにある `src/`** である。

終了コードは、反例なし 0 / 反例あり 1 / 検査器そのものの失敗・自己検査の失敗・ディスク不足で中断 2。

作業ディレクトリ（既定 `$TMPDIR/sqlite-nas-sync-explore`）は終わると消す。
途中で空きが 3GB（`--min-free-mb`）を割ったら止める。
`--all` で反例の多い版を走らせると、反例ごとに再生し直して再現手順を書くので遅くなる。

## 何を調べるか

### 遷移

状態から出る辺は次の4種類。
**範囲の中の全部**を毎回試す。

- **操作**: 端末 i のローカルDBへ、選んだ表の upsert（id × キー × 時刻 × 書式 × 本文）・削除、または `pruneChangelog`（`_changelog` を、いちばん遅れている相手の読み位置の1つ先まで削って隙間を作り、相手を**フルマージ経路**へ落とす）。
  中身は性質テストの `applyOp` / `pruneChangelog` と同じ（ローカルの制約違反は「その端末では起きなかった」、子の前に親を用意する）
- **同期**: 端末 i が本物の `performSync` を呼ぶ
- **時計を進める**（`tick`）: 以後の操作は、それまでのどの時刻より後を名乗る
- **同期の最中に書く**（`syncWrite`）: 端末 i が `performSync` し、その途中の `await copyToNas(...)`（`localDb.backup()`。非同期にページを写す）の待ちの間に、同じ端末のアプリが操作を当てる。
  `backup()` が呼ばれた直後・写し始める前（書き込みは NAS のコピーに載る。同期の冒頭の自己点検はこの書き込みを見ていない）と、写し終えた直後（コピーに載らない。このあとの取り込みは見る）の2点。
  `src/` を変えずに差し込むため、同期のあいだだけその接続の `backup` を差し替える（`tools/explore/world.ts` の `syncWithWrite`。差し込めたことは、写し始める前ならコピーに載り、写し終えた後なら載らないことで確かめてある）。
  別の端末への書き込みは、同期する端末が読むのが相手の NAS 上のコピーなので、同期の前か後に書いた場合と区別が付かず、持たない

### 性質（各状態で）

1. **取り込みが失敗として飲み込まれない** —— 遷移でも検査の同期でも、`result.warnings` に `Sync failed for client …` が出たら違反（その相手からの同期が永久に止まる）。
   相手の DB を開けなかった `Failed to open remote database` と、作り直しの失敗・先送り（`Rebuild failed` / `Rebuild deferred`）も違反に数える。
   検査器は端末ごとに接続を1本しか開かないので、先送りが起きたなら判定の前提が崩れている。
   `performSync` が例外を投げても違反
2. **収束する** —— その状態から全端末を round-robin で同期し、状態が動かなくなったとき全端末の中身が一致すること。
   **一致しない行が1つでも残れば違反**（逃げ道は無い）。
   時刻列は `julianday` で比べる（同じ瞬間の書式違いは差と数えない）。
   - **全ての開始端末から**回す（a から始めたときだけ、b から始めたときだけ、の両方を見る）
   - 「動かなくなった」＝ (状態, 次の端末) が一度出た組へ戻り、その一巡で状態が1つも変わらなかった
   - 戻った一巡で状態が変わっていれば**振動**、`--max-probe-rounds × 端末数` 回同期しても戻らなければ**動き続けた**として、どちらも違反
3. **同期の挟み方で見え方が変わる件数**（挟み方の検査。`tools/explore/history.ts`）—— **違反ではない。件数の記録である**（設計書 §8.1・§9.25）。
   案A では `_sns_ts` の引き上げがあるので、「同じ操作の集まり ⇒ 同じ見え方」（強）は成り立たない。
   **端末ごとの、検査器が発行したアプリ操作の列**（同期・時計・`pruneChangelog` は含めない）が同じ実行どうしで、全端末を不動点まで同期したときの見え方（同期対象の表の中身、`updatedAt` は julianday）が同じかを見る。
   同じ状態から開始端末だけを変えた round-robin で見え方が違う場合も数える。
   出力には**件数**と、いちばん短い**代表例1つ**（強いものを優先）を「（強）が破れた形の観察」として出す。
   - **実装から読み取ったもの（`_changelog`・`_tombstone`）では比べない。**
     実装の判断を比べる単位に借りると、実装の誤りが判定に流れ込む
   - 端末ごとの列にするのは、別々の端末への操作の前後を入れ替えても列が変わらないようにするため（順序の畳み込みと両立させる）
   - **比べない履歴**（どちらも発行した操作だけから決める）: 同時刻で中身の違う upsert を含む、同じ端末が同じキーへ自分の前の書き込みより古い時刻で書く（子の表の操作が親を自動で作った場合は、アプリに「挿入した」と返ったときだけ親の版も書き込みとして数える）。
     不動点で端末ごとに見え方が違って定まらない場合も比べない
   - 食い違いは2種類に分けて数える。
     **強い食い違い**はアプリが受け取った結果（変えた行数・制約違反）まで同じ実行どうしで、代表例に選ぶときはこちらを優先する。
     **弱い食い違い**は結果が違う実行どうしで、まだ届いていない行の削除（0行）や、届いた行と UNIQUE がぶつかる挿入（失敗）のように、設計上も結果が変わってよい形を含む（`--schedule-key ops+status` にすると弱い食い違いはそもそも比べない）
   - **どちらでも探索は止まらない。**
     止まるのは他の違反（性質1・2、判定、参照実装との食い違い）だけである

## 案A のための判定と操作

`docs/rows-table-design.md`（案A）の §8 は、いまの3つの性質に加えて判定をあげている。
判定は仕様（`docs/principles.md`）と設計書の字面から書き、実装の内部の手順は借りない。
実装を書き終えてから判定を書くと、実装に都合のよい判定しか思いつかないからである。

駆動するライブラリに案A の口（作り直し・移行・無駄な転送の抑制）が1つでも欠けていれば、検査器は起動時に例外で止まる。
黙って一部の判定を外して走らせると、調べていないのに「反例なし」と出るからである。

雛形の DB は `setupSync`（`src/index.ts`）と同じ順で仕立てる —— `migrateToRows` で案A の仕掛けを取り付け、そのあと `setupRowsLedgers` で表に触らない帳簿を作る。

### 参照実装 `rows-d1`

`tools/explore/oracles/rows-d1.ts`。
設計書 §1（意味の定義）と §2（削除）を素直に写した、「版の集合 → アプリの表の見え方」の計算である。

- **`src/` を一切呼ばない。**
  呼べば `src/` の不具合をそのまま写して、判定が素通りする
- **速度より読みやすさを優先する。**
  設計書の語（`Max`・候補・表示値・かぶり・勝者・隠れた行・置かない行・置く行）をそのまま関数名にしてある
- **SQLite に判定させるべきものは SQLite に判定させる。**
  照合順序・CHECK・NOT NULL・型・部分索引・式索引・生成列・値の種類は、一時の `:memory:` DB へ**強い順に INSERT** して、返ったエラーの種類で「置かない行」と「隠れた行」を分ける。
  かぶりの相手（勝者）も、空の DB へ2つ入れてみて決める（索引の文を字句解析しないので、部分索引・式索引でも宣言どおりに効く）
- スキーマは `CREATE TABLE` の文だけを渡し、主キー・列・外部キー・NOT NULL・既定値は一時 DB の `PRAGMA` から読む（別に宣言させると、宣言と DDL がずれたときに黙って違う表を調べる）

**参照実装そのものの試験**は `tools/explore/oracles/rows-d1-tests.ts`。
手で作った版の集合に対する期待値を表にして並べてある（かぶり・隠れた行・削除・削除より新しい版・消してすぐ作り直す・cascade で消えた子・置かない行（NOT NULL / CHECK）・`ON DELETE SET NULL`・親が削除されている間は入らない子と、親を書き直したら入る子（孫への連鎖を含む）・読み替え・1:1 の表・1:1 で読み替えた主キーの衝突・値の種類・照合順序）。
どの事例でも

- 版を並べ替えても、同じ版を重ねて渡しても答えが変わらないこと（補題C）
- 置く行が本物の表に入り、外部キーを満たすこと
- 判定13（下記）

をあわせて見る。
`npm run explore -- --unit-tests` と、探索の起動時に必ず走る。

外部キーは親の主キーを参照するものだけを扱う（`docs/principles.md` の付則4）。
主キー以外を参照する外部キーを持つスキーマは `setupSync` が断るので、参照実装も例外にする。

### 操作ごとの原則2・原則3・原則4 の確かめ

アプリの操作1回ごとに、`docs/principles.md` の原則2・原則3・原則4 を直に確かめる（`tools/explore/judgments.ts` の `checkDeletionPrinciples`）。

- **原則2**: その操作で書かれた削除の版ごとに、`_sns_ts` が削除を実行した時刻（`_tombstone.deletedAt`）より弱くないこと。
  実行した時刻より手元の Max が強ければ単調化でそこまで上がるが、実行した時刻を下回ることは無い
- **原則3**: その操作でアプリの表から消えた行ごとに、統合でその後ろに隠れていた主キーの Max が削除の版になっていること。
  消してすぐ作り直した行も「消えた行」に数える
- **原則4**（付則3 の前半）: その操作でアプリの表から消えた行（消してすぐ作り直した行を除く）ごとに、その主キーの Max が削除の版になっていること。
  親を消したクライアントにその時点であった子は SQLite が `ON DELETE CASCADE` で消し、その削除が版になる。版が無いと、親を書き直したときに子が戻る

原則2 と原則3 の確かめは、収束や参照実装との突き合わせでは見えない壊れ方を捕まえる。
全端末が同じように壊れて一致してしまい、しかも実行した時刻と、そのとき何が統合されていたかは発行した操作の列から決められないので、参照実装も突き合わせを見送るからである。
比べる実行時刻には壁時計の値が要るので、時計 C へ書き換える前に当てる。
違反は遷移の例外として、経路つきの反例になる。

判定5・6・7 は `tools/explore/judgments.ts` にあり、収束の検査の**同期1回ごと**に当たる。
判定8・10・13 は `tools/explore/world.ts` の `runtimeFor` が `onRebuildCommitted` へ差し込み、**作り直しが確定するたびに**当たる（違反は例外にして上げるので、どの遷移で裂けたかが経路つきで残る）。
違反は `judgment` という種類の反例として出る。
判定11・12 は定義そのものの性質なので、起動時の単体テストで見る。
判定20・21 は `tools/explore/rebuild-scenarios.ts` の筋書きで、起動時に当たる。

### 題材の時刻列は ISO 8601 の文字列だけ

同期する表の時刻列には ISO 8601 の文字列しか入らない（`docs/principles.md` の付則2、設計書 §1.8 の P15）。
`setupSync` がそれ以外の値を持つ表を断り、導入後はトリガーがアプリの書き込みを止める。
そこで、時刻列が `INTEGER` の `epoch_notes` と、`COLLATE NOCASE` の時刻列に `TS-A` などの値を入れる `nocase_notes` を題材から外した。
削除の版の `_sns_ts` は、どの題材でも実行した時刻（時計 C）と手元の Max の大きい方である。

この2つの表でだけ観測できた壊し方のうち、`sns-ts-as-text` は `pending` に理由を書いて残した。
`no-binary-collation` は、`instanceId` の比較で同じ壊れ方を観測できるので、範囲を変えて生かした（下の「確かめた結果」）。

### `--oracle rows-d1` の限界

判定4 の本来の入力は「判定2 で集めた版」だが、いまは `tools/explore/oracles/from-history.ts` が**発行した操作の列から版を組み立てて**参照実装へ渡す。
操作の列だけからは**同期がどこで挟まったか**が分からないので、次の形では `null`（突き合わせない）にする。

1. `_sns_ts` の引き上げ: ありうる引き上げ方を全部試し、**どれでも同じ見え方になるときだけ**答える
2. 削除を実行した時刻: 削除の版の `_sns_ts` は実行した時刻と手元の Max の大きい方である（原則2）。
   実行した時刻は操作の列に載らないので、範囲の過去の時刻より後で未来の時刻より前という条件と、同じ端末では発行した順に弱くならないという条件だけを守って、ありうる並びを全部試す。
   削除が4つ以上ある列は、並びが多すぎるので突き合わせない
3. cascade で消える子: 他の端末がその親の子を書いていれば、届いていたかどうかで削除の版の集合が変わる
4. 時刻列を変えない UPDATE: 版に載る時刻が「そのとき行に入っていた値」なので、他の端末も触るキーでは決まらない
5. `instanceId` の向き: 端末の並び順を両方試し、どちらでも同じ見え方になるときだけ答える（同着が `iid` で決まる形は、仕様でも「どのクライアントで比べても同じ答え」しか決まっていない）
6. **`L`（lamport）の引き上げ**: 取り込みは `_sns_clock.lamport` を受け取った版の最大まで引き上げる（設計書 §4.3・不変条件 C）ので、取り込んだあとの書き込みは大きい `L` を名乗る。
   `L` が効くのは `_sns_ts` が同着のときだけなので、**同じ表に、違う端末の版が同着の `_sns_ts` で並ぶ**列は突き合わせない（同じキーの `Max` だけでなく、かぶりの勝者もここで決まるので、キーごとではなく表ごとに見る）。
   削除の版はかぶりの勝者を決める比べ合いに入らないので、違うキーの削除の版との同着は数えない
7. **読み替えのあとの削除**: アプリは表示上の id で消すので、かぶりに負けて読み替えられた行があると、同じ `DELETE` 文が違う真の id の版を作る（設計書 §1.3〜1.7 の表示値と §3.3 の `TRUE_ID`）。
   読み替えが起きている列に削除があれば突き合わせない
8. **統合した行の削除**（原則3）: 統合した行を消すと、そのときその端末で隠れていた側の主キーにも削除の版が書かれる。
   何が隠れていたかは取り込みの位置で変わるので、違う id の2行が UNIQUE で衝突しうる表に削除があれば突き合わせない。
   この形は操作ごとの原則3 の確かめ（上）が見る

**見落としはしても誤検出はしない**側に倒してある。
6 と 7 が無いと、**案A の実装が設計どおりでも反例が出る**（下の「切り分け」）。

使う口は次の6つで、どれも `src/` に揃っている。

## 保証すること・しないこと

### 保証すること

**「反例は無かった」と出たら、印字された範囲の中の、深さ以下の全ての遷移の列について**:

- 途中のどの遷移でも取り込みの失敗・例外が起きず、
- 途中のどの状態から round-robin で同期しても（どの端末から始めても）、上限以内に不動点へ届き、そこで全端末の中身が一致する
- 参照実装を選んでいれば（`--oracle rows-d1`）、突き合わせられる列については、案A の意味の定義から計算した見え方と本物の見え方が一致する

ことを、本物の `performSync` と本物の SQLite ファイルDBで実際に確かめた。
確率ではない。

**挟み方の検査はここに入らない。**
それは違反ではなく件数の記録なので、「反例なし」と出た実行でも強い食い違いが何組かある（設計書 §9.25）。
出力に「調べた状態」「当てた遷移」の数と範囲を必ず添えるので、それが根拠になる。

### 保証しないこと（範囲と模型の外）

- **範囲の外は何も見ない。**
  端末の台数、表の組、id・キー・時刻・本文の種類、深さを超えた列は調べていない。
  「深さ3で反例なし」は「深さ4で反例なし」を意味しない
- **時計の模型の外。**
  操作が刻む時刻（`_changelog.changedAt`・`_tombstone.deletedAt`・削除の版の `_sns_ts`）は、世界に1本の時計 C へそろえる（下の「時計」）。
  同期を挟まない操作は、端末が違っても同じ瞬間か、`tick` を挟んだ順に並ぶ。
  **端末ごとの時計のずれ**（同期より前の時刻を名乗る操作、未来の時刻を名乗る削除）は表せない。
  行の `updatedAt` は範囲の時刻から選ぶので、こちらはずれを含めて表せる
- **削除・changelog の時刻は常に行の時刻より後。**
  行の時刻は 2026-01-01、削除は実行時の現在時刻。
  原則2 により、削除の版の `_sns_ts` もその現在時刻になる。
  性質テストと同じ条件で、「削除より新しい書き込み」は範囲の時刻からは作れない —— `--future-times`（2099-01-01）で作る
- **同期の中の刻みの揺れ。**
  同期そのものが刻む時刻は書き換えない（ライブラリの振る舞いそのものなので）。
  いま同期が刻むのは、取り込みで `_changelog` に書く通知の `changedAt` だけである。
  取り込みは相手の版を `_sns_ts` も `deletedAt` もそのまま写し、相手の値は相手の操作の直後に C へそろえてあるので、版の時刻は揺れない。
  同じ同期の中の2つの `changedAt` が同じミリ秒に収まるかは実行ごとに揺れうるので、正規化で潰すことはしない。
  探索は揺れのうち**その実行で起きた方**だけを調べる。
  揺れた場合は「再生して違う状態に戻った節」として数と列を出す。
  このため「調べた状態」の数は実行ごとに1%未満ずれることがある
- **無駄な転送の抑制の覚えは状態に入れない**（`tools/explore/world.ts` の `idleMemoryFor`）。
  抑制が落とすのは状態を変えない回だけ、という前提に立つが、例外を1つ実測している。
  相手を読まない回はその相手の `_changelog` の隙間も調べないので、「上げてから作り直す」か「作り直してから上げる」かが入れ替わり、NAS の自分の写しに入る `_sns_dirty` が変わる。
  他の端末はその表を読まない（設計書 §3.1）ので振る舞いは変わらないが、「再生して違う状態に戻った節」として数えられる。
  同期の最中の書き込みは、その同期の前に覚えを空にして必ず上げさせる（上げる回でないと `backup()` が呼ばれず、差し込めない）
- **round-robin 以外の同期の順**での収束は、検査としては見ない（ただし探索そのものが同期の順を全部試すので、深さの範囲内の途中状態としては現れる）
- **中身が一致した後の「正しさ」**（どちらの版が残るべきだったか）は見ない。
  見るのは一致と報告だけ
- **保持期間（7日）を過ぎる掃除・NAS の I/O 障害・プロセスの異常終了・スキーマの版違い**は範囲に入っていない
- **子の表の操作は id から親を1つに決めている**（`g1` の子は `t1` という名前の `g1` を親に取る。`tag_notes` の `n1` は `g1` を指す）。
  別の親を指す子・別の名前の親を作る子は範囲に無い
- **端末の入れ替えは畳まない**（下の「状態を減らす手」）。
  3台の round-robin の開始端末は「a,b,c の回転」だけで、a,c,b の順は検査の同期としては回さない
- **挟み方の検査の限界**: そもそも違反として数えない（案A では成り立たない。設計書 §9.25）。
  件数は「（強）がどれくらい破れているか」の目安であって、多いこと自体は不具合ではない。
  同期の最中の書き込みは、同期する端末への書き込みで、`backup()` の前後の2点だけ（写している途中のページの境目には差し込まない）。
  比べるのは不動点での見え方で、途中の見え方の違い（一時的に見える・消える）は見ない。
  深さの範囲に入っている挟み方どうしだけを比べる
- **判定19 は配線していない**（上の表）。
  版の鍵そのものが中継で書き換わる形を名指しで見る筋書きが無い

## 状態と正規化

状態は「全端末のローカルDB」「NAS 上の各端末のコピー」「時計」を正規化して直列化したもの。
**含め忘れると別の状態を同じと見て探索を打ち切り、反例を見逃す**ので、以後の振る舞いに効くものは全部含める。
判断の根拠は `tools/explore/state.ts` の冒頭にある。

**重複排除の単位は (状態, 発行した操作の列, 比べてよい履歴か, 次に操作してよい端末の集合)。**
挟み方の検査は列の性質（同じ操作の列の実行どうしを比べる）なので、状態だけで畳むと、違う操作の列から同じ状態へ合流した列の片方を見失い、その列の挟み方どうしの比較を落とす。
そのぶん節は増えるが、子の状態と結果は操作の列によらないので、**同じ状態の節は組にして、遷移を1回だけ実行する**（実測: 最小の範囲・深さ4で、状態 24,290・節 125,338 に対し、実行した遷移は節ごとの 144,027 から 68,115 へ。状態・操作の列・食い違いの数はまとめる前と一致した）。

| 含める                                                                           | 理由                                                                                   |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 同期対象の表の行（全列、**rowid 順**）                                           | 全件を `ORDER BY` なしで読む箇所は rowid 順に処理するので、並びも振る舞いに効く        |
| `_sns_rows_<表>`                                                                 | 案Aの版の表。これが違えば次の作り直しの結果が違う                                      |
| `_sns_clock`（`importTick` を除く）/ `_sns_shown` / `_sns_hidden` / `_sns_dirty` | 版の順序・隠れた行・作り直しの要否に効く                                               |
| `_tombstone`（全列、rowid 順）                                                   | 削除の版。取り込みと表示の計算に効く                                                   |
| `_changelog`（id・表・行・操作・時刻）                                           | 差分同期で流れる中身                                                                   |
| `sqlite_sequence`                                                                | 次に振られる changelog の id                                                           |
| `_changelog_prune.prunedThroughId`                                               | 隙間の判定                                                                             |
| `_sync_state`（相手・lastSeenId）                                                | 次にどこから読むか                                                                     |
| `_sync_meta`                                                                     | `sns.generation`・`sns.lastLamport`・`sns.instanceId` など。復元の判定と版の確認に効く |
| スキーマ（`sqlite_master` の要約）                                               | 作り直しはアプリのトリガーを外して付け直す。付け直し損ねた状態を同じと見ないため       |
| NAS 上の各端末のコピー（上の全部）                                               | 相手が読むのはこちら                                                                   |
| NAS のその他のファイル名                                                         | `.tmp` の残骸など                                                                      |
| 時計 C                                                                           | どの刻みと等しいか（等しくなければ「fresh」）だけ                                      |

| 含めない                     | 理由                             |
| ---------------------------- | -------------------------------- |
| 空きページ・ファイルの大きさ | 論理的な中身だけが振る舞いに効く |

### 採番値は生のまま

`_changelog.id`・`lastSeenId`・`prunedThroughId` は**ずらさない**。
相対値にすると畳める状態は増えるが、絶対値が効く箇所がある（`hasChangelogGap` の `lastSeenId === 0` / `prunedThroughId > 0`、`pruneChangelog` の `id <= floor + 1`）。

### 現在時刻由来の値は、大小と同着の関係だけを残す

- 範囲で決めた行の時刻は**字面のまま**（書式違いは別の値）
- 実行中に刻まれた時刻（時計 C と、同期が刻む `changedAt`）は、状態に現れる全ての時刻を `julianday` の順に並べた**順位**へ置き換える。
  札を付けるのは、名前が `At` で終わる列と `_sns_ts` である。
  `_sns_ts` には行の時刻を引き上げた値と実行時刻の両方が入るが、行の時刻は字面のまま残るので、実行時刻だけが順位になる
  同じ瞬間は同じ順位。
  **字面が違えば順位の中でさらに区別する**（字面で比べる箇所があるため）

ライブラリが時刻を扱うのは (a) `julianday` による大小・同着、(b) 字面の一致、(c) `julianday('now', '-7 days')` との大小、の3つで、(a)(b) は順位で保たれ、(c) は「実行中の時刻は常に保持期間内、行の時刻は常に保持期間外」なので状態によらず答えが決まる。
**この前提は毎回確かめ、崩れたら例外で止める。**

## 時計

アプリの操作はトリガーを通って壁時計を刻む。
刻まれるのは `_changelog.changedAt`、`_tombstone.deletedAt`、削除の版の `_tombstone._sns_ts` の3か所である。
削除の版の `_sns_ts` は、原則2 により実行した時刻と手元の Max の大きい方なので、ふつうは `deletedAt` と同じ値になる。
統合した行の削除で隠れていた側に書く墓標（原則3）も同じ値を持ち、同じ操作の中で消してから作り直した行の版は、単調化でその値まで引き上がる。

壁時計のままだと、別々の端末への操作 x, y を x→y と y→x で当てたときに刻まれる時刻の前後が入れ替わり、**結果の状態が同じにならない**。
すると順序の畳み込みの前提が崩れ、しかも同じ列を再生しても同じミリ秒に収まるかで結果が揺れる（`--self-test` で壁時計のまま走らせると、同じ列の再生が20本中11本で揺れ、「可換でない」が出ることを実測で確かめてある）。
`_sns_ts` は版の順序そのものなので、ここが揺れると、同じ瞬間に2つの端末で消した行が違う強さの削除の版を持ち、状態の重複排除も効かなくなる。

そこで世界に時計 C を1本持たせ、操作が刻んだ値を操作の直後に C へ書き換える（`tools/explore/world.ts` の `applyOpWithClock`）。

- 書き換えるのは、その操作で書かれた行だけである。
  `_changelog` は採番値で、版は `_sns_lamport` が操作前の `_sns_clock.lamport` より大きいことで見分ける
- `changedAt` と `deletedAt` は全部 C にする
- `_sns_ts` は、その操作が刻んだ壁時計の値と等しいものだけを C にする。
  手元の Max が勝った削除の版（未来の時刻の行を消した場合など）は、アプリが書いた値のまま残る
- 書き換える表にはトリガーが無いので、記録は増えない

取り込みは相手の版をそのまま写し、相手の値は相手の操作の直後に C へそろえてあるので、同期の後に追いかける必要は無い。
同期と `tick` の後は C を「まだ誰も名乗っていない瞬間」にする。
状態の正規化では、名前が `At` で終わる列と `_sns_ts` を時刻として札にする（上の「現在時刻由来の値」）。

【確認】同じ C の瞬間に端末 a と b で同じ行を消すと、どちらの `_tombstone` も `deletedAt` と `_sns_ts` が C の同じ値になり、状態の直列化でも同じ札になる。
消してすぐ作り直した行の版の `_sns_ts` も C になる。

反例の再現手順では、操作に `[時刻 Ck]` と添えてある。
決定的テストへ書き下すときは、その操作の直後に `UPDATE _changelog SET changedAt = <Ck> WHERE id > <操作前の最大id>` と、`_tombstone` と `_sns_rows_<表>` の書き換えを当てればよい。
`_tombstone` は `deletedAt` を、`_sns_ts` はその操作が刻んだ値と等しいものを `<Ck>` にし、どちらも `_sns_lamport` が操作前の lamport より大きい行に限る。
同じ瞬間でなくても再現することが多いが、同着が効く反例では要る。

## 状態を減らす手

実装は `tools/explore/reduction.ts`（根拠つき）、自己検査は `tools/explore/self-test.ts`。

1. **重複排除** —— 訪れた状態の集合（親プロセスが正本を1つ持つ）。
   違う列でも同じ状態に行き着けば1回だけ展開する。
   何も起きない操作（無い行の削除など）もここで畳まれる
2. **順序の畳み込み（partial order reduction）** —— 同期と `tick` に挟まれた操作の連なりの中では、端末の違う操作は可換（操作が書くのは自分のローカルDBだけで、時刻は C で、`pruneChangelog` が読む相手の `_sync_state` を操作は書かない）。
   連なりの中は端末の番号の順に並んだものだけを展開する。
   **同期は NAS 上の相手のコピーを読み、`_sync_state` を書き、時計を進めるので、何とも入れ替えない。**
   重複排除と組み合わせるため、重複排除の単位は (状態, 次に操作してよい端末の集合) で、既に訪れた集合が新しい集合を包むときだけ畳む

**端末の入れ替えは畳まない。**
案A では同着の最後の鍵が `instanceId` のバイト列の比較（設計書 §1.2.4〜1.2.5）で、検査器は端末ごとに固定の `instanceId` を与えるので、端末を入れ替えた状態は鏡写しにならず、対称性の畳み込みは健全でない。
そのため `--no-symmetry` と、それが切っていた畳み込みは選択肢ごと落とした。
ほかに畳まないものは、id の入れ替え（同着の版の並べ方が真の id の正規形の順で決まる）、UNIQUE キーの値の入れ替え（子の表の操作が id から親の名前を決めているので、範囲が入れ替えについて閉じていない）、時刻の書式・値の入れ替え（字面と大小が効く）である。

`instanceId` は端末 a・b・c の順に `iid-X`・`iid-x`・`iid-y` で、バイト列の比較で a ＜ b ＜ c になる。
a と b は大文字小文字だけが違う。
版の比較がバイト列であることを踏めるようにするためで、本物の `instanceId` は小文字の16進なのでこの形は起きない。
逆向き（b の iid が小さい側）を調べるには、`tools/explore/world.ts` の `instanceIdFor` を逆順にして走らせ直すこと。

**`--self-test N`** は、範囲の中の列 N 本で「別々の端末への操作の可換性」を本物を動かして確かめ、崩れていれば探索しない。
`src/` が変わって前提が崩れる（例: 操作が相手の DB を読む箇所が増える、トリガーが新しい場所へ壁時計を刻む）と、畳んだ探索は黙って反例を見逃すので、**`src/` を大きく変えたあとは付けて走らせること。**
1回ずつ比べて違っても、すぐには崩れと決めない。
同期の中の刻みの揺れ（上の「保証しないこと」）に当たっただけかもしれないので、数回再生し直し、どの再生でも共通の結果が出ないときだけ崩れとする（揺れた本数は別に数えて出す）。
自己検査が崩れを見抜けることは、時刻の書き換えを外した検査器（壁時計のまま刻ませると「可換でない」が出る）で確かめてある。

## 並列化

- ワーカーは `child_process.fork`。
  **各ワーカーは専用の作業ディレクトリと専用の `TMPDIR`** を使う（共有すると互いのDBを消し合って偽の失敗が出る。ライブラリは相手のDBを `os.tmpdir()/sqlite-nas-sync` へ写すので、`TMPDIR` も分ける。`worker_threads` では `os.tmpdir()` をスレッドごとに分けられない）
- 探索は**層ごとの幅優先**。
  深さ d の節を全ワーカーで分けて展開し、深さ d+1 の子を親が集める
- **重複排除の集合は親が正本を持つ。**
  状態数が並列度によらず同じになり、最初に見つかる反例が本当に最短になる。
  親はワーカーから子が返ってくるたびに、受け入れた状態と検査の結果の覚えを他の全ワーカーへすぐ配り、ワーカーは手元の写しで先に捨てる（層の終わりにまとめて配る形では、同じ層で同じ状態を何度も検査して並列度を上げても縮まなかった）。
  行き違いで二重に検査するぶんは残るが、数も答えも変わらない
- 節の少ない層（根の層は1節）では、1つの節の遷移を範囲に分けて複数のワーカーへ配る

### 原則4 で子のバージョンを捨てていた形（2026-09-24 に出て、2026-09-25 に直した）

最後の行の反例は `src/` の側の不具合だった。
当時の `src/` は、親行の Max が削除の版のとき、あとから届いた子のバージョンを `_sns_rows_<表>` から捨てていた。
同期の最中の書き込みを使わなくても、次の手順で再現した（時刻はどれも 2026-01-01T00:00:00Z）。

1. b が `tag_notes` の n1 を書く（親の `tags` の g1 も作る）
2. b が同期する
3. a が `tags` の g1 を書く
4. a が g1 を消す（削除の版の `_sns_ts` は実行した時刻 C）
5. a が同期する
6. a が g1 をもう一度書く

このあと何度同期しても、a には n1 が無く、b には在るまま一致しなかった。

5 の同期で a は b の g1 と n1 を取り込む。
g1 の Max は a の削除の版なので、a は n1 のバージョンを捨てた。
6 で a が g1 を書き直すと、その版は単調化で C まで引き上がり、`_sns_lamport` で削除の版に勝つ。
b は a の写しから g1 の削除の版と新しい行の版を受け取るが、Max は行の版なので、b の手元で g1 が削除されていたことは一度も無く、n1 を捨てずに置く。
a は n1 のバージョンを失っていて、b の `_changelog` はもう読み終えているので、n1 を取り込み直す経路が無い。
捨てるかどうかがその端末がその時点で何を知っていたかで決まり、各端末のバージョンの集合が併合の外で変わったことが原因である。
検査器が出した最短の形は、2 と 5 の同期の最中（写す前）に 1 と 6 を書く4手だった。

**直し方**: 子のバージョンを捨てない。
親の Max が削除の版である間だけ、作り直しがその子を `ON DELETE` に従って扱う（`docs/principles.md` の付則3）。
ユーザーテーブルに入るかどうかはバージョンの集合だけで決まり、親が書き直されれば子は元の形で入る。
上の手順は `__tests__/parent-rewrite-after-delete.test.ts` で決定的に再現してあり、書き直したあと両方の端末に n1 がある。
同じ範囲の深さ4 で反例は無い（下の「確かめた結果（2026-09-25）」）。

**見張り**: 捨てる処理を戻す壊し方 `drop-parent-deleted-versions` を置いた。
判定6 に「一度見えたキーの版が同じ端末から消えないこと」を足したので、この壊し方は遷移3回で判定6 の違反になる。
`--all` で深さ4 まで走らせると、上の黙った食い違いも出る。

### 切り分け（2026-09-16 に出た反例の読み）

この範囲で出た反例は**3件とも検査器（参照実装の組み立て）の側の誤り**で、`src/` は設計どおりだった。
どれも「発行した操作の列からは決められないこと」を決められると思って組み立てていた形である。

| 出た反例                                                                                             | 実際は                                                                                                             | 直した所                                                                                        |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| a が同期の最中に `tag_profiles` の g1 を作り、b が同期の最中にそれを消す。本物は消え、参照実装は残す | b は消す前に a の版を**取り込んでいる**ので `_sns_clock.lamport` が引き上がり、削除の `L` が勝つ。設計どおり       | `from-history.ts` の `tiedAcrossInstances`（同着の `_sns_ts` が表の中で並ぶ列は突き合わせない） |
| a が `tags` の g1 を t2(T0) → t1(T1)、b が同期の最中に g2 を t1(T1)。本物は g2 が残り、参照実装は g1 | かぶりの勝者も `L` で決まる。b は取り込みで `L` が引き上がっている。設計どおり                                     | 同上（キーごとではなく**表ごと**に見る）                                                        |
| b の `tag_profiles` が読み替えで g1 として表示されているところへ `DELETE … WHERE id='g1'`            | 削除の版は**真の id**（g2）で記録される（§3.3 の `TRUE_ID`）。操作の列だけでは、どの真の id を消したか決められない | `from-history.ts` の `hasRemap`（読み替えのある列に削除があれば突き合わせない）                 |

**「参照実装との食い違い」は、まず参照実装の組み立ての限界を疑うこと。**
本物は同期の位置を知っていて、参照実装は知らない。
知らないことを決め打ちすると、設計どおりの実装が反例に見える。

## 反例の読み方

```
反例: 黙った食い違い（収束しても端末ごとに中身が違う）
要約: 往復しても一致しない行: users:u1

端末 client-a, client-b（…）。空の世界から、この順に:

  1. [時刻 C0] client-a: INSERT INTO users (id, name, updatedAt) VALUES ('u1', 'name1', '2026-01-01T00:00:00.000Z') ON CONFLICT(id) DO UPDATE …
  2. [時刻 C0] client-b: INSERT INTO users (id, name, updatedAt) VALUES ('u1', 'name2', '2026-01-01T00:00:00.000Z') ON CONFLICT(id) DO UPDATE …

そのあと client-a から round-robin で、状態が動かなくなるまで同期する:

  3. client-a: await performSync(client-a.db, client-a.config, TABLES)
  …
食い違っている行（updatedAt は julianday）:
  users:u1
    client-a: {"id":"u1","name":"name1","updatedAt":2461041.5}
    client-b: {"id":"u1","name":"name2","updatedAt":2461041.5}
```

挟み方の食い違いは**反例ではなく観察**として、統計のあとに代表例を1つだけ出す（罫線で囲まない。読み手が案A の破れと取り違えないため）。
同じ操作の列の実行を2つ並べる形は同じ:

```
観察: 同期の挟み方で見え方が変わる（案A では `_sns_ts` の引き上げがあるので、これは設計どおり。§9.25）
要約: 同じ操作の列のあと、client-a から始める round-robin と client-b から始める round-robin で、落ち着いた先の見え方が違う

── 実行A ──
  1. [時刻 C0] client-a: INSERT INTO tags (id, name, updatedAt) VALUES ('g1', 't2', '2026-01-01T00:00:01.000Z') ON CONFLICT(id) DO UPDATE …
  2. client-a: await performSync(client-a.db, client-a.config, TABLES)
  3. [時刻 C1] client-a: INSERT INTO tags (id, name, updatedAt) VALUES ('g1', 't1', '2026-01-01T00:00:02.000Z') ON CONFLICT(id) DO UPDATE …
  4. [時刻 C1] client-b: INSERT INTO tags (id, name, updatedAt) VALUES ('g2', 't2', '2026-01-01T00:00:00.000Z') ON CONFLICT(id) DO UPDATE …
  そのあと client-a から round-robin で、状態が動かなくなるまで同期する（10 回）
  端末ごとの、発行した操作の列（アプリが受け取った結果つき）:
    client-a: upsertTag g1 t2 @00:01 → row:ok ; upsertTag g1 t1 @00:02 → row:ok
    client-b: upsertTag g2 t2 @00:00 → row:ok
  落ち着いた先の見え方: g1=t1, g2=t2

── 実行B ──（1〜4 は同じ）
  そのあと client-b から round-robin で、状態が動かなくなるまで同期する（12 回）
  落ち着いた先の見え方: g1=t1 だけ
```

この例は旧方式のもの（畳みの向きで g2 が消える）。
案A で出る観察は、たいてい `_sns_ts` の引き上げが効いた側と効かなかった側の差である。

幅優先なので、出る反例は範囲の中で**遷移の数が最短**のもの。
各行はそのまま `__tests__/helpers/sync-fixtures.ts` の足場で `db.prepare(...).run(...)` と `performSync` を並べた決定的テストへ書き下せる。
題材の表の DDL は `tools/explore/world.ts` の `DDL` にあり、その足場と同じ形である。
検査器は端末ごとに `instanceId` を決めて与えるので、同着が効く反例を写すときは `RowsSyncRuntime.instanceId` も同じ値にすること。

## 検査器が反例を見逃さないことの確かめ方

見逃す検査器は「反例なし」と嘘をつくので、無いほうがましである。
`--mutant` は `src/` を作業ディレクトリへ写し、写しの1か所だけを過去の不具合へ戻してコンパイルし、それを駆動する（`src/` には触らない。書き換える箇所が見つからなければ止まる）。

```sh
npm run explore -- --list-mutants
npm run explore -- --mutant no-rebuilding-guard --tables tags --ids 2 --keys 1 --depth 2
npm run explore -- --mutant no-delete-exec-time --tables users --ids 1 --keys 1 --times 0 --depth 2
```

当てられなくなった壊し方も、消さずに `pending` に理由を書いて残す。
`--mutant` で選ぶと、その理由を添えて止まる。

- 旧方式の不具合を戻す壊し方（`stalemate-by-literal`・`no-stalemate-report`・`tie-by-literal`・`no-self-check`・`dedup-by-id`）は、旧経路が `src/` に無いので当てられない
- `sns-ts-as-text` は、時刻列が ISO 8601 の文字列でない表を題材から外したので当てられない。
  ISO の文字列だけでは、`_sns_ts` を TEXT 列にしても格納クラスも順序も変わらない
- `asymmetric-by-name` は、端末の入れ替えの畳み込みと、その自己検査を外したので確かめるものが無い

収束の判定は「不動点で全端末の見え方が一致すること」だけで、食い違いはどんな理由でも違反である。
旧方式には、解けない食い違いを `Stalemate on <表>:<id>` と報告して済ませる逃げ道があったが、案A にも検査器にも無い。

削減手が反例を消していないことは、同じ不具合で `--no-dedup` / `--no-por` をそれぞれ付けて、同じ反例が出ることで確かめる。

**原則2〜4 の壊し方は、一致の検査でも参照実装でも出ない。**

- `no-delete-exec-time` と `no-merged-tombstone`: 全端末が同じ規則で壊れるので、全端末は一致する。
  参照実装は、削除を実行した時刻と、そのとき何が統合されていたかを操作の列から決められないので、突き合わせを見送る。
  出るのは操作ごとの原則2・原則3 の確かめ（上の「操作ごとの原則2・原則3・原則4 の確かめ」）である
- `no-parent-discard`: アプリの表の見え方は同じ（捨てる行も置かない行も表に出ない）なので、判定4・10 では出ない。
  出るのは判定13 の後半で、本物の `_sns_unplaceable` に、参照実装が「捨てる行」とした子が載る。
  子のバージョンを捨てない形に直したので、この壊し方は下の4つに置き換えた
- `no-binary-collation`: 検査器は端末 a と b に大文字小文字だけが違う `instanceId`（`iid-X` と `iid-x`）を与えるので、同じ瞬間に同じ時刻で同じ行を書くと、畳んで比べる版では勝ち負けが決まらない。
  判定11 は検査器側の参照実装の順序を総当たりで見るものなので、駆動しているライブラリを壊しても何も言わない
