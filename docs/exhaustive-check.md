# 有界網羅検査（`npm run explore`）

収束の正しさを「**この範囲には反例が無い**」という事実として確かめる道具。
`tools/` にある。ライブラリ（`src/`）にもテスト（`__tests__/`）にも含まれない。

## なぜ要るか

`__tests__/convergence-properties.test.ts` は fast-check による**乱数**の性質テストで、
不具合を見つける網としては優秀だった。だが「直った」の判定には向かない。

- 乱数は「ある」は示せても「無い」は示せない。失敗率3%の族に「10回連続通過」は偶然で
  約73%起こり、実際に誤った「直った」報告が3回続いた
- 判定に要る本数が統計で決まり、38,400ケース・約25分かかっていた
- 生成器は操作の**種類**を均等に選ぶので、単純な操作ばかり繰り返し引き、特定の組み合わせは
  滅多に引かない。同じ小さい形を何度引いても重複排除しない

この道具は**範囲を有限に区切り、その中を乱数なしで漏れなく試す**。

さらに、1回の実行の中の一致だけでは原理的に見えない「**同じアプリ操作なのに、同期のタイミングが
違うと結果が違う**」も数える（下の「性質」の3）。実証（本物のコード）: ① a が g1 を t1 で作る、
② b が g2 を t1 で作る、③ b が g2 を t2 に変える。①② → 同期 → ③ → 同期 では g2=t2 だけが残り、
①②③ → 同期 では g1=t1, g2=t2 が残る。どちらも全端末は一致しているので、一致の検査では見えない。

**案A（`docs/rows-table-design.md` 第11版）では、これは違反ではない。** `_sns_ts` の引き上げ（§1.2.1）が
あるので、他端末の版を取り込んだあとに、より古い時刻でその行を書くと、取り込んでいなかった場合より
強い版になる。したがって挟み方の検査は**件数の記録**にし、代表例を1つだけ「（強）が破れた形の観察」として
出力の末尾に添える（§8.1・§9.25）。探索は止めない。

## 使い方

```sh
npm run explore                                   # 既定の範囲（下の表）
npm run explore -- --depth 4 --workers 8          # 深さと並列度を変える
npm run explore -- --tables accounts --formats 0,1
npm run explore -- --clients 3 --tables users --ids 1 --depth 4
npm run explore -- --self-test 200                # 削減手の前提を確かめてから探索する
npm run explore -- --depth 3 --oracle rows-d1     # 参照実装（案A の意味の定義）と見え方を突き合わせる
npm run explore -- --tables epoch_notes --ids 2 --keys 1 --depth 2 --oracle rows-d1
                                                  # 時刻列が INTEGER・行の時刻が数値の題材
npm run explore -- --tables nocase_notes --ids 2 --keys 1 --depth 2 --oracle rows-d1
                                                  # 時刻列が COLLATE NOCASE・大文字小文字だけ違う時刻の題材
npm run explore -- --help                         # 引数の一覧
```

`npm run explore` は `tsc -p tools/tsconfig.json` で検査器と `src/` を
`node_modules/.cache/explore/` へコンパイルしてから走らせる（`tsx` などは使わない。依存を増やさないため）。
駆動するのは**そのとき作業ツリーにある `src/`** である。

終了コードは、反例なし 0 / 反例あり 1 / 検査器そのものの失敗・自己検査の失敗・ディスク不足で中断 2。

作業ディレクトリ（既定 `$TMPDIR/sqlite-nas-sync-explore`）は終わると消す。途中で空きが 3GB（`--min-free-mb`）を
割ったら止める。`--all` で反例の多い版を走らせると、反例ごとに再生し直して再現手順を書くので遅くなる。

## 何を調べるか

### 遷移

状態から出る辺は次の4種類。**範囲の中の全部**を毎回試す。

- **操作**: 端末 i のローカルDBへ、選んだ表の upsert（id × キー × 時刻 × 書式 × 本文）・削除
  （`epoch_notes` / `nocase_notes` では id × 名前 × その表の時刻）、
  または `pruneChangelog`（`_changelog` を、いちばん遅れている相手の読み位置の1つ先まで削って
  隙間を作り、相手を**フルマージ経路**へ落とす）。中身は性質テストの `applyOp` / `pruneChangelog`
  と同じ（ローカルの制約違反は「その端末では起きなかった」、子の前に親を用意する）
- **同期**: 端末 i が本物の `performSync` を呼ぶ
- **時計を進める**（`tick`）: 以後の操作は、それまでのどの時刻より後を名乗る
- **同期の最中に書く**（`syncWrite`）: 端末 i が `performSync` し、その途中の `await copyToNas(...)`
  （`localDb.backup()`。非同期にページを写す）の待ちの間に、同じ端末のアプリが操作を当てる。
  `backup()` が呼ばれた直後・写し始める前（書き込みは NAS のコピーに載る。同期の冒頭の自己点検は
  この書き込みを見ていない）と、写し終えた直後（コピーに載らない。このあとの取り込みは見る）の2点。
  `src/` を変えずに差し込むため、同期のあいだだけその接続の `backup` を差し替える
  （`tools/explore/world.ts` の `syncWithWrite`。差し込めたことは、写し始める前ならコピーに載り、
  写し終えた後なら載らないことで確かめてある）。別の端末への書き込みは、同期する端末が読むのが
  相手の NAS 上のコピーなので、同期の前か後に書いた場合と区別が付かず、持たない

### 性質（各状態で）

1. **取り込みが失敗として飲み込まれない** —— 遷移でも検査の同期でも、`result.warnings` に
   `Sync failed for client …` が出たら違反（その相手からの同期が永久に止まる）。同じ壊れ方の
   フルマージ版 `Full merge failed for client …` と、`Failed to open remote database` も違反に数える。
   `performSync` が例外を投げても違反
2. **収束する** —— その状態から全端末を round-robin で同期し、状態が動かなくなったとき全端末の
   中身が一致すること。**一致しない行が1つでも残れば違反**（逃げ道は無い）。時刻列は `julianday` で
   比べる（同じ瞬間の書式違いは差と数えない）。
   - **全ての開始端末から**回す（a から始めたときだけ、b から始めたときだけ、の両方を見る）
   - 「動かなくなった」＝ (状態, 次の端末) が一度出た組へ戻り、その一巡で状態が1つも変わらなかった
   - 戻った一巡で状態が変わっていれば**振動**、`--max-probe-rounds × 端末数` 回同期しても
     戻らなければ**動き続けた**として、どちらも違反
3. **同期の挟み方で見え方が変わる件数**（挟み方の検査。`tools/explore/history.ts`）——
   **違反ではない。件数の記録である**（設計書 §8.1 第11版・§9.25）。案A では `_sns_ts` の引き上げが
   あるので、「同じ操作の集まり ⇒ 同じ見え方」（強）は成り立たない。
   **端末ごとの、検査器が発行したアプリ操作の列**（同期・時計・`pruneChangelog` は含めない）が同じ
   実行どうしで、全端末を不動点まで同期したときの見え方（同期対象の表の中身、`updatedAt` は
   julianday）が同じかを見る。同じ状態から開始端末だけを変えた round-robin で見え方が違う場合も数える。
   出力には**件数**と、いちばん短い**代表例1つ**（強いものを優先）を「（強）が破れた形の観察」として出す。
   - **実装から読み取ったもの（`_changelog`・`_tombstone`）では比べない。** 実装の判断を比べる単位に
     借りると、実装の誤りが判定に流れ込む
   - 端末ごとの列にするのは、別々の端末への操作の前後を入れ替えても列が変わらないようにするため
     （順序の畳み込みと両立させる）
   - **比べない履歴**（どちらも発行した操作だけから決める）: 同時刻で中身の違う upsert を含む
     （設計書の前提 P1）、同じ端末が同じキーへ自分の前の書き込みより古い時刻で書く（設計書の
     不変条件 I5。子の表の操作が親を自動で作った場合は、アプリに「挿入した」と返ったときだけ
     親の版も書き込みとして数える）。不動点で端末ごとに見え方が違って定まらない場合も比べない
   - 食い違いは2種類に分けて数える。**強い食い違い**はアプリが受け取った結果（変えた行数・制約違反）
     まで同じ実行どうしで、代表例に選ぶときはこちらを優先する。**弱い食い違い**は結果が違う実行どうしで、
     まだ届いていない行の削除（0行）や、届いた行と UNIQUE がぶつかる挿入（失敗）のように、設計上も
     結果が変わってよい形を含む（`--schedule-key ops+status` にすると弱い食い違いはそもそも比べない）
   - **どちらでも探索は止まらない。** 止まるのは他の違反（性質1・2、判定、参照実装との食い違い）だけである

## 案A のための判定と操作

`docs/rows-table-design.md`（案A）の §8 は、いまの3つの性質に加えて判定をあげている。
判定と操作は、**実装（`src/`）が案A になる前に**先に書いた。実装を書き終えてから判定を書くと、
実装に都合のよい判定しか思いつかないからである。

段階6 で `src/` は案A だけになったので、案A の表（`_sns_rows_*`）を読む判定は**実際に集めて当たる**。
案A でない版を駆動したときは何も集まらず、何も言わない（偽の反例を出さない側に倒してある）。

雛形の DB は `setupSync`（`src/index.ts`）と同じ順で仕立てる —— `migrateToRows` で案A の仕掛けを
取り付け、そのあと `setupRowsLedgers` で表に触らない帳簿を作る（旧方式の `setupChangelog` は
段階6 で消えた）。

### 参照実装 `rows-d1`

`tools/explore/oracles/rows-d1.ts`。設計書 §1（意味の定義）と §2（削除）を素直に写した、
「版の集合 → アプリの表の見え方」の計算である。

- **`src/` を一切呼ばない。** 呼べば `src/` の不具合をそのまま写して、判定が素通りする
- **速度より読みやすさを優先する。** 設計書の語（`Max`・候補・表示値・かぶり・勝者・隠れた行・
  置かない行・置く行）をそのまま関数名にしてある
- **SQLite に判定させるべきものは SQLite に判定させる。** 照合順序・CHECK・NOT NULL・型・部分索引・
  式索引・生成列・値の種類は、一時の `:memory:` DB へ**強い順に INSERT** して、返ったエラーの種類で
  「置かない行」と「隠れた行」を分ける。かぶりの相手（勝者）も、空の DB へ2つ入れてみて決める
  （索引の文を字句解析しないので、部分索引・式索引でも宣言どおりに効く）
- スキーマは `CREATE TABLE` の文だけを渡し、主キー・列・外部キー・NOT NULL・既定値は
  一時 DB の `PRAGMA` から読む（別に宣言させると、宣言と DDL がずれたときに黙って違う表を調べる）

**参照実装そのものの試験**は `tools/explore/oracles/rows-d1-tests.ts`。手で作った版の集合に対する
期待値を表にして並べてある（かぶり・隠れた行・削除・削除より新しい版・消してすぐ作り直す・
cascade で消えた子・置かない行（NOT NULL / CHECK）・`ON DELETE SET NULL`・読み替え・1:1 の表・
1:1 で読み替えた主キーの衝突・値の種類・照合順序）。どの事例でも

- 版を並べ替えても、同じ版を重ねて渡しても答えが変わらないこと（補題C）
- 置く行が本物の表に入り、外部キーを満たすこと
- 判定13（下記）

をあわせて見る。`npm run explore -- --unit-tests` と、探索の起動時に必ず走る。

**限界**: 主キー以外の UNIQUE 列を指す外部キーで、隠れた行の中から値の組を探すときだけは
照合順序を当てずに比べる（置く行は一時 DB へ問い合わせるので効く）。範囲の表にその形の外部キーは無い。

| -------------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| **時刻列を変えない UPDATE**      | `--keep-time-updates`    | 案A では版の `_sns_ts` が手元の `Max` まで引き上がる（設計書 §1.2.1）ので、時刻だけで比べる実装との差がここに出る                  |

### 行の時刻が文字列でない題材（`epoch_notes` / `nocase_notes`）

既定の題材の時刻列はどれも `TEXT` で、行の時刻も ISO 8601 の文字列だけである。それだけでは
設計書 §1.2.3（値の種類の順序）の群1・群2 と `COLLATE BINARY` の効き目を踏めないので、
**別の表の組**として足した（既定の範囲は変えない。状態が増えるので、引数で選ぶ）。

| 表の組         | 時刻列の宣言                    | 行の時刻                                                                | 何を踏むか                                                                                                                                                                    |
| -------------- | ------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `epoch_notes`  | `updatedAt INTEGER`             | 数値 `9e12` / `10e12` / `11e12` / `12e12`（群1）                        | `_sns_ts` を TEXT 列にする壊し方（`--mutant sns-ts-as-text`）。**数としての順序と字面の順序が食い違う**値にしてある —— 桁数のそろった値だけだと、群が動いても結果が変わらない |
| `nocase_notes` | `updatedAt TEXT COLLATE NOCASE` | 文字列 `TS-A` / `ts-a` / `TS-B` / `ts-b`（群2。`julianday` が読めない） | 比較の `COLLATE BINARY` を外す壊し方（`--mutant no-binary-collation`）。**大文字小文字だけが違う**組が、畳むと同着になる                                                      |

どちらも形は「id・`UNIQUE` な名前・時刻列」の3列で、操作は upsert と削除だけ。**時刻の値は表ごとに
決まっていて、`--times` / `--future-times` からは個数だけを採る**（`--formats` は効かない。値は4種類まで）。
この2つの表の時刻列は数値（群1）と `julianday` の読めない文字列（群2）なので、**削除を実行した時刻は
順序に使われない**（原則2 の条件。`docs/principles.md` の付則2）。削除の版の `_sns_ts` は手元の `Max` か
`OLD` の時刻列の値のままで、`--future-times`（「削除より後の時刻」）はこの並びの中の前後でしかない。

時刻の正規化（下の「時刻」）はこれらの値を**字面のまま**持つ。`julianday` がどれも読めないので、
実行中に刻まれる時刻との前後が付かず、順位へ畳む対象にならない。

### `--oracle rows-d1` の限界

判定4 の本来の入力は「判定2 で集めた版」だが、いまは `tools/explore/oracles/from-history.ts` が
**発行した操作の列から版を組み立てて**参照実装へ渡す。操作の列だけからは**同期がどこで挟まったか**が
分からないので、次の形では `null`（突き合わせない）にする。

1. `_sns_ts` の引き上げ: ありうる引き上げ方を全部試し、**どれでも同じ見え方になるときだけ**答える
2. cascade で消える子: 他の端末がその親の子を書いていれば、届いていたかどうかで削除の版の集合が変わる
3. 時刻列を変えない UPDATE: 版に載る時刻が「そのとき行に入っていた値」なので、他の端末も触るキーでは決まらない
4. `instanceId` の向き: 端末の並び順を両方試し、どちらでも同じ見え方になるときだけ答える
   （同着が `iid` で決まる形は、設計上も端末の乱数で決まる）
5. **`L`（lamport）の引き上げ**: 取り込みは `_sns_clock.lamport` を受け取った版の最大まで引き上げる
   （設計書 §4.3・不変条件 C）ので、取り込んだあとの書き込みは大きい `L` を名乗る。`L` が効くのは
   `_sns_ts` が同着のときだけなので、**同じ表に、違う端末の版が同着の `_sns_ts` で並ぶ**列は突き合わせない
   （同じキーの `Max` だけでなく、かぶりの勝者もここで決まるので、キーごとではなく表ごとに見る）
6. **読み替えのあとの削除**: アプリは表示上の id で消すので、かぶりに負けて読み替えられた行があると、
   同じ `DELETE` 文が違う真の id の版を作る（§1.6・§3.3 の `TRUE_ID`）。読み替えが起きている列に
   削除があれば突き合わせない

**見落としはしても誤検出はしない**側に倒してある。5 と 6 は 2026-09-16 に足した ——
それまでは**案A の実装が設計どおりなのに反例が出ていた**（下の「切り分け」）。

### 旧方式に当てた結果（記録。段階6 で `src/` から消えた）

段階5 までの `src/` は旧方式（`_changelog` の LWW）だったので、参照実装 `rows-d1` と当然食い違った。
いちばん短い反例は「1台だけが書いて、消して、同じ id で作り直す」列で、旧方式は削除が刻む
`_tombstone.deletedAt`（実行時の現在時刻）を行の `updatedAt`（2026-01-01）と比べるため、作り直した行を
「削除より古い」と判定して落としていた（穴8）。案A では作り直しの版の `_sns_ts` が手元の `Max` へ
引き上がり、`L` が削除より大きいので**同じ端末の後の書き込みが勝つ**（補題A、設計書 §2.4 (4)）。

段階6 で旧経路は消えたので、この食い違いはもう出ない。同じ形は `--mutant no-ts-raise`

## 保証すること・しないこと

### 保証すること

**「反例は無かった」と出たら、印字された範囲の中の、深さ以下の全ての遷移の列について**:

- 途中のどの遷移でも取り込みの失敗・例外が起きず、
- 途中のどの状態から round-robin で同期しても（どの端末から始めても）、上限以内に不動点へ届き、
  そこで全端末の中身が一致する
- 参照実装を選んでいれば（`--oracle rows-d1`）、突き合わせられる列については、案A の意味の定義から
  計算した見え方と本物の見え方が一致する

ことを、本物の `performSync` と本物の SQLite ファイルDBで実際に確かめた。確率ではない。

**挟み方の検査はここに入らない。** それは違反ではなく件数の記録なので、「反例なし」と出た実行でも
強い食い違いが何組かある（設計書 §9.25）。
出力に「調べた状態」「当てた遷移」の数と範囲を必ず添えるので、それが根拠になる。

### 保証しないこと（範囲と模型の外）

- **範囲の外は何も見ない。** 端末の台数、表の組、id・キー・時刻・本文の種類、深さを超えた列は
  調べていない。「深さ3で反例なし」は「深さ4で反例なし」を意味しない
- **時計の模型の外。** 操作が刻む時刻（`_changelog.changedAt`・`_tombstone.deletedAt`）は、
  世界に1本の時計 C へそろえる（下の「時計」）。同期を挟まない操作は、端末が違っても同じ瞬間か、
  `tick` を挟んだ順に並ぶ。**端末ごとの時計のずれ**（同期より前の時刻を名乗る操作、未来の時刻を
  名乗る削除）は表せない。行の `updatedAt` は範囲の時刻から選ぶので、こちらはずれを含めて表せる
- **削除・changelog の時刻は常に行の時刻より後。** 行の時刻は 2026-01-01、削除は実行時の現在時刻。
  原則2 により、削除の版の `_sns_ts` もその現在時刻になる（時刻列が ISO 8601 の文字列である表のみ）。
  性質テストと同じ条件で、「削除より新しい書き込み」は範囲の時刻からは作れない —— `--future-times`
  （2099-01-01）で作る
- **同期の中の刻みの揺れ。** 同期そのものが刻む時刻（取り込みで書かれる版の `_sns_ts`、
  `_tombstone` の時刻など）は書き換えない（ライブラリの振る舞いそのものなので）。同じ同期の中の
  2つの刻みが同じミリ秒に収まるかは実行ごとに揺れうる（実測: 端末 b の最初の同期で、取り込んだ行の
  トリガと `_tombstone` のトリガが同じミリ秒に収まるかどうか）。別の行どうしの刻みの前後が効く箇所
  （版の順序 `(_sns_ts, _sns_lamport, _sns_instance)` の比較）があるので、正規化で潰すことはしない。探索は揺れのうち
  **その実行で起きた方**だけを調べる。揺れた場合は「再生して違う状態に戻った節」として数と列を出す。
  このため「調べた状態」の数は実行ごとに1%未満ずれることがある
- **round-robin 以外の同期の順**での収束は、検査としては見ない（ただし探索そのものが同期の順を
  全部試すので、深さの範囲内の途中状態としては現れる）
- **中身が一致した後の「正しさ」**（どちらの版が残るべきだったか）は見ない。見るのは一致と報告だけ
- **保持期間（7日）を過ぎる掃除・NAS の I/O 障害・プロセスの異常終了・
  スキーマの版違い**は範囲に入っていない
- **子の表の操作は id から親を1つに決めている**（`g1` の子は `t1` という名前の `g1` を親に取る。
  `tag_notes` の `n1` は `g1` を指す）。別の親を指す子・別の名前の親を作る子は範囲に無い
- **3台では対称性で畳まない**が、3台の round-robin の開始端末は「a,b,c の回転」だけ（a,c,b の順は
  検査の同期としては回さない）
- **挟み方の検査の限界**: そもそも違反として数えない（案A では成り立たない。§9.25）。件数は
  「（強）がどれくらい破れているか」の目安であって、多いこと自体は不具合ではない。
  同期の最中の書き込みは、同期する端末への書き込みで、`backup()` の前後の2点だけ
  （写している途中のページの境目には差し込まない）。比べるのは不動点での見え方で、途中の見え方の違い
  （一時的に見える・消える）は見ない。深さの範囲に入っている挟み方どうしだけを比べる
- **判定19 は配線していない**（上の表）。版の鍵そのものが中継で書き換わる形を名指しで見る筋書きが無い

## 状態と正規化

状態は「全端末のローカルDB」「NAS 上の各端末のコピー」「時計」を
正規化して直列化したもの。**含め忘れると別の状態を同じと見て探索を打ち切り、反例を見逃す**ので、
以後の振る舞いに効くものは全部含める。判断の根拠は `tools/explore/state.ts` の冒頭にある。

**重複排除の単位は (状態, 発行した操作の列, 比べてよい履歴か, 次に操作してよい端末の集合)。** 挟み方の検査は列の性質
（同じ操作の列の実行どうしを比べる）なので、状態だけで畳むと、違う操作の列から同じ状態へ合流した
列の片方を見失い、その列の挟み方どうしの比較を落とす。そのぶん節は増えるが、子の状態と結果は操作の
列によらないので、**世界の上で同じ状態の節は組にして、遷移を1回だけ実行する**（実測: 最小の範囲・
深さ4で、状態 24,290・節 125,338 に対し、実行した遷移は節ごとの 144,027 から 68,115 へ。状態・
操作の列・食い違いの数はまとめる前と一致した）。鏡写しの節どうしは同じ遷移の添字が鏡写しの端末を
指すので、並びを変えない直列化の鍵で組にする。

| 含める                                                                     | 理由                                                                            |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 同期対象の表の行（全列、**rowid 順**）                                     | 全件を `ORDER BY` なしで読む箇所は rowid 順に処理するので、並びも振る舞いに効く |
| `_sns_rows_<表>`（在るときだけ）                                           | 案Aの版の表。これが違えば次の作り直しの結果が違う                               |
| `_sns_clock` / `_sns_shown` / `_sns_hidden` / `_sns_dirty`（在るときだけ） | 版の順序・隠れた行・作り直しの要否に効く                                        |
| `_tombstone`（全列、rowid 順）                                             | 削除の版。取り込みと表示の計算に効く                                            |
| `_changelog`（id・表・行・操作・時刻）                                     | 差分同期で流れる中身                                                            |
| `sqlite_sequence`                                                          | 次に振られる changelog の id                                                    |
| `_changelog_prune.prunedThroughId`                                         | 隙間の判定                                                                      |
| `_sync_state`（相手・lastSeenId）                                          | 次にどこから読むか                                                              |
| `_sync_meta`                                                               | **self-check が「どこまで見直したか」を changelog の id で置いている**          |
| スキーマ（`sqlite_master` の要約）                                         | フルマージはトリガを外して付け直す                                              |
| NAS 上の各端末のコピー（上の全部）                                         | 相手が読むのはこちら                                                            |
| NAS のその他のファイル名                                                   | `.tmp` の残骸など                                                               |
| 時計 C                                                                     | どの刻みと等しいか（等しくなければ「fresh」）だけ                               |

| 含めない                     | 理由                             |
| ---------------------------- | -------------------------------- |
| 空きページ・ファイルの大きさ | 論理的な中身だけが振る舞いに効く |

### 採番値は生のまま

`_changelog.id`・`lastSeenId`・`prunedThroughId` は**ずらさない**。相対値にすると畳める状態は増えるが、
絶対値が効く箇所がある（`hasChangelogGap` の `lastSeenId === 0` / `prunedThroughId > 0`、
`pruneChangelog` の `id <= floor + 1`、`_sync_meta` の位置）。

### 現在時刻由来の値は、大小と同着の関係だけを残す

- 範囲で決めた行の時刻は**字面のまま**（書式違いは別の値）
- 実行中に刻まれた時刻は、状態に現れる全ての時刻を `julianday` の順に並べた**順位**へ置き換える。
  同じ瞬間は同じ順位。**字面が違えば順位の中でさらに区別する**（字面で比べる箇所があるため）

ライブラリが時刻を扱うのは (a) `julianday` による大小・同着、(b) 字面の一致、
(c) `julianday('now', '-7 days')` との大小、の3つで、(a)(b) は順位で保たれ、(c) は「実行中の時刻は
常に保持期間内、行の時刻は常に保持期間外」なので状態によらず答えが決まる。**この前提は毎回確かめ、
崩れたら例外で止める。**

## 時計

トリガが刻む壁時計のままだと、別々の端末への操作 x, y を x→y と y→x で当てたときに刻まれる時刻の
前後が入れ替わり、**結果の状態が同じにならない**。すると順序の畳み込みの前提が崩れ、しかも同じ列を
再生しても同じミリ秒に収まるかで結果が揺れる（`--self-test` で壁時計のまま走らせると、
同じ列の再生が20本中11本で揺れ、「可換でない」が出ることを実測で確かめてある）。

そこで世界に時計 C を1本持たせ、操作が刻んだ `_changelog.changedAt` と `_tombstone.deletedAt` を
操作の直後に C へ書き換える（`_changelog` / `_tombstone` にはトリガが無いので記録は増えない）。
同期と `tick` の後は C を「まだ誰も名乗っていない瞬間」にする。反例の再現手順では、操作に
`[時刻 Ck]` と添えてある。決定的テストへ書き下すときは、その操作の直後に
`UPDATE _changelog SET changedAt = <Ck> WHERE id > <操作前の最大id>` と
`UPDATE _tombstone SET deletedAt = <Ck> WHERE …（その操作で書かれた行）` を当てればよい
（同じ瞬間でなくても再現することが多いが、同着が効く反例では要る）。

## 状態を減らす手

実装は `tools/explore/reduction.ts`（根拠つき）、自己検査は `tools/explore/self-test.ts`。

1. **重複排除** —— 訪れた状態の集合（親プロセスが正本を1つ持つ）。違う列でも同じ状態に行き着けば
   1回だけ展開する。何も起きない操作（無い行の削除など）もここで畳まれる
2. **順序の畳み込み（partial order reduction）** —— 同期と `tick` に挟まれた操作の連なりの中では、
   端末の違う操作は可換（操作が書くのは自分のローカルDBだけで、時刻は C で、`pruneChangelog` が読む
   相手の `_sync_state` を操作は書かない）。連なりの中は端末の順に並んだものだけを展開する。
   **同期は NAS 上の相手のコピーを読み、`_sync_state` を書き、時計を進めるので、何とも入れ替えない。**
   重複排除と組み合わせるため、重複排除の単位は (状態, 次に操作してよい端末の集合) で、既に訪れた
   集合が新しい集合を包むときだけ畳む
3. **対称性（端末の入れ替え）—— 案A では外してある。** 下の「端末の入れ替えは対称でない」
   - **畳まないもの**: 3台での端末の入れ替え（取り込む順が `readdirSync` の順で決まる）、
     id の入れ替え（同着は主キーの辞書順で決まる）、UNIQUE キーの値の入れ替え（子の表の操作が
     id から親の名前を決めているので範囲が入れ替えについて閉じていない。索引の順に返す問い合わせの
     有無を全部は確かめていない）、時刻の書式・値の入れ替え（字面と大小が効く）

### 端末の入れ替えは対称でない（2026-09-17）

案A は同着の最後の鍵が `instanceId` のバイト列の比較（設計書 §1.2.5）で、検査器は端末ごとに
`iid-client-a` / `iid-client-b` を**固定して**与える（`tools/explore/world.ts` の `instanceIdFor`）。
すると「自分の iid が相手より小さい端末が書いた」状態と「大きい端末が書いた」状態は、端末を
入れ替えても同じにならない ——**後の同着の決着が逆になる**。`--self-test` は素の `src/` で、
**1回の書き込みだけの列でも鏡写しにならない**ことを検出する。

そこで `config.ts` の `symmetryActive` を常に `false` にした。実測で確かめたこと:

- 状態の数は変わらない（既定の範囲・深さ2 で 4,653 状態・7,758 遷移。ON でも OFF でも同じ）。
  正準な鍵は「入れ替えの候補の中で直列化がいちばん小さいもの」なので、鏡写しでない状態どうしが
  畳まれることはなく、**畳めるものがもともと無かった**
- ただし ON のままだと、**入れ替えを当てた鍵が作られる**（直列化が小さくなる側の候補が選ばれる）。
  挟み方の食い違いの件数はこの鍵で数えるので、鏡写しでない実行どうしが「同じ操作の列」に見えて
  件数が水増しされていた（同じ範囲で 強い216組 → 48組）。POR の「次に操作してよい端末の集合」も
  同じ入れ替えで写るので、**畳みすぎる余地があった**

逆向き（b の iid が小さい側）を調べるには、`instanceIdFor` を逆順にして走らせ直すこと。

**`--self-test N`** は、範囲の中の列 N 本で「別々の端末への操作の可換性」を本物を動かして確かめ、
崩れていれば探索しない。`src/` が変わって前提が崩れる（例: 端末名の
大小を比べる箇所が増える）と、畳んだ探索は黙って反例を見逃すので、**`src/` を大きく変えたあとは
付けて走らせること。** 1回ずつ比べて違っても、すぐには崩れと決めない。同期の中の刻みの揺れ
（下の「保証しないこと」）に当たっただけかもしれないので、数回再生し直し、どの再生でも共通の結果が
出ないときだけ崩れとする（揺れた本数は別に数えて出す）。**端末の入れ替えの検査は、対称性を外して
あるので回らない**（回せば必ず崩れる。上の節）。自己検査が崩れを見抜けることは、時刻の書き換えを
外した検査器（壁時計のまま刻ませると「可換でない」が出る）で確かめてある。

## 並列化

- ワーカーは `child_process.fork`。**各ワーカーは専用の作業ディレクトリと専用の `TMPDIR`** を使う
  （共有すると互いのDBを消し合って偽の失敗が出る。ライブラリは相手のDBを `os.tmpdir()/sqlite-nas-sync`
  へ写すので、`TMPDIR` も分ける。`worker_threads` では `os.tmpdir()` をスレッドごとに分けられない）
- 探索は**層ごとの幅優先**。深さ d の節を全ワーカーで分けて展開し、深さ d+1 の子を親が集める
- **重複排除の集合は親が正本を持つ。** 状態数が並列度によらず同じになり、最初に見つかる反例が本当に
  最短になる。親はワーカーから子が返ってくるたびに、受け入れた状態と検査の結果の覚えを他の全ワーカーへ
  すぐ配り、ワーカーは手元の写しで先に捨てる（層の終わりにまとめて配る形では、同じ層で同じ状態を何度も
  検査して並列度を上げても縮まなかった）。行き違いで二重に検査するぶんは残るが、数も答えも変わらない
- 節の少ない層（根の層は1節）では、1つの節の遷移を範囲に分けて複数のワーカーへ配る

## 反例の読み方

```
反例: 黙った食い違い（収束しても端末ごとに中身が違う）
要約: 往復しても一致しない行: users:u1

端末 client-a, client-b（…）。空の世界から、この順に:

  1. [時刻 C0] client-a: INSERT INTO users (id, name, updatedAt) VALUES ('u1', 'name1', '2026-01-01T00:00:00.000Z') ON CONFLICT(id) DO UPDATE …
  2. [時刻 C0] client-b: INSERT INTO users (id, name, updatedAt) VALUES ('u1', 'name2', '2026-01-01T00:00:00.000Z') ON CONFLICT(id) DO UPDATE …

そのあと client-a から round-robin で、状態が動かなくなるまで同期する:

  3. client-a: await performSync(client-a.db, client-a.config, TABLES)
  …
食い違っている行（updatedAt は julianday）:
  users:u1
    client-a: {"id":"u1","name":"name1","updatedAt":2461041.5}
    client-b: {"id":"u1","name":"name2","updatedAt":2461041.5}
```

挟み方の食い違いは**反例ではなく観察**として、統計のあとに代表例を1つだけ出す
（罫線で囲まない。読み手が案A の破れと取り違えないため）。同じ操作の列の実行を2つ並べる形は同じ:

```
観察: 同期の挟み方で見え方が変わる（案A では `_sns_ts` の引き上げがあるので、これは設計どおり。§9.25）
要約: 同じ操作の列のあと、client-a から始める round-robin と client-b から始める round-robin で、落ち着いた先の見え方が違う

── 実行A ──
  1. [時刻 C0] client-a: INSERT INTO tags (id, name, updatedAt) VALUES ('g1', 't2', '2026-01-01T00:00:01.000Z') ON CONFLICT(id) DO UPDATE …
  2. client-a: await performSync(client-a.db, client-a.config, TABLES)
  3. [時刻 C1] client-a: INSERT INTO tags (id, name, updatedAt) VALUES ('g1', 't1', '2026-01-01T00:00:02.000Z') ON CONFLICT(id) DO UPDATE …
  4. [時刻 C1] client-b: INSERT INTO tags (id, name, updatedAt) VALUES ('g2', 't2', '2026-01-01T00:00:00.000Z') ON CONFLICT(id) DO UPDATE …
  そのあと client-a から round-robin で、状態が動かなくなるまで同期する（10 回）

    client-a: upsertTag g1 t2 @00:01 → row:ok ; upsertTag g1 t1 @00:02 → row:ok
```

幅優先なので、出る反例は範囲の中で**遷移の数が最短**のもの。各行はそのまま
`__tests__/helpers/sync-fixtures.ts` の足場で `db.prepare(...).run(...)` と `performSync` を並べた

## 検査器が反例を見逃さないことの確かめ方

見逃す検査器は「反例なし」と嘘をつくので、無いほうがましである。`--mutant` は `src/` を
作業ディレクトリへ写し、写しの1か所だけを過去の不具合へ戻してコンパイルし、それを駆動する
（`src/` には触らない。書き換える箇所が見つからなければ止まる）。

```sh
npm run explore -- --list-mutants
npm run explore -- --mutant no-rebuilding-guard --tables tags --ids 2 --keys 1 --depth 2
npm run explore -- --mutant sns-ts-as-text --tables epoch_notes --ids 2 --keys 1 --depth 2 --oracle rows-d1
```

旧方式の不具合を戻す壊し方（`stalemate-by-literal`・`no-stalemate-report`・`tie-by-literal`・
`no-self-check`・`dedup-by-id`）は、**段階6 で旧経路が `src/` から消えたので当てられない**。
一覧には「いまは当てられない」と理由つきで残してある（消すと、検査器が何を見ていたかの記録も消える）。

とくに前の2つが見ていた「膠着（stalemate）」——「どちらも勝てない食い違いを、解かずに
`Stalemate on <表>:<id>` として報告する」という旧方式の逃げ道——は、**案A には無い**
（`src/` はこの警告を1つも出さない）。検査器の側も、収束の判定からこの逃げ道を落としてある。
判定はいま「不動点で全端末の見え方が一致すること」だけで、食い違いはどんな理由でも違反である
（報告があれば見逃す、という穴が無くなったぶん**厳しくなった**）。

削減手が反例を消していないことは、同じ不具合で `--no-dedup` / `--no-por` / `--no-symmetry` を
それぞれ付けて、同じ反例が出ることで確かめる。

### 確かめた結果（2026-09-16、端末2〜3台・並列度6）

段階6 の `src/`（案A だけ）に、案A 用の壊し方6つを当てた結果。**どれも反例が出る。**

| 戻した不具合                                                              | 範囲                                                                    | 検査器が出した反例                                                                       |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `no-rebuilding-guard`（トリガーの番人を外す）                             | `--tables tags --ids 2 --keys 1 --depth 2 --oracle rows-d1`             | **不動点に達しない**、遷移1回（作り直しの適用そのものが事実を作り、同期が止まらない）    |
| `no-ts-raise`（`_sns_ts` の引き上げをやめる）                             | `--tables tags --ids 1 --keys 1 --depth 3 --recreate --oracle rows-d1`  | **参照実装との食い違い**（判定4）、遷移3回                                               |
| `import-rewrites-lamport`（取り込みが `_sns_lamport` を自分の値で上書き） | `--clients 3 --tables tags --ids 1 --keys 2 --depth 3 --oracle rows-d1` | **判定5 違反**（同じ版の鍵なのに中身が違う）、遷移2回。設計書の判定19 の中身はこれである |

後ろの2つは**新しい題材**（`epoch_notes` / `nocase_notes`）が要る。既定の題材では、時刻列がどれも
`TEXT` で行の時刻も ISO の文字列なので、格納クラスも照合順序も動かず、壊しても結果が変わらない。
どちらも「壊していない `src/` では同じ範囲で反例なし」（各 646状態・26秒）を確かめてある。

**`sns-ts-as-text` と `no-binary-collation` は、設計書が挙げていた判定（12・5・11）では出ない。**

- `sns-ts-as-text`: 全端末が同じ壊れ方をするので、端末をまたいだ突き合わせ（判定5・12）は通る。
  破れるのは**順序**（群1 が群2 へ移り、数の順序が字面の順序に置き換わる）なので、意味の定義を
  持っている参照実装との突き合わせ（判定4）でしか見えない。したがって `--oracle rows-d1` が要る
- `no-binary-collation`: 判定11 は**検査器側の参照実装の順序**を総当たりで見るものなので、
  駆動しているライブラリを壊しても何も言わない。出るのは判定1（黙った食い違い）である

## 設計書（`docs/rows-table-design.md`）へ申し送ること

検査器を段階6 に合わせて仕上げた結果、設計書 §8 の字面と食い違うところが4つある。
**この文書からは直せない**（設計書は別の担当が持っている）ので、ここに書き出しておく。

1. **`sns-ts-as-text` は判定12・判定5 では出ない。** §8.4 の表は「判定12（格納クラス込みの
   突き合わせ）と判定5」と書いているが、全端末が同じ壊れ方をするので端末をまたいだ突き合わせは通る。
   破れるのは**順序**（群1 が群2 へ移り、数の順序が字面の順序に置き換わる）なので、意味の定義を
   持っている**判定4（参照実装との一致）**でしか見えない。踏むには、字面の順序と数の順序が食い違う
   数値の時刻が要る（桁数のそろった値では、群が動いても結果が変わらない）
2. **`no-binary-collation` は判定11 では出ない。** 判定11 は**検査器側の参照実装**の順序を総当たりで
   見るもので、駆動しているライブラリの比較は見ていない。実際に出るのは判定1（黙った食い違い）である。
   ライブラリ側の順序を直に見る判定が要るなら、`src/rows/versions.ts` の比較を外から呼ぶ口が要る
3. **判定19（受け取った版をそのまま格納）は配線していない。**
   中身は判定5（同じ版の鍵なら同じ中身）が3端末で拾える（`--mutant import-rewrites-lamport` で確認）が、
   「版の鍵そのものが中継で書き換わる」形を名指しで見てはいない
4. **端末の入れ替えは、案A ではもう対称ではない。** 同着の最後の鍵が `instanceId` のバイト列の比較
   （§1.2.5）なので、「iid の小さい端末が書いた」状態と「大きい端末が書いた」状態は入れ替えても
   同じにならない。§8.2 の「検査器の作り」が対称性の畳み込みを前提にしているなら、そこを直すこと
   （検査器の側は外した。状態の数は変わらない）

あわせて、**参照実装の組み立て（`from-history.ts`）の限界が2つ増えた**（`L` の引き上げ・
読み替えのあとの削除）。どちらも「操作の列からは同期の位置が分からない」ことによるもので、
設計の穴ではない。
