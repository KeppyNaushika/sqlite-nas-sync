# 行の版の表（案A）の設計

この文書は保守者向けで、同期を**どう実現しているか**を書く。
何を保証するかの正本は [`principles.md`](principles.md) で、この文書と食い違えばそちらが正しい。
`src/` と `tools/` のコメントは「設計書 §1.2.3」のように節番号でこの文書を参照するので、節番号は変えないこと。

表記: 【確認】＝実物を動かして確かめたこと。【推測】＝確かめていない見立て。【決定】＝この設計で選んだこと。

**用語の対応。** この文書とソースのコメントは、`principles.md` の用語を次の語で呼ぶ。

- **版** ＝ バージョン。**行の版**は `INSERT` / `UPDATE` の、**削除の版**は `DELETE` のバージョン
- **アプリ** ＝ アプリケーション
- **アプリの表** ＝ ユーザーテーブル。**同期する表**は、そのうち同期の対象になるもの
- **端末** ＝ クライアント
- **帳簿**・**補助の表** ＝ 内部テーブル
- **事実** ＝ 手元にある版の集合。アプリの書き込みが作った版と、取り込んだ版からなる
- **強い** ＝ 付則1 の順序で大きい。`Max` は、その主キーでいちばん強い版
- **引き上げ** ＝ 単調化
- **作り直し** ＝ 再構築
- **真の id** ＝ 版が持つ本来の主キー。**表示上の id** は、統合で読み替えたあとの主キー
- **隠れた行** ＝ 統合でアプリの表に出ない側。**勝者**は表に出る側

**案B を退けた理由。**
案B は、統合で隠れた行を `_hidden_*` と `_repoint` に記録しておき、勝者が消えたらアプリの表へ戻す案だった。
戻す処理はアプリの表への書き込みなので、アプリの表の `UNIQUE` に当たる。
2行の値を入れ替える書き込み（`A=t1, B=t2 → A=t2, B=t1`）が届くと、1行ずつ戻す途中で必ず衝突し、同期が止まる。
設計の穴探しでは、必須の修正が8つ出た。
案A は行を戻さず、版の集合からアプリの表を丸ごと作り直すので、値の入れ替えも通る（§3.7.2）。

**規則と論証は、任意の SQLite の表、宣言された UNIQUE と外部キー、任意の書き込み方に対して書く。**
**自前の字句解析はできるだけ減らし、判定は SQLite 自身にさせる。**

## 0. 要約

- **目標（弱）**: (a) 同じ事実を受け取った端末は同じ表示になる。(b) 同期が永久に止まらない。(c) 同期の処理そのものは事実を作らない。データを消すのはアプリの書き込みだけ
- 同期する表 `t` ごとに `_sns_rows_<t>` を置く。UNIQUE も外部キーも付けない
- 版の鍵は、順序用の時刻 `_sns_ts`・書き込み順 `_sns_lamport`・端末の `_sns_instance` の3つ
- アプリの接続でアプリの表に起きた変化は、原因によらずすべて事実になる（R0）
- かぶりと行に閉じた制約の判定は、一時の `:memory:` DB へ強い順に INSERT して SQLite 自身に決めさせる
- 取り込みは相手の版を**書き換えずにそのまま**格納する。中継に必須である（§4）
- 計算は `worker_threads`、適用は主スレッドで行う。見送りが3回続いたら、計算と適用を1つのトランザクションで行う

## 1. 目標と意味の定義

### 1.1 目標

| 記号 | 目標                                                                                                     |
| ---- | -------------------------------------------------------------------------------------------------------- |
| (a)  | 受け取った事実の集合（の各キーの最強の版）が同じ端末は、作り直しが成功した時点で、アプリの表の中身が同じ |
| (b)  | 同期が永久に止まらない                                                                                   |
| (c)  | 同期の処理は事実を作らない。データを消すのはアプリの書き込みだけ                                         |

(c) から導かれる性質: `_sns_rows_*` から行が消えるのは、アプリの書き込みが作った削除の版に負けたときだけである。
アプリが消した行に `ON DELETE CASCADE` でつながる行も、アプリの表で消えるので削除の版ができる（R0）。
統合されていた行を消したときは、隠れていた側にも削除の版ができる（原則3。§3.4）。
親が削除されているのでアプリの表に入らない子の版も捨てない（原則4。§2）。
各端末の版の集合は、主キーごとに強い方を残す併合でしか変わらない。

### 1.2 事実と版の順序

行の版 `W(t, k, ts, L, iid, c)` と削除の版 `D(t, k, ts, L, iid)`。
`k` は真の id。

#### 1.2.1 順序用の時刻 `_sns_ts`（引き上げ）

```
_sns_ts := 次の3つのうち最も強いもの（§1.2.3 の順序）
   (1) 行の版: アプリの表の時刻列の新しい値
       削除の版: 削除を実行した時刻（§2）。時刻列の無い表では NULL
   (2) 手元の _sns_rows_<t> の同じ真の id の _sns_ts
   (3) 手元の _tombstone の同じ真の id の _sns_ts
どれも無ければ OLD の時刻列の値
```

(3) を入れないと、取り込んだ強い削除を、そのあとのアプリの削除が弱い版で上書きし、`Max` が後退する。
**対価**: 一度でも異常に大きい時刻が入ると、その行の `_sns_ts` は以後その高さに固定される。

#### 1.2.2 「2段階の規則」を採らない理由

キーごとに最強の版だけを保存する実装と両立しないため。
【確認】両立しない反例を実験で確かめた。

#### 1.2.3 時刻の比較（値の種類）

| 群  | 条件                            | 群の中の比べ方   |
| --- | ------------------------------- | ---------------- |
| 0   | `typeof(x) = 'null'`            | 同着             |
| 1   | `integer` / `real`              | 数値のまま       |
| 2   | `text` で ISO 8601 の字形でない | `COLLATE BINARY` |
| 3   | `text` で ISO 8601 の字形       | `julianday(x)`   |
| 4   | `blob`                          | `COLLATE BINARY` |

群は 0 ＜ 1 ＜ 2 ＜ 3 ＜ 4。
同期する表の時刻列には群3 の値しか入らない（P15）。
それでも群の順序を残しているのは、どの値の組にも順序を付けて全順序を保つためである。
群3 以外が `_sns_ts` に入るのは、時刻列の無い表の NULL、旧方式から移した墓標で `deletedAt` が群3 でないときの NULL、P15 を入れる前の版の端末から届いた版だけである。
判定に使う `GLOB` は**全端末で同じ文字列**でなければならない。
正本は `src/rows/versions.ts` の `ISO_SHAPE_GLOBS` で、トリガーもそこから借りている。

```sql
-- ISO(x)
(typeof(x) = 'text' AND julianday(x) IS NOT NULL AND (
     x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]:[0-9][0-9]'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]:[0-9][0-9].*'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]*Z'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]*[+-][0-9][0-9]:[0-9][0-9]'))
```

4つめの `GLOB` を `….[0-9]*` にしても、群の分かれ方は変わらない。
違いは「小数点のあとに数字が無い形」だけで、【確認】`'2026-01-01T00:00:00.'` と `'2026-01-01T00:00:00.Z'` は `julianday` が NULL を返すので、どちらの `GLOB` でも群3 にはならない。
ただし字形の判定は全端末で同一でなければならないので、変えるなら全端末を同時に変える必要がある。

**限界**: 存在しない日付（`'2026-02-30'`）を通す。末尾に空白があると群2 に落ちる。ミリ秒より細かい差は丸められる。

#### 1.2.4〜1.2.5

時刻の列を進めない書き込みは許容する。
順序 `≺` は `( _sns_ts, L, iid )` の辞書順。
すべて等しければ種類で決め、行の版 ＜ 削除の版とする。
次の性質を使う。

- 不変条件 U: `(t, k, iid, L, 種類)` が版を一意に定める
- 不変条件 C: clock は手元の全ての `L` 以上
- 補題A: 同じ端末の後の書き込みが強い
- 補題B: 削除は手元の Max より強い
- 補題C: `≺` は全前順序である。したがってキーごとに最強の版だけを保存してよい

### 1.3〜1.7 候補・表示値・かぶり・勝者・見え方

- **候補（1.3）**: `Max` が行の版である id。`Max` が削除の版の id は死んでいる
- **表示値（1.4）**: 外部キーの列は、同期する親を指していれば親の `Res_p` で読み替える。1:1 の表では `disp(pk) = Res_p(真の pk)`。親が統合で隠れた行なら、その `Res_p` は勝者の値なので、子は勝者の子として表示される（原則4 の前半）
- **親が置かれていないとき（1.4）**: 宣言された `ON DELETE` に従う。`SET NULL` / `SET DEFAULT` で列を NULL や既定値にできれば、その値で置く。できなければ**置かない行**で、版は残る。親が消えている理由で2つに分ける
  - 親の `Max` が削除の版である、または親自身がこの理由で置かれていない → **親が削除されているので置かない行**（原則4、付則3。`src/rows/derive.ts` の `parentDeleted`）。原因として大元の削除を持ち、`_sns_unplaceable` に書く（§3.5）
  - それ以外（親がまだ届いていない、親が置かない行になった） → 原因の無い置かない行
  - どちらも版の集合とスキーマだけで決まる。親が同じ主キーで書き直されて `Max` が行の版になれば、次の作り直しで子は置く行になる
  - 外部キーは親の主キーを参照する（P14）ので、親は `Res_p` だけで引ける
- **置かない行（1.4）**: 主キーが NULL の行と、一時 DB への INSERT が白紙のリストのエラーで失敗した行。白紙のリストは `NOTNULL` / `CHECK` / `TRIGGER` / `DATATYPE` / `MISMATCH` で、正本は `src/rows/derive.ts` の `UNPLACEABLE_CODES`。それ以外のエラーは中止して例外にする
- **かぶり（1.5）**: 一時 DB への INSERT が `UNIQUE` / `PRIMARYKEY` / `ROWID` で失敗すること。勝者は、全ての索引と主キーで引き直して、かぶった置く行のうち最も強いものにする。索引の情報は `PRAGMA index_list` / `index_xinfo` から取り、字句解析するのは部分索引の `WHERE` と式索引の式だけである
- **強い順（1.6）**: 版の順序の強い順に一時 DB へ入れる。すべて等しければ真の id の正規形の小さい順。入った行が**置く行**、かぶりで落ちた行が**隠れた行**になる。隠れた行の `Res` は勝者の `Res`
- **見え方（1.7）**: `Φ(F)` は各表の「置く行の表示値」。作り直しが成功した時点で、アプリの表の中身は `Φ(F)`

### 1.8 前提

- P1: 主キーが `TEXT` で宣言され、NULL を取らない。値は端末をまたいで一意な id（UUID / cuid）であることを前提にする。`INTEGER PRIMARY KEY` の自動採番は、別々の端末が同じ値を別の行に割り当てるので断る
- P2: 表の依存が循環しない。自己参照は許す
- P4: 全端末で同じスキーマ・同じ SQLite の版
- P5: アプリの接続で外部キーが有効。`setupSync` は `PRAGMA foreign_key_check` で親のいない子を探し、あれば警告する
- P6: アプリのトリガーは適用の間は発火しない
- P8: 部分索引の述語と式索引の式が字句解析でき、決定的でない関数が無い
- P9: `instanceId` が重ならない
- P10: WAL
- P11: 主キーが1列
- P12: アプリの表を書くすべての接続で `PRAGMA recursive_triggers = ON`
- P13: アプリの列名が `_sns_` で始まらない
- P14: 同期する表を親とする外部キーは、親の主キーを参照する。子が同期しない表でも同じ。列を書かない `REFERENCES parent` は主キーを指すので通す
- P15: 同期する表の時刻列の値が ISO 8601 の文字列（§1.2.3 の群3）。`setupSync` が既存の行を確かめ、導入後はトリガーが `RAISE(ABORT)` で書き込みを止める
- P16: アプリの表とビューが内部テーブルの名前を使わない。`setupSync` は、内部テーブルの名前を持つビューと、ライブラリが読む列の無い表を見つけると例外にする。名前と列の一覧の正本は `src/setup/rows-preflight.ts` の `INTERNAL_TABLE_COLUMNS` で、`_sns_rows_` で始まる表には版の3列を求める

破れていれば `setupSync` が例外にするか警告する。
確かめる処理は `src/setup/rows-preflight.ts` にある。

### 1.9〜1.11

真の id の正規形は `CAST(x AS TEXT)`。
`_tombstone.recordId` が現れるすべての比較で、この正規形を通す。

## 2. 削除の意味

D1: id で消す。
D2 は「アプリが指示していない行までライブラリの判断で消す」ので採らない。

R0: アプリの接続で起きた変化はすべて事実になる。
利用者の削除、`ON DELETE CASCADE` で消えた子・孫、`SET NULL` / `SET DEFAULT` / `ON UPDATE` による書き換え、`INSERT OR REPLACE` が追い出した行を含む。

`principles.md` の原則2〜4 を、次のように実現する。

- **順序**（原則2）。削除の版の `_sns_ts` は、削除を実行した時刻・`_sns_rows_<表>` の `_sns_ts`・`_tombstone` の `_sns_ts` のうち最も強いもの。時刻列の値は ISO 8601 の文字列に限る（P15）ので、実行した時刻とそのまま比べられる
- **統合の単位**（原則3）。統合されていた行を消したら、`_sns_hidden` で隠れていた側の主キーにも削除の版を書き、`_changelog` で告げる。隠れている行はアプリの表に無く、`DELETE` トリガーが発火しないので、消した側のトリガーでまとめて書く（§3.4）
- **親の削除**（原則4、付則3）。親を消した端末にその時点であった子は、SQLite が `ON DELETE` に従って消すか書き換え、その変化がトリガーで版になる（R0）。それ以外の子、つまり親の削除と並行に他の端末で書かれた子は、版を捨てない。親の `Max` が削除の版である間だけ、作り直しがその子を `ON DELETE` に従って扱う（§1.3〜1.7）。`CASCADE` / `RESTRICT` / `NO ACTION` では置かない行、`SET NULL` / `SET DEFAULT` では列を書き換えて置けるときだけ置く。孫にも連鎖する
- 子ごとの墓標は書かない。子がアプリの表に入らないのは親の `Max` が削除の版である間だけで、親が書き直されれば入る。墓標を書くと、子の版が削除の版に負けて、親を書き直しても子が戻らなくなる
- 版を捨てないのは、捨てるかどうかがその端末がその時点で何を知っていたかで決まり、版の集合が併合の外で変わるからである。捨てていたときは、親を消した端末が子を取り込んで捨てたあとで親を書き直すと、その端末だけ子を失い、一致しなかった（`docs/exhaustive-check.md`）
- 入らなくなった子と再び入った子は、前回との差で `SyncResult.parentDeleted` / `parentReturned` に載せる（§4.4）

### 3.1 表の一覧

| 表                                                                                                                | 他端末が読むか | 中身                                                                                                                                        |
| ----------------------------------------------------------------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `_sns_rows_<表>`                                                                                                  | 読む           | 生きている id の最強の行の版。アプリの列（生成列を除く。型名を写すのは主キーだけ）＋ `_sns_ts`（型名なし）・`_sns_lamport`・`_sns_instance` |
| `_tombstone`                                                                                                      | 読む           | 削除の版。`tableName`・`recordId`・`deletedAt` ＋ `_sns_ts`（型名なし）・`_sns_lamport`・`_sns_instance`                                    |
| `_changelog`                                                                                                      | 読む           | 読み直すキーの通知                                                                                                                          |
| `_changelog_prune`                                                                                                | 読む           | 掃除した位置 `prunedThroughId`                                                                                                              |
| `_sync_meta`                                                                                                      | 読む           | `schemaVersion`（`<アプリの版>;sns-format=rows1`）、`sns.instanceId`、**`sns.generation`**、**`sns.lastInstance`**、**`sns.lastLamport`**   |
| `_sync_state`                                                                                                     | 読まない       | 相手ごとの読み位置 `lastSeenId`                                                                                                             |
| `_sns_clock` / `_sns_tick` / `_sns_shown` / `_sns_hidden` / `_sns_unplaceable` / `_sns_dirty` / `_sns_rebuilding` | 読まない       | 時計・表ごとの tick・作り直しの出力・警告の重複回避・対象・旗                                                                               |

`_sns_rows_<表>` の主キー以外のアプリの列には型名を書かない。型名の無い列は BLOB 親和性で、入れた値をそのまま持つ。
型名を写すと、STRICT の表の `ANY` 列の値が変わる。`_sns_rows_<表>` は STRICT でないので、型名 `ANY` は NUMERIC 親和性になり、文字列 `'123'` が整数 `123` になる。
STRICT でないアプリの表では、`_sns_rows_<表>` に入るのはアプリの表が親和性で変換したあとの値で、作り直しで同じ親和性をもう一度当てても値は変わらない。
主キーの列だけは型名を写す。親和性が食い違うと、`_sns_shown` から引いた文字列の id が整数の id と一致しなくなるからである。

NAS の写しには、「他端末が読む」表だけを載せる（§4.1）。
`_changelog` の `AUTOINCREMENT` の値も、`sqlite_sequence` から元のまま写す。
アプリの表・トリガー・「読まない」表は載せない。

`_sync_meta` の鍵の名前は上のとおりに固定する（H）。
`sns.generation` は `copyToNas` の前に +1 する値である。
`sns.lastInstance` / `sns.lastLamport` は、自分が最後に NAS の写しへ書いたときの `instanceId` と `lamport` である。

### 3.2 `_sns_rows_<表>`・`_sns_clock`・`instanceId`

`_sns_clock(onlyRow, lamport, importTick, instanceId)`、`_sns_tick(tableName, tick)`。
`instanceId` は `setupSync` のたびに `crypto.randomBytes(16)` で作る。

**`_sns_clock` の行はトリガーでは作らない。**
行が失われたら `lamport` が 0 から数え直され、不変条件 C が破れるからである。
行が無ければアプリの書き込みが `NOT NULL` で失敗する（気づける）形が正しい。
行を作るのは表の作成と `setupSync` / `performSync` だけ。
`_sns_tick` はトリガーの `ON CONFLICT DO UPDATE` で作ってよい。

### 3.3 生成に使う式

`GUARD`（`NOT EXISTS (SELECT 1 FROM _sns_rebuilding)`）、`ISO(x)` / `GRP(x)`、`TSGT(a,b)`、`NEWTS`（3項の最大。`UNION ALL` + `ORDER BY` の形）、`STRONGER(a,b)`、`TICK(t)`、`TRUE_ID(v)`、`KEY_TEXT(v)`。
定義は `src/rows/triggers.ts` にある。

### 3.4 トリガー

同期する表ごとに4本作る。
INSERT、UPDATE が2本（主キーが変わる・変わらない）、BEFORE DELETE である。
すべての `WHEN` に `GUARD` を入れ、本体の書き込みは `ON CONFLICT` の形で書く。
`_changelog` は対象なしの `ON CONFLICT DO NOTHING` で書く。
`TICK(t)` は本体の先頭に置く。
UPDATE で書かれなかった列は3分岐で決める。
`NEW."c" IS NOT OLD."c" COLLATE BINARY` なら `NEW."c"`、`_sns_rows_*` に行があればその値、無ければ `OLD."c"` である。
1:1 の表で表示 id だけが変わる場合は削除の版を作らず、`_sns_shown` の書き換えは**本体の最後**に置く。
`PRAGMA recursive_triggers = ON` が要る（P12）。

DELETE の `_sns_ts` は、削除を実行した時刻・`_sns_rows_*` の `_sns_ts`・`_tombstone` の `_sns_ts` のうち最も強いもので、どれも無ければ `OLD` の時刻列に落ちる（原則2）。
時刻列の値は群3 に限る（P15）ので、実行した時刻はいつも混ぜる。
時刻列の無い表では実行した時刻を使わない。その表の行の版の `_sns_ts` はいつも NULL なので、削除にだけ時刻を与えると群の差だけで削除が必ず勝つ。

INSERT と UPDATE の2本は、本体の先頭で `NEW` の時刻列が群3 かを確かめ、違えば `RAISE(ABORT, …)` でアプリの書き込みを失敗させる（P15）。
AFTER トリガーの `ABORT` はその文の変更を取り消すが、同じトランザクションのそれより前の文は残す。
判定の式は `src/rows/triggers.ts` の `isIsoTimeSql` で、`setupSync` の確かめもこれを使う。

BEFORE DELETE はさらに、`_sns_hidden` でその行の後ろに隠れている主キーにも削除の版を書き、負けた行の版を落とし、`_changelog` で告げる（原則3）。
隠れている行の `_sns_ts` は、削除を実行した時刻・**その行自身が持っている版の時刻**・`_tombstone` の時刻のうち最も強いもの。
勝っている側の版の時刻は持ち込まない。
隠れている行はアプリの表に無く、その DELETE トリガーは発火しないので、ここでまとめて書くしかない。

### 3.5 補助の表

`_sns_shown(tableName, trueId, shownId)` は主キーが `(tableName, trueId)` で、`(tableName, shownId)` に UNIQUE 索引を張る。
`_sns_hidden(tableName, trueId, winnerId)`、`_sns_unplaceable(tableName, trueId, reason, causeTable, causeId)`、`_sns_dirty(tableName)`。
`_sns_shown`・`_sns_hidden`・`_sns_unplaceable` は作り直しの**出力**である。
`_sns_unplaceable` の `causeTable` / `causeId` は、親が削除されているので置かない行の大元の削除で、それ以外の置かない行では NULL である。
0.20.0 の DB にはこの2列が無いので、`setupSync` が `ALTER TABLE … ADD COLUMN` で足す。
同期は作り直しの前後でこれらの表を読み、その差を報告にする（§4.4）。

### 3.6 他端末が読む範囲

相手の `_sns_rows_<t>` と `_tombstone` の強い方が `Max`。
`_changelog` は通知だけ。

### 3.7 作り直し

範囲は `_sns_dirty` の表とその子孫の表。
表示値のために祖先も**計算する**が、**適用はしない**。
`_sns_shown`・`_sns_hidden`・`_sns_unplaceable` も、適用した表の分だけ書き直す。
祖先について計算した分は書かない。

#### 3.7.1 計算（worker_threads）

```
ワーカー: 読み取り専用で開き、defaultSafeIntegers(true)（一時 DB の接続にも）
BEGIN                                   -- (A-2) 計算全体を読みのトランザクションで囲む
  token = { 計算に使う表ごとの _sns_tick.tick, _sns_clock.importTick }   -- (A-1) どのデータより先に読む
  一時 DB（:memory:）を用意する（同期する表の CREATE TABLE と索引だけ。アプリのトリガーは写さない）
  _sns_rows_*、_tombstone、_sns_shown、_sns_hidden を読む
  表は依存の順に: 表示値 → 強い順に一時 DB へ INSERT（置く行／隠れた行／置かない行（親が削除されているものは原因つき）／中止）
  アプリの表を読み、差（消す行・入れる行）を作る
COMMIT
```

**(A-1) token を最初に読む。**
一時 DB の用意より後に読むと、その間の書き込みを見落とす。

**(A-2) 読みのトランザクションで囲む（必須）。**
読み取り専用の接続でも、**トランザクションで囲まないと文ごとに別の快照を見る**。
【確認】親の表を読んだあとに主スレッドが親を消すと、子だけが新しい姿で読まれ、「計画が裂けたまま token が一致して適用される」ことが起きる。
アプリが消した行が表に戻ってしまう。
`BEGIN`（読みの `DEFERRED`）で囲めば、最初の読みで快照が固まる。

**token の役割と守りの分担。**
token が捕まえるのは、計算を始めてから適用の `BEGIN IMMEDIATE` を取るまでの書き込みだけである。
適用の最中は旗が立っていて `_sns_tick` も進まないので、token では捕まえられない。
そこは **`BEGIN IMMEDIATE` が握る書き込みのロック**が守る。

自己参照する表は、候補を深さの順に決める。
同じ表の候補を親に持たない候補が深さ0で、子の深さは親の深さの最大に1を足したものである。
`SET DEFAULT` の外部キーでは、既定値が指す候補も親に数える。
深さの順に決めるので、子を見るときには同じ表の親の `Res` と削除が揃っている。
同じ深さの中は §1.6 の強い順で入れ、隠れた行の勝者はその深さを入れ終えたところで決める。
輪の上にある候補と輪に繋がる候補は深さが決まらないので、置かない行にする（§6.5 の8）。

**値の受け渡し。**
ワーカーは `defaultSafeIntegers(true)` なので、大きい整数は `BigInt` で返る。
`BigInt` は `postMessage` の構造化複製でそのまま渡せる。
そこで**主スレッドへ `BigInt` のまま渡し、適用の接続でも `defaultSafeIntegers(true)` にして `BigInt` のまま束縛する**。
`Number` へ戻すと 2^53 を超える値が壊れる。

#### 3.7.2 適用（主スレッド）

入口は2つある。
「通常」と、「k 回目の合流」である。
合流では計算も同じトランザクションの中で行う。
**適用は、その表の「消す行」と「入れる行」をまとめて当てる。実質は表全体の入れ替えである。**
UNIQUE の値の入れ替え（`A=t1,B=t2 → A=t2,B=t1`）が通るのはこのためである。

```
db.inTransaction なら何もしない
prevFK = PRAGMA foreign_keys; prevBusy = PRAGMA busy_timeout      -- トランザクションの外で読む
PRAGMA busy_timeout = 0（通常）/ 数十 ms（k 回目）; PRAGMA foreign_keys = OFF   -- 外で設定する
try:
  BEGIN IMMEDIATE
  通常の入口では token を確かめ、違えば ROLLBACK して「見送り」として抜ける（見送り回数 +1）
  旗を立てる（_sns_rebuilding）
  アプリのトリガーを外す（"main"."…" / "temp"."…" と修飾。temp の sql には TEMP を挿し直す）
  消す行 → 入れる行（生成列は書かない）→ §3.7.5 の後始末
  _sns_shown・_sns_hidden・_sns_unplaceable を、適用した表の分だけ書き直す
  アプリのトリガーを戻す
  外部キーの検査: 対象 = 適用した表 ∪ 後始末で触った表 ∪ それらを親として参照している表。
     表ごとに `PRAGMA foreign_key_check(<表>)` を1つずつ。違反があれば ROLLBACK して §6.2 の出口へ
  DELETE FROM _sns_dirty WHERE tableName IN (<適用した表>)   -- 旗が立っている間に消す
  旗を下ろす
  COMMIT（見送り回数を 0 に戻す）
catch (e):
  db.inTransaction なら ROLLBACK
  **(J) e.code === 'SQLITE_BUSY' なら「見送り」として抜け、見送り回数 +1。それ以外は投げ直す**
finally:
  db.inTransaction が真なら例外（PRAGMA を戻せないまま進ませない）
  そうでなければ PRAGMA foreign_keys = prevFK; PRAGMA busy_timeout = prevBusy
```

**(J)**: `busy_timeout = 0` の `BEGIN IMMEDIATE` は**例外を投げる**（`SQLITE_BUSY`）。
これを投げ直すと見送りに数えられず、k 回目の合流経路に永久に入らない。
`SQLITE_BUSY` と token の不一致の**両方**を見送りに数える。

適用は `_sns_rows_*` を書かない。
親が削除されているので置かない行も、版は `_sns_rows_*` に残る。

#### 3.7.3 アプリのトリガーの外し戻し

`DROP TRIGGER "main"."<名前>"` / `"temp"."<名前>"` と schema を修飾する。
`sqlite_temp_master` の `sql` には `TEMP` の語が入らないので、`CREATE` の直後に `TEMP` を挿入してから実行する。

#### 3.7.4 見送りが続いたときの経路

見送り回数は `SyncInstance` の記憶に全体で1つ持つ。
**`SQLITE_BUSY` と token の不一致の両方を数える**（J）。
確定したとき、または `_sns_dirty` が空のときに 0 に戻す。
k（既定 3）回目は、`busy_timeout` を数十 ms にして `BEGIN IMMEDIATE` し、その中で計算と適用を続けて行う。

#### 3.7.5 同期しない表からの外部キーの後始末（B）

`foreign_keys = OFF` の下では `ON DELETE` は自動では起きないので、**ライブラリが手で当てる**。
適用のトランザクションの中で、アプリの表から消えた親を指す**同期しない表**の子を、宣言どおりに始末する。
子を消すとその子を親とする孫が孤児になるので、変化が無くなるまで繰り返す。

| その外部キーの `ON DELETE` | 子への当て方                                                               |
| -------------------------- | -------------------------------------------------------------------------- |
| `CASCADE`                  | 子を消す                                                                   |
| `SET NULL`                 | その外部キーの全列を NULL にする。**NOT NULL の列を含むなら子を消す**      |
| `SET DEFAULT`              | その外部キーの全列を既定値にする。既定値の親が居なければ子を消す           |
| `RESTRICT` / `NO ACTION`   | 子を消す。残すと外部キーの検査に引っかかり、その表が永久に作り直せなくなる |

同期しない表の子は、親が統合で隠れた行になっても勝者へ付け替えない。
隠れた親の主キーはアプリの表に無いので、上の表のとおりに始末される。
触った表は外部キーの検査の対象に含める。

### 3.8 版の確認

`_sync_meta.schemaVersion = <アプリの版>;sns-format=rows1`。
値が違う端末どうしは、互いに読み飛ばす。

### 3.9 移行・列の増減（C・D・E・F・G）

移行は1つのトランザクションで行う。
`setupSync` のたびに呼ばれ、既に案A の DB なら `_tombstone` と `_changelog` を作り直さず、列の増減と仕掛けの取り付けだけを行う。

1. `_sns_clock`（行を作る）、`_sns_tick`（表ごとの行）、`_sns_shown` などの補助の表を作る
2. **`_tombstone` と `_changelog` は作り直す**（F）。理由は次のとおり
   - 【確認】行のある `_tombstone` に `ADD COLUMN "_sns_lamport" INTEGER NOT NULL` は、既定値なしでは断られる。空の表では通る。行の有無で変わるので、`DEFAULT 0` を必ず書くか作り直す
   - 【確認】旧 `_tombstone.deletedAt` に既定値が無い DB では、新しいトリガーの INSERT が `NOT NULL constraint failed: _tombstone.deletedAt` で落ちる
   - 旧 `_changelog` は列が違うので、`CREATE TABLE IF NOT EXISTS` では追いつかず、最初の書き込みが落ちる
   - 作り直しでは必要な列だけを写す。**旧方式の「畳み」の事実（`_id_merge`・`mergedInto`・`revokedAt`）は捨てる**。捨てた結果、畳まれていた敗者 id の行が他端末から届けば重複として現れる。案A では重複は両方残り、勝者を選んで片方を隠すだけなので、問題にならない
3. アプリの表に同じ id がある `_tombstone` の行は写さない。比較は `recordId = CAST(<主キー> AS TEXT)`。写す行は `_sns_lamport = 0`、`_sns_instance` ＝ 自分、**`_sns_ts` は旧 `deletedAt`**。旧 `deletedAt` はその削除を実行した時刻なので、原則2 のとおりそれで比べる。旧 `deletedAt` が群3 でないとき、または時刻列の無い表では NULL（群0＝最小）
4. **`_sns_rows_<t>` へ写す行の版（C）**: `_sns_ts` ＝ **アプリの表の時刻列の値**（§1.2.1 の (1) と同じ）、`_sns_lamport = 0`、`_sns_instance` ＝ 自分
   - 時刻列の値は全端末で同じ文字列なので、`_sns_ts` に入れても端末差にならない
   - 【確認】`_sns_rows_*` の `_sns_ts` を NULL にすると、移行した2端末の同じ行の勝敗が `(群0, 0, instanceId)` の比較になり、**起動ごとに変わる乱数（`instanceId`）で決まる**
5. トリガーを作る（4本）。**`_sns_rebuilding` に残った行があれば、トリガーを作る前に消す**（I）
6. **`_changelog` は刈らない**（G）。旧版の端末が残っている間に刈ると、その端末へ渡すべき事実が消える。隙間の検出は既存の仕組みに任せる
7. `_sync_state` を空にし、`sns.instanceId` / `sns.generation` / `sns.lastInstance` / `sns.lastLamport` を書き、全表を `_sns_dirty` に入れる

旧版が残した仕掛けも、同じトランザクションで撤去する。

- `_heartbeat` の表とトリガーを落とす。トリガーを先に落とす。表だけ先に消すと、以後の `ALTER TABLE` が DB の全トリガーを読み直すときに落ちる
- 誰も読まない列を、列があるときだけ `ALTER TABLE … DROP COLUMN` で落とす。対象は `_tombstone.mergedInto` / `revokedAt`、`_sns_unplaceable.reasonKind` / `noticedAt`、`_changelog_prune.prunedAt`、`_sync_state.lastSyncedAt` で、正本は `src/rows/migrate.ts` の `UNUSED_COLUMNS`。`_heartbeat` のトリガーを落としたあとに行う
- `_sync_meta` の `sns.deleteProtected` の鍵を消す
- 主キー以外のアプリの列に型名のある `_sns_rows_<表>` は、型名の無い表を作って行をそのまま写し、置き換える。0.21.0 までは型名を写していた（§3.1）。行も版も変えないので、既に変換された値は元に戻らない

撤去を済ませた DB は、撤去前の版のライブラリでは開き直せない。
落とした列を名指しで書き込むので、`no such column` で失敗する。

**列が増えた／減ったとき（D・E）**

- **その表のトリガー4本を落として作り直す**（D）。【確認】作り直さないと、列を落とした場合はアプリの INSERT が `has no column named …` で落ち、増えた場合は新しい列が事実にならず、作り直しのたびにアプリが書いた値が既定値へ戻る
- **列の増減があった表は、その端末が移行の中で全行を新しい版として書き直す**（E）。アプリの表の現在の内容を使う。`_sns_ts` は §1.2.1 の3項の最大、`_sns_instance` は自分である。`_sns_lamport` は進めた値で、表ごとに1つでよい。鍵は `(t, k, iid, L, 種類)` なので、行が違えば重ならない
- **「既定値を1回評価して埋める」は採らない**。【確認】評価のたびに変わる既定値では、端末ごとに違う値が同じ版の鍵で入り、永久に食い違う
- 既定値が評価できず、その列が NOT NULL の場合は `setupSync` で例外にする
- 増えた列は `_sns_rows_*` に型名なしで足す（§3.1）。アプリの表に居ない行は、既定値が定数ならその定数で埋める。定数はアプリの列と同じ型名で、アプリの表が STRICT なら STRICT の一時の表に入れて読み直した値にする。字面のまま入れると、アプリの表に入る値と型が違い、作り直しがその行を毎回違うと数える
- `_sns_rows_*` から列を落とす場合、【確認】**主キーの列は `DROP COLUMN` できない**（`cannot drop PRIMARY KEY column`）。索引の張られた列も落とせない。`_sns_rows_*` は主キーにしか索引を張らないので、主キー以外は落とせる
- **アプリの表の主キーの列名が変わった・消えた場合は `setupSync` で例外にする**。行の同定ができなくなるためである
- 列の増減があった表は `_sns_dirty` に入れる

### 3.10 外部での複製・復元・書き換えの検出

| 検出                                  | 条件・手当て                                                                                                                                                                                                                                                 |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 復元・巻き戻り                        | NAS 上の自分の写しの `sns.lastLamport` より手元の `lamport` が小さい、または `sns.generation` が写しより小さい。**判定は、その同期回の取り込みより前に行う**（H）。取り込みが `lamport` を引き上げると証拠が消える。知らせたうえで、必要なら §3.9 のやり直し |
| 仕掛けの欠け                          | トリガーが無い、`_sns_clock` の行が無い、`_sns_tick` の行が足りない → 作り直す。**`_sns_rebuilding` に行が残っていれば、知らせたうえで `setupSync` の中で、トリガーを作る前に消す**（I）。残っているとアプリの書き込みが1つも事実にならず、警告も出ない      |
| **`_tombstone` の版の列が欠けている** | **`_sns_ts` / `_sns_lamport` / `_sns_instance` のどれかが無ければ、§3.9 の移行のやり直しを呼ぶ**。【確認】欠けたままだと、アプリの DELETE がトリガーごと `table _tombstone has no column named _sns_ts` で落ちる。アプリの文が失敗する                       |
| 写しの取り合い                        | 自分が写しを書いたあとにだけ判定する。NAS 上の自分の写しの `instanceId` が自分のものでなければ、同期を止めて知らせる                                                                                                                                         |

## 4. 同期の流れと取り込み

### 4.1 `performSync` の段階

| 段階 | 内容                                                                                                                                                    |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | `writeSchemaVersion`。**§3.10 の復元・巻き戻りの判定（取り込みより前）**。トリガー・`_sns_clock` の行・`_sns_tick` の行・`_sns_rebuilding` の残りの確認 |
| 1    | 相手の列挙と、隙間の事前確認                                                                                                                            |
| 2    | 相手ごとに取り込み → 作り直し → `sns.generation` +1 → `copyToNas`。作り直しが例外で止まっても、`copyToNas` まで行ってから投げ直す                       |
| 3〜5 | `cleanupChangelog`、`onAfterSync`                                                                                                                       |

**NAS への写しには、他の端末が読む表だけを載せる**（`src/nas.ts` の `copyToNas`）。
まず `backup()` で、手元の一時領域に DB 全体の一貫した写しを取る。
`copyFile` では WAL の `-wal` が付いてこないので、写しから `_sns_rows_*` の最近の書き込みが見えない。
次に新しい DB へ、§3.1 で「読む」の表を、元と同じ `CREATE` 文と索引で作って行を写す。
`sqlite_sequence` の値も元のまま写す。
隙間の判定（§4.3 の規則2・3）とフルマージのあとの読み位置が、`_changelog` が振った最大の id としてこの値を読むからである。
行から数え直すと、いま残っている最大の id になり、末尾が消えた相手を見逃すか、フルマージを繰り返す。
最後にそれを NAS へ置いて `rename` する。
不要な表を `DROP` して作る方法は採らない。アプリの仮想表は、そのモジュールを登録していない接続では `DROP` できないからである。

アプリの表とトリガーは、他の端末も自分の写しの確認（§3.10）も読まない。
フルマージが表の名前の綴りを揃えるときも、相手の `_sns_rows_<表>` の名前から引き、相手のアプリの表は見ない。

**写しは取り込みと作り直しのあとに作る。**
取り込みで変わった版と中継の通知が、その回の写しに載る。
取り込みより前に作ると、それが載るのは次の回になり、その写しを読んだ端末の上げ直しもさらに1回ずつ遅れる。

**やっても何も変わらない転送はしない**（`src/sync/idle.ts`）。
段階1 で相手のファイルの印が前に読んだときのままなら、写さない。
段階2 で手元の印が前に上げたときのままなら、上げない。
印は、他の端末が読む表（§3.1）の変化だけを拾う。
`_sync_state` と作り直しの書き込みは、他の端末が読む表を変えないので、上げる理由にならない。
印に表れない変化は2つあり、どちらも上げた覚えを捨てて上げ直させる。
1つは、取り込みが `Max` を変えずに版を格納したときである。手元の行の版より弱い削除の版が、手元の削除の版より強かった場合に起きる。
もう1つは、仕掛けの取り付け直しが `_tombstone` と `_changelog` を作り直したときである。
段階0 の復元の判定も、NAS 上の自分の写しが自分の書いたままなら省く。
起動直後・前回の失敗・版の変化・一定回数ごとには必ず行う。

### 4.2 相手の選び方

- NAS の `client-*.sqlite` のうち自分以外（`listRemoteClients`）。読むのは `openRemoteDbViaLocalCopy` が作るローカルの写し
- 相手の `_sync_meta.schemaVersion` が自分のものと文字列として一致しなければ、その相手を丸ごと見送り、`skippedRemotes` に載せる。**`sns-format` が `rows1` でない相手も同じ**（G）
- 相手の DB が開けない・整合性検査に落ちる場合も見送り、警告する

### 4.3 相手1人ぶんの取り込み（1トランザクション）

範囲 `S` は次のとおり。

| 場合                                                                        | `S`                                                                                                                   |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **その相手を一度も読んでいない。手元の `_sync_state` にその相手の行が無い** | **フルマージ**。範囲は下の「隙間あり」と同じ                                                                          |
| 隙間なし                                                                    | 相手の `_changelog` の `id > lastSeenId` の行から作る `(表, 真の id)` の集合。表名は自分の綴りへ畳み、重複は1つにする |
| 隙間あり（フルマージ）                                                      | 相手の `_sns_rows_<t>` の全 id と、相手の `_tombstone` の全 `(表, id)`                                                |

**初回はフルマージにする。**
`_changelog` は移行で作り直され、掃除でも短くなるので、**相手が持っている `_sns_rows_*` の行に対応する通知が `_changelog` に残っているとは限らない**。
初回に差分だけを読むと、その行は誰にも届かないまま残りうる（【確認】3端末の試験）。
隙間の検出だけでは、相手の `_changelog` が頭から残っている場合に「隙間なし」と判定されるので、初回かどうかを独立した条件として扱う。
初回かどうかは `_sync_state` に行があるかどうかで決める（`src/sync/state.ts` の `getSyncState` は行が無ければ `null` を返し、`src/sync/rows-sync.ts` の `needsFullMerge` はそれを初回とみなす）。
`lastSeenId = 0` を初回の印にはしない。
一度も書いていない相手はフルマージのあとも読み位置が 0 のままなので、0 を印にすると読むたびにフルマージを繰り返す。

**隙間の判定**は `src/changelog.ts` の `hasChangelogGap` が行う。
次のどれかに当たれば隙間ありとする。

1. 相手の `_changelog_prune.prunedThroughId` が `lastSeenId` より大きい。読む前に掃除で消えた通知がある。
2. 相手の `_changelog` が振った最大の id を `sqlite_sequence` から読み（`readChangelogSequence`）、それが `lastSeenId` より大きいのに、`id > lastSeenId` の行の数が `sequence - lastSeenId` より少ない。
   `_changelog` は `AUTOINCREMENT` なので、振った id は 1 から途切れずに並び、行を消しても `sqlite_sequence` は下がらない。
   掃除を通らない消え方、たとえば生の `DELETE FROM _changelog` は `_changelog_prune` に載らないが、この規則で見える。
   頭・途中・末尾・全部のどれが消えても拾う。
3. `lastSeenId` が、振った最大の id と `prunedThroughId` の両方を追い越している。相手のファイルが差し替わったか `_changelog` が作り直されて、id が振り直された形である。
4. `sqlite_sequence` を読めない相手に限り、`_changelog` の `MIN(id)` が `lastSeenId + 1` より大きい。`_changelog` が空なら、`prunedThroughId` が 0 で `lastSeenId` が 0 より大きいときだけ隙間とする。

これらの規則は、0 まで読んだ相手があとで書き、その通知が読まれる前に直に消えた形も拾う。
`_changelog` は空で `prunedThroughId` も 0 なので一度も書いていない相手と同じに見えるが、`sqlite_sequence` が 1 以上なので規則2 に当たる。

フルマージのあとの読み位置は `fullMergeCursor` が決める。
相手の `_changelog` の最大の id、`prunedThroughId`、振った最大の id のうち最も大きいものである。
振った最大の id まで進めないと、末尾が消えていた相手を読むたびに規則2 に当たり、フルマージを繰り返す。
どの規則も、この読み位置に対しては偽になる。

処理は相手ごとに1つの `BEGIN IMMEDIATE` … `COMMIT` で行う。
途中で失敗したら、その相手ぶんだけ巻き戻り、`_sync_state` も進まない。

```
for (t, k) in S:                      -- t が同期する表でなければ飛ばす
  rW = 相手の _sns_rows_<t> の k の行（無ければ無し）
  rD = 相手の _tombstone の (t, KEY_TEXT(k)) の行（無ければ無し）
  lW = 手元の _sns_rows_<t> の k の行、lD = 手元の _tombstone の行
  before = Max(lW, lD)                -- §1.2.5 の順序。JS で決める
  W' = 強い方(lW, rW);  D' = 強い方(lD, rD)
  after = Max(W', D')
  -- 格納（受け取った版は書き換えない）
  D' が lD と違えば _tombstone を D' に置き換える
  W' が D' より強ければ _sns_rows_<t> を W' にする。そうでなければ _sns_rows_<t> の k の行を消す
  -- 時計
  _sns_clock.lamport = MAX(lamport, rW._sns_lamport, rD._sns_lamport)
  -- 通知
  before ≠ after なら:  _changelog に (t, KEY_TEXT(k)) の通知を書き、_sns_dirty に t を載せる
_sns_clock.importTick = importTick + 1
_sync_state を進める（隙間なしなら読んだ最後の通知の id、フルマージなら fullMergeCursor）
```

**受け取った版はそのまま格納する。**
`_sns_ts`・`_sns_lamport`・`_sns_instance` を**書き換えない**。
書き換えると、その版を第三の端末へ中継したときに別の版になり、鍵と中身の対応（不変条件 V）が壊れる。
`lamport` の引き上げは `_sns_clock` に対してだけ行い、格納する値には触らない。

**`Max` が変わったかは、`before` と `after` を取り込みの側（JS）で比べて判定する。**
`ON CONFLICT … DO UPDATE … WHERE` の `changes()` には頼らない。
【確認】退けられた upsert では `changes` が 0 になる場合があり、版によって数え方が変わるものに通知の有無を賭けない。

**SQL の雛形（K）**: `INSERT … SELECT … ON CONFLICT` は `WHERE true` が要る。

```sql
-- 【確認】WHERE true が無いと near "DO": syntax error になる
INSERT INTO "_sns_rows_t" ("id", "name", "updatedAt", "_sns_ts", "_sns_lamport", "_sns_instance")
SELECT ?, ?, ?, ?, ?, ? WHERE true
ON CONFLICT ("id") DO UPDATE SET
  "name" = excluded."name", "updatedAt" = excluded."updatedAt", "_sns_ts" = excluded."_sns_ts",
  "_sns_lamport" = excluded."_sns_lamport", "_sns_instance" = excluded."_sns_instance"
WHERE <STRONGER(excluded, "_sns_rows_t")>;
```

**相手の形が違うとき（G）**:

| 形                                    | 読み方                                                                 |
| ------------------------------------- | ---------------------------------------------------------------------- |
| 相手に `_sns_rows_<t>` が無い         | その表について、その相手は主張していないものとして読む（削除ではない） |
| 相手に無い列がある                    | 自分の表のその列の既定値として読む（`_sns_rows_*` に入れる値は既定値） |
| 相手にしかない列がある                | 無視する                                                               |
| 相手の `sns-format` が `rows1` でない | §4.2 のとおり相手を丸ごと見送る                                        |

取り込みは `_sns_rows_*`・`_tombstone`・`_changelog`・`_sns_dirty`・`_sns_clock`・`_sync_state` にしか書かない。
したがって、アプリの制約（UNIQUE・外部キー・NOT NULL）で失敗することはない。

### 4.4 `SyncResult`

- `inserted` / `updated` / `deleted` は、作り直しでアプリの表に入れた・入れ替えた・消した行数
- `skipped` は、取り込みで手元の版の方が強かったキーの数
- `folds` / `restores` は `_sns_hidden` の差分だけ
- `parentDeleted` / `parentReturned` は `_sns_unplaceable` の原因つきの行の差分だけ。前回は原因が無いか行が無く、今回は原因がある行が `parentDeleted`。前回は原因があり、今回は原因が無いか行が無く、アプリの表に置かれている行が `parentReturned`。どちらも表・主キー・`_sns_rows_<表>` にある中身・原因の親を持つ。前回の状態は前回の作り直しが書いた `_sns_unplaceable` で、同期は作り直しの前にそれを読む。同じ子が他の端末から再び届いても、状態が変わらなければ出ない
- `warnings` に出るのは、`Unplaceable …`（`_sns_unplaceable` の原因の無い行の差分だけ）、`Rebuild deferred …`（見送り）、`Rebuild failed …`（§6.2 の出口で表を作り直しの対象から外したこと）、§3.10 の検出、`setupSync` の前提の確認の警告（§1.8）

## 5. 規則（12場面）

| 場面                                            | 案A の振る舞い                                                                                                                                                                                                                                                                      |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 5-1 基本                                        | `_sns_rows_tags` は `{g1(t1,00:01), g2(t2,00:03)}`。アプリの表は `g1=t1, g2=t2`。同期を挟む位置によらない                                                                                                                                                                           |
| 5-2 3行以上が同じ値でかぶる                     | 版の順序の強い順に置き、置けなかった行は隠れた行。勝者はかぶった置く行のうち最も強いもの。鎖（B→C→A）は作らない                                                                                                                                                                     |
| 5-3 勝者の書き換え / 削除                       | 書き換え: かぶりが解けた行は次の作り直しで置かれる。削除: 隠れていた側の主キーにも削除の版ができるので、隠れていた行は表に戻らない（原則3）。その端末のアプリの表で `ON DELETE CASCADE` により消えた子にも削除の版ができる（R0）                                                    |
| 5-4 隠れた行が他端末で更新される                | 版の順序で強くなれば、その行が置く行になり、いままでの勝者が隠れた行になる。子の表示値も入れ替わる                                                                                                                                                                                  |
| 5-5 隠れた行が利用者に削除される                | 隠れている端末では見えないので消せない。見えている端末で消せばその id の削除の版ができ、他端末でも `Max` が削除になる。勝者を消した場合は 5-3 のとおり隠れた行も消える                                                                                                              |
| 5-6 読み替えた子の編集                          | 外部キー列を書き換えなければ `_sns_rows_*` の真の値のまま。書き換えればその値。表示中の勝者を明示的に書き直す場合は区別できない                                                                                                                                                     |
| 5-7 勝者へ新しい子を足す                        | その子の真の外部キーは勝者の id。あとで勝者が隠れた行になれば、その子は新しい勝者の下に表示される                                                                                                                                                                                   |
| 5-8 子の重複禁止が読み替え先でかぶる            | 子の表も同じ規則で、表示値でかぶりを判定する。読み替えた結果かぶった子は隠れた行になる                                                                                                                                                                                              |
| 5-9 1:1 の子（主キーが親を指す）                | 表示上の主キーでかぶる形として扱う。`ON UPDATE CASCADE` で表示 id が変わる場合は削除の版を作らず、`_sns_shown` を書き換える                                                                                                                                                         |
| 5-10 複数列の重複禁止・部分索引・式索引・生成列 | 一時 DB に同じ索引を作って SQLite に判定させる。照合順序と値の種類もそのまま効く                                                                                                                                                                                                    |
| 5-11 かぶりの連鎖（戻した行が別の行を隠す）     | 貪欲に1回なめるだけ。結果は版の順序から決まる                                                                                                                                                                                                                                       |
| 5-12 時刻を作らない                             | 作り直しも取り込みも時刻を作らない。`_sns_ts` に入るのは、アプリが書いた値、手元の版の値、削除を実行した時刻（時刻列のある表だけ。§2）、移行で写した旧 `deletedAt`（§3.9）のどれか。ほかに現在時刻が入るのは `_tombstone.deletedAt`（順序に使わない）と `_changelog.changedAt` だけ |

ほかに次の場面も決まる。

- 親より先に子が届く: 置かない行。親が届けば次の作り直しで置かれる
- 親の削除とすれ違った子: 親の `Max` が削除の版である間は、時刻によらず `ON DELETE` に従って扱う。版は残り、親が書き直されれば元の形で置かれる（原則4）
- 消してから同じ id で作り直す: 作り直しが勝つ
- 時刻列を変えない書き込み: 後の書き込みが勝つ
- NOT NULL・CHECK に当たる行: 置かない行
- 値の入れ替え: 表全体の入れ替えなので通る
- `ON UPDATE` の動作: R0

## 6. 論証

### 6.1 目標 (a)

不変条件 V（同じ鍵の版は中身も格納クラスも同じ）、補題1（`Max_F` は集合だけで決まる）、補題2（`Φ` は `Max_F` とスキーマの関数。P8 が要る）、補題3（置く行は一時 DB に実際に入った行）、定理1。

**不変条件 V と、列の増減（E）。**
列が増えた／減った表は、その端末が**新しい版の鍵で全行を書き直す**ので、同じ鍵なのに中身が違う版は生まれない。
既定値を1回評価して埋める方式は、評価のたびに変わる既定値で V を壊すので採らない。
取り込みが受け取った版を書き換えないこと（§4.3）も、V を守るために要る。

原則4 で親が削除されているので置かない子も、`Max_F` とスキーマだけで決まる。
親の `Max` が削除の版かは `Max_F` で決まり、`ON DELETE` はスキーマで決まるからである。
作り直しは版を捨てないので、各端末の版の集合は併合でしか変わらない。
2周で一致することは、この性質と「アプリの表は版の集合だけの関数」に支えられている。

### 6.2 目標 (b)

- 取り込みはアプリの制約が無い表に書くだけ
- 作り直しは、白紙のリストのエラーだけを「置かない行」にし、それ以外は中止して知らせる
- 見送り（`SQLITE_BUSY` と token の不一致。J）は k 回までで、k 回目は計算と適用を1つのトランザクションで行う
- **中止が有限回で終わること（B の出口）**: 外部キーの検査の違反で中止した場合、同じ事実・同じスキーマでは同じ計画が出る。そのままでは同じ例外を繰り返し、その表は二度と作り直せない。そこで **2回続けて同じ表で違反が出たら、その表を作り直しの対象から外し、`warnings` に名指しで出す**。外したことは `SyncInstance` の記憶に持ち、**その表の `_sns_tick` が動いた（新しい事実が来た）ときに解く**。対象の表の数は有限で、外した表は事実が変わるまで再挑戦しないので、作り直しは有限回で必ず止まる

### 6.3 目標 (c)

取り込みも作り直しも版を作らない。
要は旗の番人である。
`_sns_rows_*` から行が消えるのは、§1.1 のとおりアプリの書き込みが作った削除の版に負けたときだけである。

**DDL によるアプリの書き込みを記録する場合（E）。**
列の増減のときに全行を新しい版として書き直すのは、(c) の例外ではない。
`ALTER TABLE` とそれに伴う値の設定は**アプリが行った書き込み**で、トリガーを通らなかっただけである。
ライブラリは、アプリが既に行った変更を事実として記録しているにすぎない。

### 6.4 参考: （強）が成り立つ条件

- C1: 1:1 の表への書き込みが無い
- C2: UPDATE は全列を書く
- C3: 表示中の勝者の id を外部キーへ書かない
- C4': `ON DELETE` / `ON UPDATE` が子に及ぶ行を消す・主キーを変える文が無い
- C5: 行を真の id でだけ特定し、書く値がアプリの表を読んだ結果に依存しない

### 6.5 論証できていない点

1. （強）は目標から外した
2. SQLite の版の違いで、CHECK・式索引・生成列・照合順序・`julianday` の受け入れ方が変わりうる
3. 索引の字句解析が正しいのは、解析できた形についてだけ
4. P8 の検査は字句解析なので、別名の関数・将来の非決定的な関数・接続ごとの登録は見落としうる
5. 引き上げの恒久性
6. ISO の字形の判定の限界
7. アプリのトリガーが保証している不変条件は、作り直しの適用では保たれない
8. 自己参照する表で輪になったデータは置かれない
9. 1:1 の表で「親の主キーが変わった」のか「アプリが別の親へ付け替えた」のかを区別できない
10. 他の接続が書き込みを続けていると、k 回目でもロックが取れない
11. 外部での書き換えで消された行は反映されない
12. ワーカーが Electron の主プロセスで動くことは未確認
13. 同着は書き込み量の多い端末が勝ちやすい
14. 作り直しの間はアプリの表が `Φ(F)` と違う
15. **§6.2 の出口で対象から外した表は、その表の事実が変わるまで表示が更新されない**。同期は続く
16. **取り込みの窓でアプリが一部の列を編集すると、`OLD` に落ちた列の値で行が復活しうる**（§9.23）。他端末が見たことのない内容が、その端末の版として全端末へ渡る
17. **（強）は、`_sns_ts` の引き上げがある以上、案A では成り立たない**（§9.25 の例）。挟み方の検査は違反ではなく件数の記録として扱う（§8.1）
18. **親が削除されているので置かない子の版は、親が書き直されない限り `_sns_rows_<表>` に残り続ける**。容量の上限は論じていない。子そのものを消すには、親を書き直して子を置いてからアプリが消すしかない
19. **同期しない表の子は、統合された親の勝者へ付け替えない**（§3.7.5）。原則4 の前半が効くのは同期する表の子だけである

**挟み方の検査（（強）の検査）は、違反ではなく件数の記録として扱う。**
案A では「同じ操作の集まりなら同じ見え方」は**成り立たない**。
`_sns_ts` の引き上げ（§1.2.1）があるので、**他端末の版を取り込んだあとに、より古い時刻でその行を書くと、引き上げのぶんだけ強い版になる**。
取り込んでいなければ弱い版のままである。
反例の一覧は「（強）が破れた形の観察」として出す（§6.5-17、§9.25）。

### 8.2 検査器の作り

主スレッドで計算する経路、計算中の差し込み口、`BEGIN IMMEDIATE` を失敗させる口、`generation`・lamport・`instanceId` の正規化を持つ。
操作には、未来の時刻、時刻列を変えない UPDATE、消してすぐ作り直す、`ON DELETE SET NULL` の子を持つ親を消す、1:1 の親の主キーを変える、を含む。

**端末の入れ替えによる対称性の畳み込みは、案A では使えない（健全でない）。**
同着の最後の鍵が `instanceId` のバイト列（§1.2.5）なので、「`iid` の小さい端末が書いた状態」と「大きい端末が書いた状態」は鏡写しにならない。
同じ操作を端末を入れ替えて当てても、勝つ版が入れ替わるとは限らないためである。
【確認】検査器の自己検査が、素の実装でこれを検出した。
したがって検査器は**端末の入れ替えを畳まない**。
畳み込みの仕組みそのものを検査器から削除したので、それを切る選択肢も無い。
状態数はそのぶん増える。

## 9. 既知の制限と README に書く注意点

項目の番号はソースのコメントが参照しているので変えない。
1〜22 は欠番である。

23. **取り込みの窓でアプリが一部の列だけを編集すると、その端末でしか見たことのない内容の行が全端末へ渡る。**
    取り込みが `_sns_rows_*` の行を消した直後、つまり `Max` が削除になった直後に、アプリがその行の一部の列を UPDATE すると、書かなかった列は `OLD` に落ちる（§3.4 の3分岐）。
    `OLD` はアプリの表に残っていた古い値である。
    その版は取り込んだ削除より強くなりうるので、**行が復活し、他端末が一度も見ていない中身が広まる**。
24. **NAS への写しは `backup()` で作り、他の端末が読む表だけを載せる**（§4.1）。
    WAL の DB を `copyFile` で写すと `-wal` が付いてこないので、写しから最近の書き込み（`_sns_rows_*` を含む）が見えない。
    写しにはアプリの表が無いので、NAS の写しはアプリの DB のバックアップにならない。
25. **（強）は成り立たない。**
    「同じ操作の集まりなら、同期をいつ挟んでも同じ見え方」は案A では保証しない。
    `_sns_ts` の引き上げがあるので、**他端末の版を取り込んだあとに、より古い時刻でその行を書くと、取り込んでいなかった場合より強い版になる**。
    例: a が `X` を 10:00 で書き、b がそれを取り込んでから `X` を 09:00 で書くと、b の版は `_sns_ts = 10:00`（引き上げ）＋ b の `lamport` で a に勝つ。
    b が取り込む前に 09:00 で書いていれば、`_sns_ts = 09:00` で a に負ける。
26. **1回の書き込みが、動いている全端末に写しの上げ直しと読み直しを起こす。**
    量は §7 の「同期1回の転送量」にある。
    次の2つが重なって起きる。
    1. 取り込みで手元の `Max` が変わると、自分の `_changelog` に中継の通知を書き、その回のうちに写しを上げ直す（§4.1・§4.3）。
    2. 上げ直した写しはファイルの印が変わるので、他の端末はそれを読む。読んで何も変わらなければ、読んだ側は上げ直さない。

    写しはファイル単位でしか転送できないので、上げ直しと読み直しのたびに DB 全体が行き来する。
    1台が書き続ける間は、動いている端末がそれぞれ毎回、自分の写しを1回上げ、相手の写しを全部読む。

27. **同期の間、呼び出したスレッドが止まる。**
    相手の写しの複製は `fs.copyFileSync`、その検査は `PRAGMA integrity_check`、取り込みは better-sqlite3 の同期 API で行い、どれも呼び出したスレッドで動く。
    自分の写しに載せる表を選んで写す処理（§4.1）と、それを NAS へ置く `fs.copyFileSync` も同じである。
