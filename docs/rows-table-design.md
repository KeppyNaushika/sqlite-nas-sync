## 0. 要約

- **目標（弱）**: (a) 同じ事実を受け取った端末は同じ表示になる。(b) 同期が永久に止まらない。
  (c) 同期の処理そのものは事実を作らない。データを消すのはアプリの書き込みだけ
- 同期する表 `t` ごとに `_sns_rows_<t>` を置く（UNIQUE も外部キーも付けない）
- 版の鍵は (順序用の時刻 `_sns_ts`, 書き込み順 `_sns_lamport`, 端末の `_sns_instance`)
- アプリの接続でアプリの表に起きた変化は、原因によらずすべて事実になる（R0）
- かぶりと行に閉じた制約の判定は、一時の `:memory:` DB へ強い順に INSERT して SQLite 自身に決めさせる
- 取り込みは相手の版を**書き換えずにそのまま**格納する（中継に必須。§4）
- 計算は `worker_threads`、適用は主スレッド。見送りが3回続いたら計算と適用を1つのトランザクションで行う

## 1. 目標と意味の定義

### 1.1 目標

| 記号 | 目標 |
| --- | --- |
| (a) | 受け取った事実の集合（の各キーの最強の版）が同じ端末は、作り直しが成功した時点で、アプリの表の中身が同じ |
| (b) | 同期が永久に止まらない |
| (c) | 同期の処理は事実を作らない。データを消すのはアプリの書き込みだけ |

(c) から導かれる性質: `_sns_rows_*` から行が消えるのは、アプリの書き込みが作った削除の版に負けたときだけ。
ただし、アプリが消した行に宣言された `ON DELETE CASCADE` でつながる行は消える。

### 1.2 事実と版の順序

行の版 `W(t, k, ts, L, iid, c)` と削除の版 `D(t, k, ts, L, iid)`。`k` は真の id。

#### 1.2.1 順序用の時刻 `_sns_ts`（引き上げ）

```
_sns_ts := 次の3つのうち最も強いもの（§1.2.3 の順序）
   (1) アプリの表の時刻列の新しい値（削除の版には無い）
   (2) 手元の _sns_rows_<t> の同じ真の id の _sns_ts
   (3) 手元の _tombstone の同じ真の id の _sns_ts
どれも無ければ OLD の時刻列の値
```

(3) を入れないと、取り込んだ強い削除を、そのあとのアプリの削除が弱い版で上書きし、`Max` が後退する。
**対価**: 一度でも異常に大きい時刻が入ると、その行の `_sns_ts` は以後その高さに固定される。

#### 1.2.2 「2段階の規則」を採らない理由

キーごとに最強の版だけを保存する実装と両立しないため（付録 A.10 の反例）。

#### 1.2.3 時刻の比較（値の種類）

| 群 | 条件 | 群の中の比べ方 |
| --- | --- | --- |
| 0 | `typeof(x) = 'null'` | 同着 |
| 1 | `integer` / `real` | 数値のまま |
| 2 | `text` で ISO 8601 の字形でない | `COLLATE BINARY` |
| 3 | `text` で ISO 8601 の字形 | `julianday(x)` |
| 4 | `blob` | `COLLATE BINARY` |

群は 0 ＜ 1 ＜ 2 ＜ 3 ＜ 4。判定に使う `GLOB` は**全端末で同じ文字列**でなければならない。

```sql
-- ISO(x)
(typeof(x) = 'text' AND julianday(x) IS NOT NULL AND (
     x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]:[0-9][0-9]'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9]*'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]*Z'
  OR x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][T ][0-9][0-9]:[0-9][0-9]*[+-][0-9][0-9]:[0-9][0-9]'))
```

**4つめの `GLOB` は `….[0-9]*`（この文書の形）で統一する。** 実装（`src/rows/versions.ts`）の `….*` との違いは
「小数点のあとに数字が無い形」だけで、【確認】`'2026-01-01T00:00:00.'` と `'2026-01-01T00:00:00.Z'` は
`julianday` が NULL を返すため、どちらの `GLOB` でも群3 にはならない（付録 A.17）。結果は同じだが、
**字形の判定は全端末で同一でなければならないので、文書と実装のどちらかに揃える**。意図（小数の桁があること）が
はっきりしている `….[0-9]*` を正とする。

**限界**: 存在しない日付（`'2026-02-30'`）を通す、末尾の空白があると群2 に落ちる、ミリ秒より細かい差は丸められる。

#### 1.2.4〜1.2.5

時刻の列を進めない書き込みは許容する。順序 `≺` は `( _sns_ts, L, iid )` の辞書順。すべて等しければ 種類
（行の版 ＜ 削除の版）。不変条件 U（`(t, k, iid, L, 種類)` が版を一意に定める）、不変条件 C（clock ≥ 手元の
全ての `L`）、補題A（同じ端末の後の書き込みが強い）、補題B（削除は手元の Max より強い）、補題C（全前順序。
キーごとに最強の版だけを保存してよい）。

### 1.3〜1.7 候補・表示値・かぶり・勝者・見え方

- 表示値は親の `Res_p` と `ON DELETE` の宣言で決まる。1:1 の表では `disp(pk) = Res_p(真の pk)`
- 置かない行: 主キーが NULL、または一時 DB への INSERT が白紙のリストのエラー
  （`NOTNULL` / `CHECK` / `DATATYPE` / `MISMATCH` / `TOOBIG`）で失敗したもの。それ以外のエラーは中止して例外
- かぶり: 一時 DB への INSERT が `UNIQUE` / `PRIMARYKEY` / `ROWID` になること。勝者は全ての索引と主キーで
  引き直して最も強い置く行にする。索引の情報は `PRAGMA index_list` / `index_xinfo` から取り、字句解析は
  部分索引の `WHERE` と式索引の式だけ
- 見え方 `Φ(F)` は各表の「置く行の表示値」。作り直しが成功した時点で、アプリの表の中身は `Φ(F)`

#### 1.3.1 `deleteProtected` の表（`TableConfig.deleteProtected`）

【決定】**`deleteProtected` の表では、削除の版は表示の計算で勝たない。行の版がある限り、その行は置かれる。**

| 場所 | 振る舞い |
| --- | --- |
| 候補（§1.3） | その表の候補は「`_sns_rows_<t>` にある行の版」である。削除の版は見ない |
| 取り込み（§4.3） | 削除の版が強くても、**`_sns_rows_<t>` の行を消さない**（消すと戻せない）。`_tombstone` には今までどおり削除の版を格納する（事実は捨てない） |
| 削除トリガー（§3.4） | 削除の版は作る（R0）。ただし**`_sns_rows_<t>` の行を消す文は生成しない** |
| 作り直し | その表の削除の版を無視して `Φ` を計算する。したがって、アプリがその表の行を消しても、**次の作り直しでその行が置き直される** |

事実（削除の版）は捨てないので、`deleteProtected` を後から外せば、そのとき初めて削除が効く。

**設定は全端末で同じであること（P14）**: 端末ごとに設定が違うと、同じ事実から違う表示が出る（目標 (a) の破れ）。
`_sync_meta` に `sns.deleteProtected`（表名を正規形で並べ、`,` でつないだ文字列）を書き、**取り込みの前に
相手の値と比べて、違えば `warnings` に名指しで出す**（読み飛ばしはしない。設定の食い違いは利用者が直すもの）。
`setupSync` は、自分の設定を同じ形で書き直す。

### 1.8 前提

P1（主キーが `TEXT` で宣言され、NULL を取らない。値は端末をまたいで一意な id ——
UUID / cuid —— であることを前提にする。`INTEGER PRIMARY KEY` の自動採番は、別々の端末が
同じ値を別の行に割り当てるので断る）、P2（表の依存が循環しない。自己参照は許す）、P4（全端末で同じスキーマ・
同じ SQLite の版）、P5（アプリの接続で外部キーが有効）、P6（アプリのトリガーは適用の間は発火しない）、
P8（部分索引の述語と式索引の式が字句解析でき、決定的でない関数が無い）、P9（`instanceId` が重ならない）、
P10（WAL）、P11（主キーが1列）、P12（アプリの表を書くすべての接続で `PRAGMA recursive_triggers = ON`）、
P13（アプリの列名が `_sns_` で始まらない）、**P14（`deleteProtected` の設定が全端末で同じ。違えば同じ事実から
違う表示になる。§1.3.1 のとおり `_sync_meta.sns.deleteProtected` を突き合わせて警告する）**。

## 3. データの持ち方

### 3.1 表の一覧

| 表 | 他端末が読むか | 中身 |
| --- | --- | --- |
| `_sns_rows_<表>` | 読む | 生きている id の最強の行の版。アプリの列（生成列を除く）＋ `_sns_ts`（型名なし）・`_sns_lamport`・`_sns_instance` |
| `_tombstone` | 読む | 削除の版。`tableName`・`recordId`・`deletedAt` ＋ `_sns_ts`（型名なし）・`_sns_lamport`・`_sns_instance` |
| `_changelog` | 読む | 読み直すキーの通知 |
| `_changelog_prune` / `_heartbeat` | 読む | 掃除の位置・生存 |
| `_sync_meta` | 読む | `schemaVersion`（`<アプリの版>;sns-format=rows1`）、`sns.instanceId`、**`sns.generation`**、**`sns.lastInstance`**、**`sns.lastLamport`** |
| `_sns_clock` / `_sns_tick` / `_sns_shown` / `_sns_hidden` / `_sns_unplaceable` / `_sns_dirty` / `_sns_rebuilding` | 読まない | 時計・表ごとの tick・作り直しの出力・警告の重複回避・対象・旗 |

`_sync_meta` の鍵の名前は上のとおりに固定する（H）。`sns.generation` は `copyToNas` の前に +1 する値、
`sns.lastInstance` / `sns.lastLamport` は「自分が最後に NAS の写しへ書いたときの `instanceId` と `lamport`」である。

### 3.2 `_sns_rows_<表>`・`_sns_clock`・`instanceId`

`_sns_clock(onlyRow, lamport, importTick, instanceId)`、`_sns_tick(tableName, tick)`。
`instanceId` は `setupSync` のたびに `crypto.randomBytes(16)`。

**`_sns_clock` の行はトリガーでは作らない**（行が失われたら `lamport` が 0 から数え直され、不変条件 C が破れる）。
行が無ければアプリの書き込みが `NOT NULL` で失敗する（気づける）形が正しい。行を作るのは表の作成と
`setupSync` / `performSync` だけ。`_sns_tick` はトリガーの `ON CONFLICT DO UPDATE` で作ってよい。

### 3.3 生成に使う式

`GUARD`（`NOT EXISTS (SELECT 1 FROM _sns_rebuilding)`）、`ISO(x)` / `GRP(x)`、`TSGT(a,b)`、
`NEWTS`（3項の最大。`UNION ALL` + `ORDER BY` の形）、`STRONGER(a,b)`、`TICK(t)`、`TRUE_ID(v)`、`KEY_TEXT(v)`。
定義は第9版と同じ。

### 3.4 トリガー

4本（INSERT / UPDATE×2（主キーが変わる・変わらない）/ BEFORE DELETE）。すべての `WHEN` に `GUARD` を入れ、
本体の書き込みは `ON CONFLICT` の形（`_changelog` は対象なしの `ON CONFLICT DO NOTHING`）で書く。
`TICK(t)` は本体の先頭。UPDATE の「書かれなかった列」は3分岐（`NEW."c" IS NOT OLD."c" COLLATE BINARY` →
`NEW."c"` / `_sns_rows_*` に行があればその値 / 無ければ `OLD."c"`）。DELETE の `_sns_ts` は
「`_sns_rows_*` にも `_tombstone` にも行が無いときだけ `OLD` の時刻列」。1:1 の表で表示 id だけが変わる場合は
削除の版を作らず、`_sns_shown` の書き換えは**本体の最後**に置く。`PRAGMA recursive_triggers = ON` が要る（P12）。

### 3.5 補助の表

`_sns_shown(tableName, trueId, shownId)`（主キー `(tableName, trueId)`、`(tableName, shownId)` に UNIQUE 索引）、
`_sns_hidden`、`_sns_unplaceable`、`_sns_dirty`。`_sns_shown`・`_sns_hidden` は作り直しの**出力**。

### 3.6 他端末が読む範囲

相手の `_sns_rows_<t>` と `_tombstone` の強い方が `Max`。`_changelog` は通知だけ。

### 3.7 作り直し

範囲は `_sns_dirty` の表とその子孫の表。表示値のために祖先も**計算する**が、**適用はしない**
（`_sns_shown`・`_sns_hidden`・`_sns_unplaceable` も、適用した表の分だけ書き直す。祖先について計算した分は書かない）。

#### 3.7.1 計算（worker_threads）

```
ワーカー: 読み取り専用で開き、defaultSafeIntegers(true)（一時 DB の接続にも）
BEGIN                                   -- (A-2) 計算全体を読みのトランザクションで囲む
  token = { 計算に使う表ごとの _sns_tick.tick, _sns_clock.importTick }   -- (A-1) どのデータより先に読む
  一時 DB（:memory:）を用意する（同期する表の CREATE TABLE と索引だけ。アプリのトリガーは写さない）
  _sns_rows_*、_tombstone、_sns_shown、_sns_hidden を読む
  表は依存の順に: 表示値 → 強い順に一時 DB へ INSERT（置く行／隠れた行／置かない行／中止）
  アプリの表を読み、差（消す行・入れる行）を作る
COMMIT
```

**(A-1) token を最初に読む**: 一時 DB の用意より後に読むと、その間の書き込みを見落とす。

**(A-2) 読みのトランザクションで囲む（必須）**: 読み取り専用の接続でも、**トランザクションで囲まないと文ごとに
別の快照を見る**。【確認】親の表を読んだあとに主スレッドが親を消すと、子だけが新しい姿で読まれ、
「計画が裂けたまま token が一致して適用される」ことが起きる（アプリが消した行が表に戻る）。
`BEGIN`（読みの `DEFERRED`）で囲めば、最初の読みで快照が固まる。

**token の役割と守りの分担**: token が捕まえるのは「計算を始めたあと、適用の `BEGIN IMMEDIATE` を取るまで」の
書き込みだけである。適用の最中は旗が立っていて `_sns_tick` も進まないので token では捕まえられず、
**`BEGIN IMMEDIATE` が握る書き込みのロック**が守る。

自己参照する表は、根から始めて「真の親がすでに置かれた候補」を繰り返し置き、1回も置けなくなったら止める。

**値の受け渡し**: ワーカーは `defaultSafeIntegers(true)` なので、大きい整数は `BigInt` で返る。
`BigInt` は `postMessage` の構造化複製でそのまま渡せるので、**主スレッドへ `BigInt` のまま渡し、適用の接続でも
`defaultSafeIntegers(true)` にして `BigInt` のまま束縛する**（`Number` へ戻すと 2^53 を超える値が壊れる）。

#### 3.7.2 適用（主スレッド）

入口は「通常」と「k 回目の合流（計算も同じトランザクションの中で行う）」の2つ。
**適用は、その表の「消す行」と「入れる行」をまとめて当てる（実質は表全体の入れ替え）。**
UNIQUE の値の入れ替え（`A=t1,B=t2 → A=t2,B=t1`）が通るのはこのためである。

```
db.inTransaction なら何もしない
prevFK = PRAGMA foreign_keys; prevBusy = PRAGMA busy_timeout      -- トランザクションの外で読む
PRAGMA busy_timeout = 0（通常）/ 数十 ms（k 回目）; PRAGMA foreign_keys = OFF   -- 外で設定する
try:
  BEGIN IMMEDIATE
  通常の入口では token を確かめ、違えば ROLLBACK して「見送り」として抜ける（見送り回数 +1）
  旗を立てる（_sns_rebuilding）
  アプリのトリガーを外す（"main"."…" / "temp"."…" と修飾。temp の sql には TEMP を挿し直す）
  消す行 → §3.7.5 の後始末 → 入れる行（生成列は書かない）
  _sns_shown・_sns_hidden・_sns_unplaceable を、適用した表の分だけ書き直す
  アプリのトリガーを戻す
  外部キーの検査: 対象 = 適用した表 ∪ 後始末で触った表 ∪ それらを親として参照している表。
     表ごとに `PRAGMA foreign_key_check(<表>)` を1つずつ。違反があれば ROLLBACK して §6.2 の出口へ
  DELETE FROM _sns_dirty WHERE tableName IN (<適用した表>)   -- 旗が立っている間に消す
  旗を下ろす
  COMMIT（見送り回数を 0 に戻す）
catch (e):
  db.inTransaction なら ROLLBACK
  **(J) e.code === 'SQLITE_BUSY' なら「見送り」として抜け、見送り回数 +1。それ以外は投げ直す**
finally:
  db.inTransaction が真なら例外（PRAGMA を戻せないまま進ませない）
  そうでなければ PRAGMA foreign_keys = prevFK; PRAGMA busy_timeout = prevBusy
COMMIT のあと: config.onAfterRebuild?.(db, 変わった表と id)
```

**(J)**: `busy_timeout = 0` の `BEGIN IMMEDIATE` は**例外を投げる**（`SQLITE_BUSY`）。これを投げ直すと
見送りに数えられず、k 回目の合流経路に永久に入らない。`SQLITE_BUSY` と token の不一致の**両方**を見送りに数える。

#### 3.7.3 アプリのトリガーの外し戻し

`DROP TRIGGER "main"."<名前>"` / `"temp"."<名前>"` と schema を修飾する。`sqlite_temp_master` の `sql` には
`TEMP` の語が入らないので、`CREATE` の直後に `TEMP` を挿入してから実行する。

#### 3.7.4 見送りが続いたときの経路

見送り回数は `SyncInstance` の記憶に全体で1つ持つ。**`SQLITE_BUSY` と token の不一致の両方を数える**（J）。
確定したとき、または `_sns_dirty` が空のときに 0 に戻す。k（既定 3）回目は、`busy_timeout` を数十 ms にして
`BEGIN IMMEDIATE` し、その中で計算と適用を続けて行う。

#### 3.7.5 同期しない表からの外部キーの後始末（B）

`foreign_keys = OFF` の下では `ON DELETE` は自動では起きないので、**ライブラリが手で当てる**。
適用のトランザクションの中で、消える親（アプリの表から消え、入れ直されない主キー）ごとに、
その親を指す**同期しない表**の子を、宣言どおりに始末する。

| その外部キーの `ON DELETE` | 子への当て方 |
| --- | --- |
| `CASCADE` | 子を消す |
| `SET NULL` | その外部キーの全列を NULL にする。**NOT NULL の列を含むなら子を消す** |
| `SET DEFAULT` | その外部キーの全列を既定値にする（既定値の親が居なければ子を消す） |
| `RESTRICT` / `NO ACTION` | 子を消す（残すと外部キーの検査に引っかかり、その表が永久に作り直せなくなる） |

親が隠れた行になって勝者が置かれている場合は、消す代わりに外部キーを勝者へ書き換える
（書き換えでその表の UNIQUE に当たる子は消し、`RecordFold.lostChildren` に数える）。
触った表は外部キーの検査の対象に含める。

### 3.8 版の確認

`_sync_meta.schemaVersion = <アプリの版>;sns-format=rows1`。新版と旧版の端末は互いに読み飛ばす。

### 3.9 移行・列の増減（C・D・E・F・G）

移行は1つのトランザクションで行う。

1. `_sns_clock`（行を作る）、`_sns_tick`（表ごとの行）、`_sns_shown` などの補助の表を作る
2. **`_tombstone` と `_changelog` は作り直す**（F）。理由:
   - 【確認】行のある `_tombstone` に `ADD COLUMN "_sns_lamport" INTEGER NOT NULL` は既定値なしでは断られる
     （空の表では通る。行の有無で変わるので、`DEFAULT 0` を必ず書くか作り直す）
   - 【確認】旧 `_tombstone.deletedAt` に既定値が無い DB では、新しいトリガーの INSERT が
     `NOT NULL constraint failed: _tombstone.deletedAt` で落ちる（付録 A.17）
   - 旧 `_changelog` は列が違うので `CREATE TABLE IF NOT EXISTS` では追いつかず、最初の書き込みが落ちる
   - 作り直しでは必要な列だけを写す。**旧「畳み」の事実（`_id_merge`・`mergedInto`・`revokedAt`）は捨てる**。
     捨てた結果、畳まれていた敗者 id の行が他端末から届けば重複として現れるが、**案A では重複はそのまま両方
     残る**（勝者を選んで片方を隠すだけで、消しはしない）ので問題にならない
3. アプリの表に同じ id がある `_tombstone` の行は写さない（比較は `recordId = CAST(<主キー> AS TEXT)`）。
   写す行は `_sns_lamport = 0`、`_sns_instance` ＝ 自分、**`_sns_ts` は NULL**（群0＝最小）
4. **`_sns_rows_<t>` へ写す行の版（C）**: `_sns_ts` ＝ **アプリの表の時刻列の値**（§1.2.1 の (1) と同じ）、
   `_sns_lamport = 0`、`_sns_instance` ＝ 自分。
   `_tombstone` を NULL にするのは「移行時の削除に大きな時刻を与えない」ためで、**`_sns_rows_*` には当てはまらない**
   （時刻列の値は全端末で同じ文字列なので、`_sns_ts` に入れても端末差にならない）。
   【確認】`_sns_rows_*` の `_sns_ts` を NULL にすると、移行した2端末の同じ行の勝敗が
   `(群0, 0, instanceId)` の比較になり、**起動ごとに変わる乱数（`instanceId`）で決まる**
5. トリガーを作る（4本）。**`_sns_rebuilding` に残った行があれば、トリガーを作る前に消す**（I）
6. **`_changelog` は刈らない**（G）。旧版の端末が残っている間に刈ると、その端末へ渡すべき事実が消える。
   隙間の検出は既存の仕組みに任せる
7. `_sync_state` を空にし、`sns.instanceId` / `sns.generation` / `sns.lastInstance` / `sns.lastLamport` を書き、
   全表を `_sns_dirty` に入れる

**列が増えた／減ったとき（D・E）**

- **その表のトリガー4本を落として作り直す**（D）。【確認】作り直さないと、列を落とした場合はアプリの INSERT が
  `has no column named …` で落ち、増えた場合は新しい列が事実にならず、作り直しのたびにアプリが書いた値が
  既定値へ戻る
- **列の増減があった表は、その端末が移行の中で全行を新しい版として書き直す**（E）。アプリの表の現在の内容を使い、
  `_sns_ts` は §1.2.1 の3項の最大、`_sns_lamport` は進めた値（表ごとに1つでよい。鍵は `(t, k, iid, L, 種類)` なので
  行が違えば重ならない）、`_sns_instance` は自分。
  **「既定値を1回評価して埋める」は採らない**。【確認】評価のたびに変わる既定値では、端末ごとに違う値が
  同じ版の鍵で入り、永久に食い違う
- 既定値が評価できず、その列が NOT NULL の場合は `setupSync` で例外にする（従来どおり）
- `_sns_rows_*` から列を落とす場合、【確認】**主キーの列は `DROP COLUMN` できない**
  （`cannot drop PRIMARY KEY column`）。索引の張られた列も落とせない。`_sns_rows_*` は主キーにしか索引を
  張らないので、主キー以外は落とせる。**アプリの表の主キーの列名が変わった・消えた場合は `setupSync` で例外**
  （行の同定ができなくなるため）
- 列の増減があった表は `_sns_dirty` に入れる

### 3.10 外部での複製・復元・書き換えの検出

| 検出 | 条件・手当て |
| --- | --- |
| 復元・巻き戻り | NAS 上の自分の写しの `sns.lastLamport` より手元の `lamport` が小さい、または `sns.generation` が写しより小さい。**判定は、その同期回の取り込みより前に行う**（H。取り込みが `lamport` を引き上げると証拠が消える）。知らせたうえで、必要なら §3.9 のやり直し |
| 仕掛けの欠け | トリガーが無い、`_sns_clock` の行が無い、`_sns_tick` の行が足りない → 作り直す。**`_sns_rebuilding` に行が残っていれば、知らせたうえで `setupSync` の中で（トリガーを作る前に）消す**（I。残っているとアプリの書き込みが1つも事実にならず、警告も出ない） |
| **`_tombstone` の版の列が欠けている** | **`_sns_ts` / `_sns_lamport` / `_sns_instance` のどれかが無ければ、§3.9 の移行のやり直し（`_tombstone` の作り直し）を呼ぶ**。【確認: 段階5 の実装】欠けたままだと、アプリの DELETE がトリガーごと `table _tombstone has no column named _sns_ts` で落ちる（アプリの文が失敗する） |
| 写しの取り合い | 自分が写しを書いたあとにだけ判定する。NAS 上の自分の写しの `instanceId` が自分のものでなければ、同期を止めて知らせる |

## 4. 同期の流れと取り込み

### 4.1 `performSync` の段階

| 段階 | 内容 |
| --- | --- |
| 0 | `writeSchemaVersion`。**§3.10 の復元・巻き戻りの判定（取り込みより前）**。トリガー・`_sns_clock` の行・`_sns_tick` の行・`_sns_rebuilding` の残りの確認 |
| 1 | 相手の列挙と、隙間の事前確認 |
| 2 | 隙間なし: `sns.generation` +1 → `copyToNas` → 相手ごとに取り込み → 作り直し。隙間あり: 相手ごとに全キーの取り込み → 作り直し → heartbeat → `sns.generation` +1 → `copyToNas` |
| 3〜5 | heartbeat、`cleanupChangelog`、`onAfterRebuild`、`onAfterSync` |

**NAS への写しは `backup()` で作る**（`copyFile` では WAL の `-wal` が付いてこないので、写しから
`_sns_rows_*` の最近の書き込みが見えない）。

### 4.2 相手の選び方

- NAS の `client-*.sqlite` のうち自分以外（`listRemoteClients`）。読むのは `openRemoteDbViaLocalCopy` が作る
  ローカルの写し
- 相手の `_sync_meta.schemaVersion` が自分のものと文字列として一致しなければ、その相手を丸ごと見送り
  （`skippedRemotes` に載せる）。**`sns-format` が `rows1` でない相手も同じ**（G）
- 相手の DB が開けない・整合性検査に落ちる場合も見送る（警告）

### 4.3 相手1人ぶんの取り込み（1トランザクション）

範囲 `S` は次のとおり。

| 場合 | `S` |
| --- | --- |
| **その相手を一度も読んでいない（`lastSeenId = 0`）** | **フルマージ**（下と同じ範囲） |
| 隙間なし | 相手の `_changelog` の `id > lastSeenId` の行から作る `(表, 真の id)` の集合（表名は自分の綴りへ畳む。重複は1つに） |
| 隙間あり（フルマージ） | 相手の `_sns_rows_<t>` の全 id と、相手の `_tombstone` の全 `(表, id)` |

**初回はフルマージにする理由**: `_changelog` は移行で作り直され、掃除でも短くなるので、**相手が持っている
`_sns_rows_*` の行に対応する通知が `_changelog` に残っているとは限らない**。初回に差分だけを読むと、その行は
誰にも届かないまま残りうる（【確認: 段階5 の3端末の試験】）。既存の隙間の検出だけでは、相手の `_changelog` が
頭から残っている場合に「隙間なし」と判定されるので、`lastSeenId = 0` を独立した条件として扱う。

処理は相手ごとに1つの `BEGIN IMMEDIATE` … `COMMIT` で行う（途中で失敗したら、その相手ぶんだけ巻き戻り、
`_sync_state` も進まない）。

```
for (t, k) in S:                      -- t が同期する表でなければ飛ばす
  rW = 相手の _sns_rows_<t> の k の行（無ければ無し）
  rD = 相手の _tombstone の (t, KEY_TEXT(k)) の行（無ければ無し）
  lW = 手元の _sns_rows_<t> の k の行、lD = 手元の _tombstone の行
  before = Max(lW, lD)                -- §1.2.5 の順序。JS で決める
  W' = 強い方(lW, rW);  D' = 強い方(lD, rD)
  after = Max(W', D')
  -- 格納（受け取った版は書き換えない）
  D' が lD と違えば _tombstone を D' に置き換える
  W' が D' より強ければ _sns_rows_<t> を W' にする。そうでなければ _sns_rows_<t> の k の行を消す
  -- 時計
  _sns_clock.lamport = MAX(lamport, rW._sns_lamport, rD._sns_lamport)
  -- 通知
  before ≠ after なら:  _changelog に (t, KEY_TEXT(k)) の通知を書き、_sns_dirty に t を載せる
_sns_clock.importTick = importTick + 1
_sync_state を進める（隙間ありなら max(相手の MAX(id), 相手の prunedThroughId)）
```

**受け取った版はそのまま格納する**: `_sns_ts`・`_sns_lamport`・`_sns_instance` を**書き換えない**。
書き換えると、その版を第三の端末へ中継したときに別の版になり、鍵と中身の対応（不変条件 V）が壊れる。
`lamport` の引き上げは `_sns_clock` に対してだけ行う（格納する値には触らない）。

**`Max` が変わったかの判定**: `before` と `after` を**取り込みの側（JS）で比べる**。
`ON CONFLICT … DO UPDATE … WHERE` の `changes()` には頼らない。【確認】退けられた upsert では `changes` が 0 に
なる場合があり（付録 A.17）、版によって数え方が変わるものに通知の有無を賭けない。

**SQL の雛形（K）**: `INSERT … SELECT … ON CONFLICT` は `WHERE true` が要る。

```sql
-- 【確認】WHERE true が無いと near "DO": syntax error になる（付録 A.17）
INSERT INTO "_sns_rows_t" ("id", "name", "updatedAt", "_sns_ts", "_sns_lamport", "_sns_instance")
SELECT ?, ?, ?, ?, ?, ? WHERE true
ON CONFLICT ("id") DO UPDATE SET
  "name" = excluded."name", "updatedAt" = excluded."updatedAt", "_sns_ts" = excluded."_sns_ts",
  "_sns_lamport" = excluded."_sns_lamport", "_sns_instance" = excluded."_sns_instance"
WHERE <STRONGER(excluded, "_sns_rows_t")>;
```

**相手の形が違うとき（G）**:

| 形 | 読み方 |
| --- | --- |
| 相手に `_sns_rows_<t>` が無い | その表について、その相手は主張していないものとして読む（削除ではない） |
| 相手に無い列がある | 自分の表のその列の既定値として読む（`_sns_rows_*` に入れる値は既定値） |
| 相手にしかない列がある | 無視する |
| 相手の `sns-format` が `rows1` でない | §4.2 のとおり相手を丸ごと見送る |

取り込みは `_sns_rows_*`・`_tombstone`・`_changelog`・`_sns_dirty`・`_sns_clock`・`_sync_state` にしか書かないので、
アプリの制約（UNIQUE・外部キー・NOT NULL）で失敗することはない。

### 4.4 `SyncResult`

`inserted` / `updated` / `deleted` は作り直しでアプリの表に入れた・入れ替えた・消した行数。
`skipped` は取り込みで手元の版の方が強かったキーの数。`folds` / `restores` は `_sns_hidden` の差分だけ。
`warnings` は `Unplaceable …`、`Rebuild failed …`、`Rebuild deferred …`、`Hidden <表>:<id>: parent …`、
§3.10 の検出、§6.2 の出口（表を作り直しの対象から外したこと）。

## 5. 規則（12場面）

| 場面 | 案A の振る舞い |
| --- | --- |
| 5-1 基本（実験1・2） | `_sns_rows_tags` は `{g1(t1,00:01), g2(t2,00:03)}`。アプリの表は `g1=t1, g2=t2`。同期を挟む位置によらない |
| 5-2 3行以上が同じ値でかぶる | 版の順序の強い順に置き、置けなかった行は隠れた行。勝者はかぶった置く行のうち最も強いもの。鎖（B→C→A）は作らない |
| 5-3 勝者の書き換え / 削除 | 書き換え: かぶりが解けた行は次の作り直しで置かれる。削除: R0 なので、その端末のアプリの表で `ON DELETE CASCADE` により消えた子にも削除の版ができる |
| 5-4 隠れた行が他端末で更新される | 版の順序で強くなれば、その行が置く行になり、いままでの勝者が隠れた行になる。子の表示値も入れ替わる |
| 5-5 隠れた行が利用者に削除される | 隠れている端末では見えないので消せない。見えている端末で消せばその id の削除の版ができ、他端末でも `Max` が削除になる |
| 5-6 読み替えた子の編集 | 外部キー列を書き換えなければ `_sns_rows_*` の真の値のまま。書き換えればその値。表示中の勝者を明示的に書き直す場合は区別できない |
| 5-7 勝者へ新しい子を足す | その子の真の外部キーは勝者の id。あとで勝者が隠れた行になれば、その子は新しい勝者の下に表示される |
| 5-8 子の重複禁止が読み替え先でかぶる | 子の表も同じ規則で、表示値でかぶりを判定する。読み替えた結果かぶった子は隠れた行になる |
| 5-9 1:1 の子（主キーが親を指す） | 表示上の主キーでかぶる形として扱う。`ON UPDATE CASCADE` で表示 id が変わる場合は削除の版を作らず、`_sns_shown` を書き換える |
| 5-10 複数列の重複禁止・部分索引・式索引・生成列 | 一時 DB に同じ索引を作って SQLite に判定させる。照合順序と値の種類もそのまま効く |
| 5-11 かぶりの連鎖（戻した行が別の行を隠す） | 貪欲に1回なめるだけ。結果は版の順序から決まる |
| 5-12 時刻を作らない | 作り直しも取り込みも時刻を作らない。`_sns_ts` はアプリが書いた値か、手元の版の値。現在時刻が入るのは `_tombstone.deletedAt`（順序に使わない）と `_changelog.changedAt` だけ |

新しく決まる場面: 親より先に子が届く（置かない行）、親の削除とすれ違った子（R0）、消してから同じ id で
作り直す（作り直しが勝つ）、時刻列を変えない書き込み（後の書き込みが勝つ）、NOT NULL・CHECK に当たる行
（置かない行）、値の入れ替え（表全体の入れ替えなので通る）、`ON UPDATE` の動作（R0）。

## 6. 論証

### 6.1 目標 (a)

不変条件 V（同じ鍵の版は中身も格納クラスも同じ）、補題1（`Max_F` は集合だけで決まる）、補題2（`Φ` は
`Max_F` とスキーマの関数。P8 が要る）、補題3（置く行は一時 DB に実際に入った行）、定理1。

**不変条件 V と、列の増減（E）**: 列が増えた／減った表は、その端末が**新しい版の鍵で全行を書き直す**ので、
「同じ鍵なのに中身が違う版」は生まれない。既定値を1回評価して埋める方式は、評価のたびに変わる既定値で
V を壊すので採らない。取り込みが受け取った版を書き換えないこと（§4.3）も V を守るために要る。

### 6.2 目標 (b)

- 取り込みはアプリの制約が無い表に書くだけ
- 作り直しは、白紙のリストのエラーだけを「置かない行」にし、それ以外は中止して知らせる
- 見送り（`SQLITE_BUSY` と token の不一致。J）は k 回までで、k 回目は計算と適用を1つのトランザクションで行う
- **中止が有限回で終わること（B の出口）**: 外部キーの検査の違反で中止した場合、同じ事実・同じスキーマでは
  同じ計画が出るので、そのままでは同じ例外を繰り返し、その表は二度と作り直せない。
  **2回続けて同じ表で違反が出たら、その表を作り直しの対象から外し、`warnings` に名指しで出す**。
  外したことは `SyncInstance` の記憶に持ち、**その表の `_sns_tick` が動いた（新しい事実が来た）ときに解く**。
  これで、作り直しは有限回で必ず止まる（対象の表の数は有限で、外した表は事実が変わるまで再挑戦しない）

### 6.3 目標 (c)

取り込みも作り直しも版を作らない（旗の番人が要）。`_sns_rows_*` から行が消えるのは、アプリの書き込みが
作った削除の版に負けたときだけ。

**DDL によるアプリの書き込みを記録する場合（E）**: 列の増減のときに全行を新しい版として書き直すのは、
(c) の例外ではない。`ALTER TABLE` とそれに伴う値の設定は**アプリが行った書き込み**であり、トリガーを
通らなかっただけである。ライブラリは、アプリが既に行った変更を事実として記録しているにすぎない
（ライブラリが自分の判断で中身を変えているのではない）。

### 6.4 参考: （強）が成り立つ条件

C1（1:1 の表への書き込みが無い）、C2（UPDATE は全列を書く）、C3（表示中の勝者の id を外部キーへ書かない）、
C4'（`ON DELETE`/`ON UPDATE` が子に及ぶ行を消す・主キーを変える文が無い）、C5（`deleteProtected` の削除が無い）、
C6（行を真の id でだけ特定し、書く値がアプリの表を読んだ結果に依存しない）。

### 6.5 論証できていない点

1. （強）は目標から外した
2. SQLite の版の違いで、CHECK・式索引・生成列・照合順序・`julianday` の受け入れ方が変わりうる
3. 索引の字句解析が正しいのは、解析できた形についてだけ
4. P8 の検査は字句解析なので、別名の関数・将来の非決定的な関数・接続ごとの登録は見落としうる
5. 引き上げの恒久性
6. ISO の字形の判定の限界
7. アプリのトリガーが保証している不変条件は、作り直しの適用では保たれない
8. 自己参照する表で輪になったデータは置かれない
9. 1:1 の表で「親の主キーが変わった」のか「アプリが別の親へ付け替えた」のかを区別できない
10. 他の接続が書き込みを続けていると、k 回目でもロックが取れない
11. 外部での書き換えで消された行は反映されない
12. ワーカーが Electron の主プロセスで動くことは未確認
13. 同着は書き込み量の多い端末が勝ちやすい
14. 作り直しの間はアプリの表が `Φ(F)` と違う
15. **§6.2 の出口で対象から外した表は、その表の事実が変わるまで表示が更新されない**（同期は続く）
16. **取り込みの窓でアプリが一部の列を編集すると、`OLD` に落ちた列の値で行が復活しうる**（§9 の項目。
    他端末が見たことのない内容が、その端末の版として全端末へ渡る）
17. **（強）は、`_sns_ts` の引き上げがある以上、案A では成り立たない**（§9.25 の例）。挟み方の検査は
    違反ではなく件数の記録として扱う（§8.1）

    同じ事実から違う表示になる（P14。警告は出すが、止めはしない）

## 8. 検査

### 8.1 判定

1（表示の一致）、2（同期が事実を作らない）、3（同期が止まらない）、4（参照実装との一致）、6（`Max` の単調）、

11（順序の性質）、12（版の突き合わせ）、13（置かない行・隠れた行の逆向きの検査）、14（移行の中断）、
15（`PRAGMA foreign_keys` の復元）、16（アプリのトリガーの置き場所）、17（適用で `lamport`・`_tombstone`・
`_sns_dirty` が増えない）、18（1:1 の `ON UPDATE CASCADE`）に加えて、

| # | 判定 |
| --- | --- |
| **19** | **取り込みが受け取った版をそのまま格納していること**（`_sns_ts`・`_sns_lamport`・`_sns_instance` が、相手の値と一致する。3端末で中継して確かめる） |
| **20** | **ワーカーの計算が1つの快照から読んでいること**（計算の途中に親を消す差し込みを入れ、適用が見送られるか、消した行が戻らないこと） |

**挟み方の検査（（強）の検査）の言い分を弱める**: 案A では「同じ操作の集まりなら同じ見え方」は**成り立たない**。
`_sns_ts` の引き上げ（§1.2.1）があるので、**他端末の版を取り込んだあとに、より古い時刻でその行を書くと、
引き上げのぶんだけ強い版になる**（取り込んでいなければ弱い版のまま）。したがって、この検査は
**違反ではなく件数の記録**として扱い、反例の一覧は「（強）が破れた形の観察」として出す（§6.5-17、§9.25）。

### 8.2 検査器の作り

主スレッドで計算する経路、計算中の差し込み口、`BEGIN IMMEDIATE` を失敗させる口、`generation`・lamport・
`instanceId` の正規化、新しい操作（未来の時刻・時刻列を変えない UPDATE・消してすぐ作り直す・
`ON DELETE SET NULL` の子を持つ親を消す・1:1 の親の主キーを変える）。

**端末の入れ替えによる対称性の畳み込みは、案A では使えない（健全でない）。**
同着の最後の鍵が `instanceId` のバイト列（§1.2.5）なので、「`iid` の小さい端末が書いた状態」と
「大きい端末が書いた状態」は鏡写しにならない。同じ操作を端末を入れ替えて当てても、勝つ版が入れ替わるとは
限らないためである。【確認: 段階6 の検査器の自己検査が、素の実装でこれを検出した】。
したがって検査器は**端末の入れ替えを畳まない**（`--no-symmetry` 相当が既定）。状態数はそのぶん増える。

## 9. 既知の制限と README に書く注意点

第9版の22項目に次を足す。

23. **取り込みの窓でアプリが一部の列だけを編集すると、その端末でしか見たことのない内容の行が全端末へ渡る。**
    取り込みが `_sns_rows_*` の行を消した直後（＝ `Max` が削除になった直後）に、アプリがその行の一部の列を
    UPDATE すると、書かなかった列は `OLD`（アプリの表に残っていた古い値）に落ちる（§3.4.3 の3分岐）。
    その版は取り込んだ削除より強くなりうるので、**行が復活し、他端末が一度も見ていない中身が広まる**。
    §5 の場面(3)（削除のあとに別の端末が親を編集する）と結果は似ているが、**戻る中身が違う**
    （場面(3) は編集した端末が持っていた版、こちらはアプリの表に残っていた列の値）
25. **（強）は成り立たない。** 「同じ操作の集まりなら、同期をいつ挟んでも同じ見え方」は案A では保証しない。
    `_sns_ts` の引き上げがあるので、**他端末の版を取り込んだあとに、より古い時刻でその行を書くと、
    取り込んでいなかった場合より強い版になる**。例: a が `X` を 10:00 で書き、b がそれを取り込んでから
    `X` を 09:00 で書くと、b の版は `_sns_ts = 10:00`（引き上げ）＋ b の `lamport` で a に勝つ。
    b が取り込む前に 09:00 で書いていれば、`_sns_ts = 09:00` で a に負ける
26. **`deleteProtected` の意味が変わった。** 旧方式は「利用者操作による削除を**他端末から**適用しない」で、
    消した端末ではその行が消えたままだった。案A では「**削除の版は表示の計算で勝たない**」なので、
    **消した端末でも次の作り直しでその行が戻る**（§1.3.1）。削除の事実は捨てないので、設定を外せばそのとき効く。
    設定は全端末で同じにすること（P14。違えば警告が出る）
24. **NAS への写しは `backup()` で作る。** WAL の DB を `copyFile` で写すと `-wal` が付いてこないので、
    写しから最近の書き込み（`_sns_rows_*` を含む）が見えない
