## 0. 要約

**同期は事実を作らない。事実を作るのはアプリの書き込みだけにする。** 畳みは、受け取った
事実の集合から毎回導く「見え方」にすぎず、どこにも記録として刻まない。

- 事実は「行の版」と「削除の版」の2種類だけ。1つの行について、いちばん強い版（新しい版）
  だけが意味を持つ
- 生きている版（候補）の中で、重複禁止の値がかぶる行どうしは、`isPreferredOverRival` の
  順（時刻が新しい方、同時刻なら主キーの辞書順で小さい方）に**貪欲に**選ぶ。先に選ばれた行と
  かぶる行は「まとめられた行」になり、アプリの表からは見えなくなる
- まとめられた行の中身は、新しい同期対象の表 `_hidden_<表>` に**真の版のまま**置く
  （他端末へ渡る）。子の外部キーを付け替えたときは、元の値を `_repoint` に置く
  （これも他端末へ渡る）
- かぶりが解消すれば、同じ規則で導き直すだけで、まとめられた行と子が元に戻る

いまの実装が実験1と実験2で違う結果になるのは、**同期そのものが事実を1つ作っている**からで
ある【確認】。実験1では、②のあとの同期が
`_tombstone(g1, deletedAt=00:02, mergedInto=g2)` を書く（付録A）。つまり実験1と実験2では
受け取った事実の集合がそもそも違う。この設計では、同期が書くのは導いた見え方と、その符号化
（`_hidden_*` / `_repoint`）だけになる。事実の集合は実験1と実験2で同じなので、結果も同じになる。

## 1. 意味の定義

### 1.1 事実

すべての端末で共通の、次の2種類の**事実**を考える。`t` は表、`k` は**真の主キー**。

| 種類 | 形 | 作る者 |
| --- | --- | --- |
| 行の版 | `W(t, k, ts, c)` | アプリの INSERT / UPDATE。`ts` はその行の時刻列、`c` は全列の値 |
| 削除の版 | `D(t, k, ts, a)` | アプリの DELETE（とそのカスケード）。`ts` は削除した時刻。`a` は旧版が残した畳み先（§2.5）で、この設計が新しく作る削除では常に `⊥` |

`c` の外部キー列には**真の値**が入る。真の値とは、アプリが書いた値（§3-6 の規則で決まる）で
あり、ライブラリが表示のために付け替えた値ではない。

**端末の状態とは、受け取った事実の集合 `F` のことである。** 自分のアプリが作った事実も、
他端末から受け取った事実も区別しない。

### 1.2 版の強さと `Max`

同じ `(t, k)` の版には、次の全順序 `≺`（右が強い）を置く。

1. 時刻 `ts` を時刻として比べる（`julianday`。`compareTimestamps` と同じ）
2. 同時刻なら、削除の版が行の版より強い（`isShadowedByTombstone` の「同時刻は削除が勝つ」と同じ）
3. 同時刻の削除どうしは、`a ≠ ⊥` のものが強い。`a` どうしは文字列として小さい方が強い
4. 同時刻で中身の違う行の版どうしは**順序を定めない**（前提 P1）

`Max_F(t, k)` は、`F` に含まれる `(t, k)` の版のうち最も強いもの。版が無ければ `⊥`。

### 1.3 候補

表 `t` の**候補**とは、`Max_F(t, k)` が行の版である `k` の、その版のことである。
`Max_F(t, k)` が削除の版なら `k` は**死んでいる**。

### 1.4 表示値（外部キーの読み替え）

表は外部キーの依存の順（親が先）に処理する（前提 P2）。親の表 `p` について §1.6 で
`Res_p(k)`（真の id `k` がいま表のどの行として見えているか）が決まっているとき、子の候補
`c` の**表示値** `disp(c)` を次で決める。

- 親の主キーを指す外部キー列 `col`（`c.col = k`）: `Res_p(k) ≠ ⊥` なら `Res_p(k)` に置き換える。
  `⊥` なら置き換えない（その扱いは既存の `ON DELETE` 規則。範囲外、§4.5）
- 親の主キー以外の重複禁止列を指す外部キー（`REFERENCES p(code)`）: その値を持つ候補のうち
  最も強い候補を `h` とする。`h` が見えているなら値はそのまま。`h` がまとめられているなら、
  `h` の勝者（§1.6）の、指されている列の値に置き換える
- それ以外の列は、真の値のまま

主キーが外部キーを兼ねる表（`tag_profiles.id REFERENCES tags(id)`）では、主キー列も
この規則で置き換わる。つまり**表示上の主キーと真の id が違う**ことがある。

### 1.5 かぶる

同じ表の2つの候補 `x`, `y`（真の id が違う）が**かぶっている**とは、次を満たすユニークキー
`K` が1本でもあることをいう。

- `K` の全列について `disp(x)` と `disp(y)` の値が NULL でなく、`K` の照合順序で等しい

ユニークキーとして数えるのは、次の2種類である。

- `readSecondaryUniqueKeys` が返すもの。部分索引と式索引は含まない（いまと同じ）
- 主キーが外部キーを兼ねる表では、表示上の主キーも数える

**かぶるかどうかは表示値、つまり「いまの値」だけで決まる。** かつてかぶっていたかどうかは
使わない。

### 1.6 勝者・まとめられた行・見え方

表 `t` の候補を、次の順（前が強い）に並べる。

> **時刻が新しい方、同時刻なら真の主キーの辞書順で小さい方**

これは `isPreferredOverRival` そのものである。主キーには**真の id** を渡す。1:1 の表では、
かぶった2行の表示上の主キーは同じになるためである。

この順に1つずつ見ていき、次の手続きで分ける（**貪欲**）。

- それまでに「見える」と決まった候補のどれともかぶらなければ、**見える行**にする
- かぶる相手が居れば、**まとめられた行**にする。その候補の**勝者**は、かぶる見える行のうち
  最も強いもの

`Res_t(k)` は次のように決まる。

- `k` の候補が見える行なら、その `disp` の主キー
- `k` の候補がまとめられた行なら、その勝者の `Res_t`。勝者は見える行なので1段で止まる
- `k` が死んでいて、その削除の版が `a ≠ ⊥` を持つなら、`Res_t(a)`（§2.5 の旧版の畳み。
  鎖はたどり、循環したら `⊥`）
- それ以外は `⊥`

**見え方** `Φ(F)` は、各表 `t` について `{ disp(c) | c は見える行 }` である。これがアプリの
表の中身そのものになる。

用語の対応:

| 言葉 | 定義 |
| --- | --- |
| かぶっている | §1.5 |
| かぶりが解消した | `F` が増えた結果、ある候補が、いまの勝者（とそれより強い見える行）の誰ともかぶらなくなった |
| 勝者 | §1.6 の「かぶる見える行のうち最も強いもの」 |
| まとめられた行 | §1.6 で見えないと決まった候補 |
| 付け替えた子 | 真の外部キーの値と表示値が違う子 |

### 1.7 前提

| 記号 | 前提 | 破れたとき |
| --- | --- | --- |
| P1 | 同じ `(t, k)` に、同時刻で中身の違う行の版は無い | その行は膠着。いまと同じく報告だけする |
| P2 | 同期対象の表の外部キーは循環しない（自己参照も無い） | 表示値が1回では決まらない。【確認】両アプリ（`score-at-once-electron`、`school-planner`）の Prisma スキーマに自己参照の関係は見当たらない（字面での検索） |
| P3 | 時刻列の値は `julianday` で読める | `isLaterTimestamp` の字面へのフォールバックは推移律を保証しない |
| P4 | 全端末で、同期対象の表・ユニーク索引・時刻列・`deleteProtected` の設定が同じ | `schemaVersion` の不一致は、いまと同じく相手を見送る |

### 1.8 定義の帰結（実験への当てはめ）

受け取った事実は、実験1でも実験2でも次の3つである。

```
W(tags, g1, 00:01, name=t1)
W(tags, g2, 00:02, name=t1)
W(tags, g2, 00:03, name=t2)
```

`Max` を取ると候補は `g1(t1, 00:01)` と `g2(t2, 00:03)` になる。この2つはかぶらないので、
両方が見える行になる。**`Φ = { g1=t1, g2=t2 }`**。途中で同期を挟んでも事実は増えないので、
実験1も同じになる。

### 1.9 採らなかった定義

- **連結成分ごとに1行だけ残す**（A と B がかぶり、B と C がかぶるなら A だけ残す）:
  A と C はかぶっていないのに C が見えなくなり、「かぶっていないものは見える」に反する。
  §3-11 の連鎖で、戻すべき行が戻らない
- **畳んだ時点の勝敗を覚えておく**: 覚えた勝敗は履歴であり、事実の集合だけからは決まらない。
  いまの実装が抱えている問題そのものである
- **1:1 の子は親に従う（子の時刻を見ない）**: 表ごとの規則が2つになる。1:1 でも「表示上の
  主キーがかぶった」という同じ形に還元できるので、一般の規則に入れた（§3-9）

## 2. データの持ち方

### 2.1 置き場所の決定

【決定】`_tombstone` は広げない。まとめられた行の中身と付け替えた子の元の値は、
**新しい表**に置く。

理由:

1. **旧版の端末は `_tombstone` の行を削除（または畳み）として読む。** まとめられた行を
   `_tombstone` に置くと、旧版はそれを消す主張と受け取り、生きている行を消す
   （`sync/entries.ts` の `applyTombstoneDelete`）【確認: コードを読んだ】
2. まとめられた行は削除ではない。版として `W` であり、`D` ではない。同じ表に置くと
   「強い版」の比較に種類の違う2つが混ざる
3. `_tombstone` の主キーは `(tableName, recordId)` の1行だけで、行の全列（BLOB を含む）を
   型を保ったまま載せられない

`_id_merge` は他端末へ渡らないので、置き場所の候補にならない。

### 2.2 新しい表

`_` で始まる表は `discoverTables` の対象外で、`computeSchemaHash` にも入らない【確認】。
どれも NAS のコピーにそのまま載るので、他端末から読める。

#### `_hidden_<表>` —— まとめられた行の真の版

```sql
CREATE TABLE IF NOT EXISTS "_hidden_tags" (
  -- 元の表と同じ列名・同じ宣言型。制約・既定値・外部キーは付けない
  id TEXT, name TEXT, updatedAt TEXT,
  PRIMARY KEY (id)
);
-- 元の表のユニークキーごとに、同じ列・同じ照合順序の「ユニークでない」索引
CREATE INDEX IF NOT EXISTS "_hidden_tags__name" ON "_hidden_tags"(name COLLATE BINARY);
```

- 行は**真の id と真の値**で置く。外部キー列も真の値である（`_repoint` は要らない）
- 表ごとに写しの表を作るのは、BLOB、整数と実数の区別、大きな整数を型のまま残すため。
  JSON では落ちる
- アプリのマイグレーションで列が増えたら、`setupChangelog` が起動のたびに足す。
  【推測】列の改名は追えない（写しの表の古い列は読まれない）。移行時の注意として書く

#### `_hidden_target` —— まとめられた行の勝者（ローカルの控え）

```sql
CREATE TABLE IF NOT EXISTS _hidden_target (
  tableName TEXT NOT NULL, recordId TEXT NOT NULL, targetId TEXT NOT NULL,
  PRIMARY KEY (tableName, recordId)
);
```

最後に導いた勝者の真の id である。**事実ではなく導出の控え**で、読む側は使わない。削除
トリガーが「その行と一緒に消える行」を引くためだけにある（§2.4）。

#### `_repoint` —— 付け替えた子の元の値

```sql
CREATE TABLE IF NOT EXISTS _repoint (
  tableName      TEXT NOT NULL,   -- 子の表
  rowId          NOT NULL,        -- 表に置いてある行の主キー（表示上の主キー）
  columnName     TEXT NOT NULL,   -- 付け替えた列（1:1 の表では主キー列そのもの）
  originalValue,                  -- 真の値（型を保つため、型を宣言しない）
  displayedValue,                 -- いま表に置いている値
  version        NOT NULL,        -- この記録が当てはまる、その行の版の時刻
  PRIMARY KEY (tableName, rowId, columnName)
);
```

- **表示値と真の値が違う列についてだけ**行を置く。戻ったら消す
- 複合外部キーは列ごとに1行
- `version` が、その行の時刻列の値と**時刻として等しい**ときだけ効く。違えば「その記録より
  新しい版をアプリが書いた」ことになり、表の値が真の値になる（§3-6）

#### `_sync_writing` —— 「いまはライブラリが書いている」の旗

```sql
CREATE TABLE IF NOT EXISTS _sync_writing (onlyRow INTEGER PRIMARY KEY CHECK (onlyRow = 0));
```

旗は、ライブラリの取り込みトランザクションの中で立てて、その中で下ろす。
**TEMP 表にはできない**。トリガーから TEMP 表は参照できない（`no such table: main.tf`）【確認: 実験】。
better-sqlite3 のトランザクションは同期的で、`copyToNas` の `await` はトランザクションの
外にある（`sync.ts`、`sync/pull.ts`）。そのため、旗を立てたままアプリの書き込みが割り込むことは
ない【確認: コードを読んだ】。

#### `_sync_meta` のキー

`foldProtocol = '2'`。この設計の端末であることの印で、旧版の検出に使う（§2.6）。

### 2.3 公開する符号化と、読む側の規則

端末 X の DB（NAS のコピー）からは、`(t, k)` の最も強い版を次のように読む。

1. 表 `t` の行のうち、**真の id が `k`** のもの。真の id は、主キー列に効いている `_repoint`
   があれば `originalValue`、無ければ主キーの値。外部キー列も効いている `_repoint` があれば
   `originalValue` で読む
2. `_hidden_t` の `k` の行
3. `_tombstone` の `k` の行。`deletedAt` と `mergedInto` を読み、`revokedAt` は §2.7 で扱う

この3つのうち §1.2 で最も強いものが、X にとっての `Max(t, k)` である。

**符号化の不変条件（I1）**: 各端末の DB は、自分の `F` のすべての `(t, k)` について、上の読み方で
`Max_F(t, k)` を返さなければならない。表と `_hidden_t` の両方に同じ真の id が載ることは無い
（排他）。`_tombstone` は、その `k` のより弱い削除として残っていてよい。

**`_changelog` の役割は「どの `(t, k)` を読み直すべきか」の通知だけになる。** 読む側は、
エントリの `operation` と `changedAt` を LWW に使わない。いま `entry.changedAt` を削除時刻の
代わりにしている経路は、相手の DB に `_tombstone` 表そのものが無い場合だけに残す。

### 2.4 トリガー

いまのトリガー（`setup/index.ts` と、それを写した `sync/triggers.ts` の `reEnableTriggers`）を
次の形に作り直す。

- **INSERT / UPDATE**: `WHEN NOT EXISTS (SELECT 1 FROM _sync_writing)` を付ける。
  中身はいまと同じ
- **DELETE**: 同じ `WHEN` を付けて、次を行う
  1. 真の id `k = COALESCE((主キー列に効いている _repoint.originalValue), OLD.pk)` について、
     `_changelog` に DELETE を書き、`_tombstone(k, 現在時刻, mergedInto=NULL)` を書く
  2. **一緒に消える行**: `_hidden_target.targetId = k` の隠れ行のうち、**OLD の二次ユニークの
     値のどれかと今もかぶる**ものすべてについて、同じ `deletedAt`（1. で書いた値を読み直す）で
     `_tombstone` と `_changelog` を書き、`_hidden_t` と `_hidden_target` から消す。
     1:1 の表では、`targetId = k` の隠れ行を全部含める。表示上の主キーでかぶっているため
  3. `_repoint` から、`tableName = t AND rowId = OLD.pk` を消す

  かぶりの再確認は、表ごとのユニークキーからトリガーの SQL を組み立てて行う。セットアップは
  表ごとにトリガーを作っているので、生成できる。
- **旗が立っている間は何も書かない。** ライブラリが導出のために行を消したり書いたりしても、
  `_tombstone` も `_changelog` も増えない。カスケードで子のトリガーが走っても、同じ旗で
  止まる【確認: 実験。旗を立てて親を消すと、子はカスケードで消え、子のトリガーは何も書かなかった】

この形にすると、フルマージのたびにトリガーを DROP して作り直す処理（`sync/triggers.ts`）は
要らなくなる。旗を立てるだけで済む。

**隠れた孫（`_hidden_<子>` の行で、真の親が一緒に消える id を指すもの）** は、トリガーからは
再帰的にたどりにくい。そこで次の `performSync` の自己点検（`sync/self-check.ts`）で補う。
自己点検は `_changelog` のカーソル以降に自分が書いた DELETE を読み、`ON DELETE CASCADE` の
外部キーでそれを指している隠れ行に、同じ `deletedAt` の削除を書く。自己点検は、導出より先に
走り、NAS へのコピーより先に走るので、他端末からは1回の削除として見える。

### 2.5 過去の畳み（中身を持たない履歴）

【決定】**過去の畳みは戻さない。** 旧版が書いた `_tombstone(k, T, mergedInto=W)` は、
§1.1 の `D(t, k, T, a=W)` として読む。

- `k` の最も強い版がこの削除なら、`k` は死んでいて、`Res_t(k) = Res_t(W)` になる（§1.6）。
  遅れて届いた `k` の子は、いまと同じく `W` の行へ付け替わって見える
- `T` より新しい `k` の版が届けば、いまと同じく `k` は候補に戻る
- 既存の DB の表は、過去の畳みを適用し終えた姿（敗者は無く、子は勝者を指したまま）である。
  子の真の値は勝者として扱う（元の値は失われている）
- 移行で書くものは、新しい表を作ることと `foldProtocol` だけ。最初の導出は、ほとんどの DB で
  何も変えない。【推測】「幽霊」（`mergedInto` の墓標があるのに敗者行が残っている形）を持つ DB
  では、最初の同期でその行が消える（`Max` が削除になるため）。**本番の DB の写しで、最初の同期の
  差分を事前に測ること**（§7 段階6）
- `_id_merge` は書くのをやめて凍結する。読むのは移行の検算だけ。ライブラリを旧版へ戻したときに
  使えるよう、表は1版のあいだ残す
- 旧版の `A→C`、`C→B` の鎖は、`Res` がたどる。`collapseIdMergeChains` は要らない

### 2.6 旧版の端末が混ざったとき

【決定】**止めずに、警告して続ける。** 相手の DB の `_sync_meta` に `foldProtocol` が無ければ、
`SyncResult.warnings` へ次を出す。

`Client X runs an older sqlite-nas-sync; merged rows may not be restored while it takes part`

旧版が混ざると、次のように振る舞う【推測: コードを読んだうえでの見立て】。

| 旧版の端末がすること | 新版の端末から見えること |
| --- | --- |
| いまの実装のまま畳み、`mergedInto` 付きの墓標を公開する | §2.5 の旧版の畳みとして読む。**その畳みは戻らない**（旧版の端末が1台でも畳めば、その組は戻らない）。結果は全端末で揃う |
| 新版の `_hidden_*` / `_repoint` を読まない | 新版の端末で隠れている行は、旧版からは「届かない行」に見える。旧版が自分でその行を持っていれば、旧版の規則で畳む（上の行） |
| 付け替えた子を「その時刻のその値」として受け取る | 同じ時刻で外部キーの値だけが違う版が、旧版と新版で並ぶことがある（P1 の破れ）。**膠着として報告される** |
| 1:1 の子の、表示上の主キーの行を受け取る | 別の id の中身が、その id の版として写る【推測】。両アプリにはこの形の表が無い【確認: 字面での検索】 |

同期が止まる壊れ方（取り込みの巻き戻り）は、この表からは生まれない見込みである【推測】。
§7 段階7 で、端末ごとにライブラリを差し替えて網羅検査することを提案する。

### 2.7 `revokedAt`

`revokedAt` は**一度もリリースされていない**。v0.19.0 のタグにも HEAD のコミットにも無く、
作業ツリーにだけある【確認: `git show`】。したがって本番の DB には無い。新しい設計では書かない。
開発中の DB に残った取り消し済みの墓標は、移行のときに「その墓標は無い」として読む
（いまの `isTombstoneRevoked` と同じ答え）。取り消されていない墓標は §2.5 の旧版の畳みとして読む。

## 3. 規則

各規則は **状況 → 決定 → 結果 → 理由** の順で書く。どれも §1 の定義から導いた答えであり、
例外の分岐ではない。

### 3-1. 基本（実験1・実験2）

- **状況**: 実験1（①② → 同期 → ③ → 同期）と実験2（①②③ → 同期）
- **決定**: 同期は事実を作らない。①②のあとの同期で、`g1` は `_hidden_tags` へ移り
  （`_hidden_target(g1→g2)`）、`g1` の子は `g2` へ付け替わって `_repoint` に元の値 `g1` が
  残る。`_tombstone` と `_id_merge` には何も書かない
- **結果**: ③（`g2` を `t2`、00:03）を受け取って導き直すと、`g1(t1)` と `g2(t2)` はかぶらない。
  `g1` は表へ戻り、子は `_repoint` の元の値 `g1` へ戻り、`_repoint` の行は消える。
  **実験1も実験2も `g1=t1, g2=t2`**。子 `n1` は `g1` に付く
- **理由**: §1.8

### 3-2. 3行以上が同じ値でかぶる

- **状況**: `A(t1, 00:03)`、`B(t1, 00:02)`、`C(t1, 00:01)`
- **決定**: 順は A, B, C。A が見える行になり、B と C はどちらも勝者 A にまとめられる
  （`_hidden_target` は B→A と C→A。B→C のような鎖は作らない）
- **結果**:
  - B を `t2`（00:04）へ変える → 順は B, A, C。B も A も見え、C は A にまとめられたまま
  - A を `t2`（00:04）へ変える → 順は A, B, C。A は見える行になる。B は A とかぶらないので
    見える行になる。C は B とかぶるので **B にまとめられる**（勝者が A から B へ移る）。
    C の子の表示値は B の id になり、`_repoint.displayedValue` もそれに合わせて書き換わる。
    `originalValue`（C）は変わらない
- **理由**: 勝者は「いま見えている行のうち、かぶる中で最も強いもの」で、毎回導き直す

### 3-3. かぶりが解消する原因が、勝者の書き換えか、勝者の削除か

**書き換えと削除は違う結果になる。**

- **勝者の書き換え**（`g2` を `t2` にする）: 3-1 のとおり、まとめられた行は戻る
- **勝者の削除**:
  - **削除した端末で、その勝者に行がまとめられていた場合**: 削除トリガー（§2.4）は、
    その勝者と、今もその勝者とかぶっている隠れ行を**一緒に**消す。どれも同じ `deletedAt` を持つ
    削除の版になり、他端末へ渡る。**戻らない**
  - **削除した端末が、まとめられた行を知らなかった場合**（その行をまだ受け取っていない端末が
    勝者を消した）: 削除の版は勝者の id の分だけ作られる。受け取った端末では、まとめられていた
    行のかぶる相手が居なくなるので、**戻る**
- **理由**: 利用者が消したのは「その端末で見えていた1つのもの」である。見えていた1つには、
  その端末でまとめられていた行が全部入っている。消した端末が知らなかった行は、利用者が消そうと
  した対象に入っていない。どちらも「作った端末が知っていたこと」で決まる事実なので、見え方は
  事実の集合から一意に決まる

### 3-4. まとめられた行が、他端末で更新される

- **状況**: B では `g1` が `g2` にまとめられている。`g1` がまだ見えている端末 A で、`g1` が
  更新されて新しい版が届く
- **決定**: 版の比較（§1.2）で新しい版が `Max(g1)` になり、候補の中身が入れ替わる
- **結果**:
  - 重複禁止の値が同じまま、時刻が `g2` より古い → まとめられたまま。`_hidden_tags` の `g1` を
    新しい版で書き換える。表は変わらない
  - 重複禁止の値が同じまま、時刻が `g2` より新しい → **順が入れ替わる**。`g1` が見える行、
    `g2` がまとめられた行になる。`g2` の子は `g1` へ付け替わって `_repoint` に元の値 `g2` が残り、
    `g1` の子の `_repoint` は消える
  - 重複禁止の値が変わってかぶらない → 両方見える（3-1 と同じ）
- **理由**: 勝敗の物差しは `isPreferredOverRival`（時刻が新しい方）で、それを「いまの版」に
  当てるとこうなる。**編集するたびに勝者が入れ替わりうる**ことは、この物差しを選んだ帰結で
  ある。いまの実装も同じ入れ替わりを起こしている（`applyMergedDelete` が「敗者行の方が
  新しければ畳みを見送る」）【確認: コードを読んだ】

### 3-5. まとめられた行が、利用者に削除される

- **どの id を消したのか**:
  - まとめられている端末では、その行はアプリから見えない。アプリが消せるのは見えている勝者で、
    3-3 の「一緒に消える」になる。消えるのは勝者の真の id と、今もかぶっている隠れ行の id である
  - まだ見えている端末（受け取っていない端末）でアプリがその行を消した場合は、**その行の id
    だけ**が消える
- **結果**: その id の削除の版は、同期でまとめられた側の端末へ届く。それが `Max` になれば
  候補ではなくなり、`_hidden_tags` から消える。まとめられていた行の子（勝者へ付け替わって
  見えている子）は、真の親が死んだことになる。扱いは既存の `ON DELETE` 規則になる（§4.5 の範囲外）。
  削除した端末がその子を持っていれば、カスケードの削除の版が作られて届くので、全端末で消える
- **理由**: README「直っていないこと」5 は「利用者が敗者 id を消したとき、それが記録を消した
  のか、死んだ id を消したのか分からない」だった。この設計では、利用者は見えている行しか
  消せず、消したものは消した端末が id で列挙して事実にするので、読み分けは起きない

### 3-6. 付け替えた子が、まとめられている間に編集される

子 `n1` の真の親が `g1`、表示上の親が `g2` で、`_repoint(n1, tagId, 元=g1, 表示=g2, version=v)`
があるとする。

- **外部キー以外の列だけを編集した**（アプリは `tagId=g2` のまま、時刻 `v'` で書く）
  - **決定**: 次の同期の自己点検（導出の前）が、`_changelog` のカーソル以降の書き込みを見る。
    表の `tagId` が `_repoint.displayedValue` と等しければ「外部キーは変えていない」とみなし、
    `_repoint.version` を `v'` へ進める
  - **結果**: 真の版は `W(n1, v', tagId=g1, 新しい本文)`。`g1` が戻れば `n1` は `g1` に付く
- **外部キーそのものを別の親 `p` へ変えた**
  - **決定**: 表の値 `p` が `displayedValue` と違うので、`version` を進めない。記録は古くなり、
    効かなくなる。自己点検が記録を消す
  - **結果**: 真の版は `tagId=p`。`g1` が戻っても `p` のまま
- **表示されている勝者 `g2` を、あらためて明示的に選び直した**
  - **決定**: 値が変わらないので、上の「変えていない」と区別できない。「変えていない」として扱う
  - **結果**: `g1` が戻ると `g1` に付く
- **子を消した**: トリガーが `_repoint` の行を消す（§2.4-3）
- **理由**: 事実を作るのはアプリの書き込みで、その真の中身は**書いた端末が書いた時点の見え方**
  で決めてよい（読む側はそれを受け取るだけなので、見え方の決定性を壊さない）。書いた時点の
  見え方は、自己点検までの間は変わらない。導出は同期の中でしか走らず、自己点検はその先頭で走る

### 3-7. まとめられている間に、勝者へ新しい子が足される

- **状況**: `g1` が `g2` にまとめられている端末で、アプリが `g2` に子 `n2` を足す
- **決定**: `n2` の真の外部キーは `g2`。`_repoint` は作らない
- **結果**: `g1` が戻っても `n2` は **`g2` に付いたまま**。のちに 3-4 で `g2` がまとめられる側に
  回れば、`n2` は新しい勝者へ付け替わって見え、`_repoint(元=g2)` が付く
- **理由**: アプリが指した id は `g2` であり、ライブラリが付け替えたものではない。「本当は
  `g1` に足したつもりだった」は、事実からは読み取れない。そこへ寄せると、`g2` へ足した子まで
  動いてしまう

### 3-8. 子も重複禁止の値を持っていて、付け替え先でさらにかぶる

- **状況**: `docs/child-fold-not-revoked.md` の形。`es-a` が `es-b` にまとめられ、
  `sd-a(→es-a, 設問1, 0002)` の表示値が `(→es-b, 設問1)` になって、`sd-b(→es-b, 設問1, 0004)`
  とかぶる
- **決定**: 子の表の候補を表示値でかぶりを判定し、同じ貪欲で分ける。`sd-b` が見える行、
  `sd-a` はまとめられた行になる。`sd-a` は真の値（`→es-a`）のまま `_hidden_score_decisions` に
  置く。`sd-a` の子（孫）は `sd-b` へ付け替わって `_repoint` が付く
- **結果**: 文書の手順5（`es-a` を 佐藤、0006）が届くと、`es-a` は見える行へ戻る。`sd-a` の表示値は
  `(→es-a, 設問1)` になり、`sd-b` とかぶらないので `sd-a` も戻る。孫も戻る。**文書の
  「規則1〜4 で足りないもの」（佐藤の設問1が失われる）は起きない**
- **理由**: 子の畳みも記録ではなく、親の見え方から毎回導くためである

### 3-9. 親と主キーを共有する 1:1 の子

- **状況**: `tag_profiles(id REFERENCES tags(id))`。`g1` が `g2` にまとめられた
- **決定**: `profile(g1)` の表示上の主キーは `g2` になる
  - `profile(g2)` が無い → `profile(g1)` の中身が、表の `id=g2` の行として見える。
    `_repoint(tag_profiles, rowId=g2, columnName=id, 元=g1, version)` を置く
  - `profile(g2)` もある → 2つの候補は表示上の主キーでかぶる。§1.6 の順（時刻、同時刻なら
    **真の id** の辞書順）で強い方を `id=g2` の行として見せ、弱い方を `_hidden_tag_profiles` に
    真の id のまま置く
- **結果**:
  - アプリが `id=g2` の行を編集した → 主キーは変えられないので、3-6 の「変えていない」になる。
    **見えている中身の持ち主（上の例では `g1`）の新しい版**になる
  - アプリが `id=g2` の行を消した → トリガーは真の id と、表示上の主キーでかぶっている隠れ行の
    両方を消す（§2.4）
  - `g1` が戻った → `profile(g1)` は `id=g1` へ、隠れていた `profile(g2)` は `id=g2` へ戻る
  - 表示上の主キーを動かすときは、UPDATE ではなく **孫を先に付け替えてから DELETE → INSERT**
    で行う。孫の `ON UPDATE` が働かないようにするためである（README「直っていないこと」6 の
    形を、導出からは作らない）
- **理由**: 1:1 の特別扱いを増やさず、「表示上の主キーがかぶった」という一般の形で扱う。
  いまの `findIdentityOwningParents` を使った向きの決着は要らない。【確認】両アプリには
  この形の表が無い（`fields: [id]` の字面での検索）。したがってこの規則の出番は、テスト用
  スキーマと将来の利用者に限られる

### 3-10. 複数列の重複禁止（`@@unique([a, b])`）で、片方の列だけが書き換わる

- **決定**: かぶりはキーの**全列が等しい**ときだけである（§1.5）。`a` だけを変えて組が
  違えばかぶらない。どちらかの列が NULL になってもかぶらない（SQLite の UNIQUE と同じ）
- **結果**: 組が変わった時点で、まとめられていた行は戻る。ユニークキーが2本ある表
  （`accounts(username, email)`）では、どれか1本でも等しければかぶる。そのため、`username` を
  変えても `email` がまだ等しければ戻らない
- **理由**: SQLite が禁じるものと、ライブラリがかぶりと呼ぶものを一致させる

### 3-11. 元に戻したら、戻した行が別の行とかぶる（連鎖）

- **状況**: `accounts` で `X(u1, e1, 00:03)`、`Y(u1, e2, 00:02)`、`Z(u9, e2, 00:01)`。
  Y は X と `username` でかぶり、Z は Y と `email` でかぶる
- **決定**: 順は X, Y, Z。X が見える。Y は X とかぶるのでまとめられる。Z がかぶる相手の Y は
  見えていないので、**Z は見える**
- **結果**: X が `username` を `u2`（00:04）へ変える → 順は X, Y, Z。X も Y も見える。Z は見えて
  いる Y とかぶるので **まとめられる**。戻した Y が別の行を隠す。どこまで波及しても、結果は
  §1.6 の貪欲1回ぶんで決まる
- **理由**: 貪欲は「順に並べて1回なめる」だけなので、戻す・隠すの連鎖を別の規則として
  持つ必要がない。導き直す範囲は、かぶりでつながった成分に限ってよい（§4.3）

### 3-12. 元に戻した行に付ける時刻

- **決定**: **導出は時刻を1つも作らない。**
  - 戻した行は `_hidden_*` に置いてあった版を、その**版の時刻のまま**表へ書く
  - まとめた行も、表にあった版の時刻のまま `_hidden_*` へ移す
  - `_repoint.version` は、子の行の時刻列の値の写しである
  - 畳みの時刻（いまの `mergedAt`、`deletedAt=勝者の版`）、取り消しの時刻（`revokedAt`）は無い
  - 現在時刻が入るのは次の2つだけで、どちらも LWW の比較には使わない、または**アプリの
    操作そのもの**である
    - アプリの削除（トリガー）の `deletedAt`。一緒に消える行も、同じ1回の削除の時刻を写す
    - `_changelog.changedAt`（通知。§2.3 で比較に使わないと決めた）
- **理由**: 導出の結果に端末ごとの時刻が混ざると、後から同期した端末の時刻が勝ち、見え方が
  事実の集合から決まらなくなる

## 4. 論証

### 4.1 意味の決定性

**補題1（`Max` は集合だけで決まる）**: 前提 P1 のもとで、`≺` は同じ `(t, k)` の版の上の
全順序である。最大元は並べる順によらず一意なので、`Max_F` は `F` の要素の到着順によらない。
さらに、`Max_{F∪G} = Max_F ⊔ Max_G`（各キーごとに強い方）であり、`⊔` は可換・結合的・冪等である。

**補題2（導出は `Max_F` だけの関数）**: §1.3〜§1.6 の各段は、次のものしか入力にしない。

- `Max_F`
- 表とユニーク索引の定義（P4 により全端末で同じ）
- 前の段の結果

各段の手続きは決定的である。

- 候補の並びは `isPreferredOverRival` の全順序（真の id が端末をまたいで一意なので、同点は無い。
  P3）で、一意に決まる
- 貪欲は、並びが決まれば結果が一意に決まる
- 表の処理順は外部キーの依存の順（P2）である。依存の無い表どうしの順は結果に効かない。
  各表の結果が、その祖先の `Res` だけで決まるからである（依存の深さについての帰納法）

**定理1（見え方の決定性）**: `Φ(F)` は `F` だけで決まる。とくに、2つの端末が同じ事実の集合を
受け取っていれば、見え方は同じである。

*証明*: 補題1と補題2の合成である。∎

**同期のタイミングによらないこと**: 同期は事実を作らない（§3-12、§2.4 の旗）。そのため、
「いつ同期を挟んだか」は `F` を変えない。アプリの書き込みは、書いた端末の見え方に依存しうる
（3-6、3-3）。しかしそれはアプリが作った事実の中身の話であり、同じ事実を受け取った端末どうしの
見え方は定理1で一致する。

**実験1がいまの実装で違う結果になる理由**: いまの同期は `D(g1, 00:02, a=g2)` にあたる事実を
作る（付録A）。そのため、実験1の `F` には実験2に無い削除の版が入り、定理1の前提が崩れている。

### 4.2 貪欲の性質

**補題3（衝突が無く、極大）**: 見える行どうしはかぶらない。まとめられた行は、どれも少なくとも
1つの見える行とかぶる。

*証明*: 見える行にするのは、それまでの見える行の誰ともかぶらないときだけである。まとめるのは、
かぶる見える行が居るときだけである。∎

したがって `Φ(F)` は SQLite のユニーク制約を満たす（部分索引・式索引を除く。§4.5）。

### 4.3 導き直しを成分に限ってよいこと

**補題4（成分の局所性）**: 候補を頂点、かぶりを辺とするグラフを考える。ある頂点が見える行か
どうか、およびその勝者は、**その頂点を含む連結成分の中の、それより強い頂点**だけで決まる。

*証明*: 順に沿った強い帰納法で示す。頂点 `v` の判定が見るのは、`v` より強い見える頂点のうち
`v` とかぶるものである。`v` とかぶる頂点は `v` と同じ成分に居る。その頂点が見える行かどうかは、
帰納法の仮定により、同じ成分の中のさらに強い頂点だけで決まる。∎

**系（差分での導き直し）**: `(t, k)` の候補が変わった（増えた・消えた・中身が変わった）とき、
次の2つの和に含まれる頂点が属する**新しいグラフの成分**だけを導き直せば、残りは前回の結果の
ままでよい。

- 変わった頂点を含む、**前回の**グラフの成分
- 変わった頂点を含む、**今回の**グラフの成分

前回の成分に変わった頂点が居なければ、その成分の辺は変わっていない。今回の成分に変わった頂点が
居なければ、その成分は前回と同じ頂点の集合で、同じ辺を持つ。どちらでもない成分は補題4により
前回と同じ答えになる。

子の表へは次のように伝わる。`Res_p` の値が変わった親の id を、真の外部キーとして持つ子の候補を、
「変わった頂点」として子の表に積む。並びの鍵（時刻と真の id）は `Res` に依存しないので、表示値
以外は変わらない。

【確認】この系を、ユニークキー2本、値3種、NULL を含む無作為な候補の集合で、2万回確かめた。
1つの候補を変えたり足したり消したりしたあと、全体をやり直した結果と、上の成分だけやり直した
結果を比べると、**2万回とも一致した**。衝突が無いこと・極大であること（補題3）も同時に確かめた。
これは実装の確認ではなく、補題の反例探しである。

### 4.4 実装が定義どおりに振る舞うこと

実装が満たすべき不変条件を次に置く。

| 記号 | 不変条件 | 担う箇所 |
| --- | --- | --- |
| N0 | 導出（取り込み・フルマージ・自己点検のうち導出にあたる部分）は事実を作らない | §2.4 の旗、§3-12 |
| I1 | 符号化が失われない。各端末の DB は、自分の `F` のすべてのキーについて §2.3 の読み方で `Max_F` を返す | `_hidden_*`、`_repoint`、`_tombstone` の書き方 |
| I2 | 取り込みのトランザクションが終わった時点で、アプリの表 ＝ `Φ(F_local)` | 導出と適用（§7 段階3、4） |
| I3 | 相手 R から、読むべき id の集合 `S` を読むと、`S` の上で `Max_local := Max_local ⊔ Max_R` になる | 読む側（§2.3） |
| I4 | 端末 X で `Max` が変わったキーは、X の `_changelog` の、読む側の読み位置より後に通知が載る。あるいは読む側が隙間を検出してフルマージに落ちる | トリガー（アプリの書き込み）、取り込みで `Max` が変わったキーの通知の書き足し、既存の隙間検出 |
| I5 | アプリの書き込みは、同じキーの手元の `Max` より弱い版で上書きしない | 前提。破れたときは既存の自己点検と `advertiseLocalRow` が補う |

**定理2（収束）**: アプリの書き込みが止まったあと、どの2端末 X, Y についても「X が Y を読む」が
Y の最後の変化より後に起きるように同期を回すと、全端末の `F`（の `Max`）が一致し、I2 により
見え方も `Φ(全事実)` で一致する。

*証明の筋*:

1. 取り込みは `Max` を各キーで強い方へしか動かさない（I3、補題1）
2. キーも版も有限なので、`Max` はいつか動かなくなる
3. 動かなくなったあとで、あるキーについて X の `Max` が Y より強いとする。そうなった時点で
   X の `_changelog` に通知が載る（I4）。Y は次に X を読むときにそれを読み、`Max` を強める（I3）。
   これは「動かなくなった」に反する
4. よって全端末の `Max` は一致し、I2 により見え方も一致する。∎

いまの実装で「名乗り直し」の継ぎ当てが多数要ったのは、I1 と N0 が成り立っていなかったからで
ある。まとめられた行の中身を捨てていた（I1 の破れ）。畳みを事実として刻み、それをあとから取り消す
必要があった（N0 の破れ）。

### 4.5 論証できていない範囲

次のことは、上の論証の外にある。「定義は決まっているが実装で守れるか確かめていない」ものと、
「定義そのものが無い」ものを分けて書く。

**定義の外（いまの振る舞いを据え置く）**

1. **P1 の破れ（同一主キー・同時刻・中身違い）**: 見え方は到着順で決まる。いまと同じく膠着として報告する
2. **真の親が死んでいる、または届いていない子**（`ON DELETE` の再現）: いまの `remap.ts` の規則を
   導出の中で当てる。ただし、取り込み側でカスケードやスキップにより子の版を手元から落とすと、
   I1 が崩れる。親があとで作り直されたとき、子を持っている端末と持っていない端末に分かれうる
   （いまの「採らないと決めた行は戻ってこない」と同じ）。
   **拡張案**: 親が死んでいて見えない子も `_hidden_*`（理由＝孤児）に置けば、この族も定理1の中に
   入る。増えるのは「親の削除とすれ違った子」の数だけである。既存の振る舞い（捨てる）を変えるので、
   本設計の必須範囲からは外した
3. **P2 の破れ（外部キーの循環、自己参照）**: 表示値が1回で決まらない。不動点反復が要る。
   両アプリには無いと見ている（字面での検索）
4. **P3 の破れ（読めない時刻）**: 字面比較へのフォールバックは推移律を保証しないので、補題2の
   「並びが一意」が崩れうる
5. **旧版の端末との混在**（§2.6）: 事実の意味が端末によって違うので、定理1は成り立たない

**定義はあるが、実装で守れるかを論証していないもの**

6. **I2 の適用順序（活性）**: 見え方の差分を SQLite へ当てる途中で、ユニーク制約が一時的に
   ぶつかることがある。たとえば、見える2行が値を入れ替える（`A:t1→t2`、`B:t2→t1`）。
   SQLite の UNIQUE は文ごとに検査されて遅延できない。適用が例外で落ちると、その相手の
   取り込みは毎回巻き戻る（同期が止まる）。§7 段階3 で順序の規則を置くが、**あらゆる形で
   順序が組めることは示していない**
7. **部分索引・式索引のユニーク**: かぶりに数えないので、`Φ(F)` がそれらを破ることがある。
   いまと同じく、適用で例外になり取り込みが巻き戻る
8. **I4（通知の完全性）**: 既存の `_changelog`・隙間検出・フルマージの正しさに寄りかかっている。
   この設計はその部分を変えない（取り込みで `Max` が変わったキーの通知を足すだけ）
9. **I5（アプリが過去の時刻で書く）**: 既存の自己点検の範囲である
10. **自己点検の「書いた時点の見え方」**: 3-6 の判定は、アプリの書き込みから自己点検までの間に
    導出が走らないことに依っている。これはいまの `performSync` の並び（自己点検が先頭）では
    成り立つ【確認: コードを読んだ】。ただし、アプリが `performSync` を二重に呼ぶような使い方を
    すると崩れうる【推測】
11. **削除トリガーの「今もかぶる」の再確認**: トリガーが見るのは最後に導いた勝者の控え
    （`_hidden_target`）である。アプリが勝者の値を変え、同期する前にその勝者を消すと、
    3-3 の「今もかぶる」を OLD の値で確かめるので、変えたあとの値で判定される。これは書いた端末の
    事実なので決定性は崩れないが、利用者の意図に合うかは確かめていない

### 5.3 単純になるか、複雑になるかの見立て

【推測】**規則は大きく単純になり、コードも減る。ただし、新しい種類の難しさが3つ入る。**

- **行数**: 行数は `wc -l` で数えた【確認】。作り直し後は【推測】。
  - 対象の現状: `src/conflict/` 4,952行。`sync/entries.ts`・`self-check.ts`・`full-merge.ts`・
    `state.ts`・`triggers.ts`・`setup/id-merge-repair.ts` で 2,192行。計およそ 7,100行
  - 作り直し後の内訳:
    - 残るもの: `schema`・`timestamp`・`unique`・`stalemate`・`transaction` と、`child-carry`・
      `ON DELETE` の再現。およそ 1,500行
    - 新しいもの: 版の読み書き・導出・適用・移行・取り込み・自己点検。およそ 2,200〜2,600行
  - 計 3,700〜4,100行。このリポジトリのコメントの厚さを保った場合の見立て
- **規則の数**: いまは、「このときは主張を断る」「このときは取り消す」「このときは名乗り直す」の
  ような、到着順ごとの述語が15以上ある。それぞれが実測の反例1つずつに対応している。作り直すと、
  柱は4本になる
  1. キーごとの `Max`
  2. 貪欲の導出1つ
  3. 符号化の読み書き
  4. トリガー
- **新しく入る難しさ**:
  1. **適用の順序**（§4.5-6）。見え方の差分を、ユニーク制約とカスケードにぶつけずに当てる順序。
     いまは畳みと書き込みが1件ずつ交互に起きていたので、この問題は見えにくかった
  2. **1:1 の表の、表示上の主キーと真の id の食い違い**（3-9）。読む側・トリガー・自己点検の
     すべてが `_repoint` の主キー列を知る必要がある。両アプリには出番が無い
  3. **差分での導出**（§4.3）。成分の局所性は示したが、表をまたいだ「変わった頂点」の伝え方を
     実装で漏らすと、I2 が黙って崩れる。参照実装との突き合わせ（§7）で押さえる
- **作り方の危うさ**: 継ぎ当ての積み上げではなく、置き換えである。途中の段階で旧経路と
  新経路を並べて持つ期間ができる。§7 の順序は、検査器の新しい判定を先に作ってから本体を
  置き換える並びにしてある

比例し、戻れば減る。いまの `_id_merge` / `_tombstone.mergedInto` は戻らないので減らなかった。

【推測】`score-at-once-electron` の使い方では、まとめられた行は「複数の先生が同じ実体を
別々に作った」ぶんだけ生まれ、そのほとんどは同じ実体なので、戻らずに残り続ける。
その子（採点など）は `_repoint` の行として残る。行数は、畳まれた親の子の数に比例する。

### 6.2 上限を設ける場合

【決定】**既定では上限を設けない。** `SyncResult` に件数を出す口（`hiddenRows`、`repointedColumns`）を
加算的に足し、実際の増え方を測ってから決める。

上限を設ける場合の案と、そのときの意味の保証の変わり方:

- **基準**: まとめられた行の**自分の版の時刻**が、保持期間 N 日より古いこと。「まとめられた時刻」は
  導出の結果で事実ではないので、基準に使えない
- **行うこと（確定）**: その行 `h` について、`D(t, h, ts = h の版の時刻, a = 勝者の真の id)` という
  削除の版を作り、`_hidden_*` から消す。これは §2.5 の旧版の畳みと同じ形の**事実**なので、
  見え方の決定性（定理1）は保たれる
  - 同時刻は削除の版が勝つので、`h` は死ぬ。そのあとで `h` がアプリに編集されれば
    （より新しい版）、また候補になる
  - 2つの端末が別々の勝者で確定した場合は、§1.2 の3（`a` の小さい方）で決まる
- **保証の変わり方**: 「かぶりが解消すれば戻る」は、**まとめられた行が最後に編集されてから N 日
  以内に解消した場合だけ**になる。N 日を過ぎて解消した場合は、確定がどの端末で先に起きたか次第で、
  いったん戻ってからもう一度消える
  - 最終的な答えは全端末で揃う
  - 途中の見え方は端末によって揺れる
- **減らせないもの**: 付け替えた子の `_repoint` は、確定しても消せない。消すと子の真の値が
  変わるが、新しい時刻を作らずにそれを事実にする方法が無い（作れば §3-12 に反する）。確定で
  減るのは `_hidden_*` の中身だけで、`_repoint` は子が消えるか編集されるまで残る

## 7. 実装の段取り

### 段階0 —— 判定を先に作る（`tools/` のみ。担当と調整する）

`tools/explore` の性質は、いまは「往復すれば全端末が一致する」だけである。実験1は、どちらの
並びでも一致するので反例にならない。新しい判定を2つ足す。

1. **参照実装との一致**: 探索中に端末が作った事実を、世界の側で集める。集めるのは、各操作の直後に
   読める行の版と、その操作で書かれた `_tombstone`。検査器の時計 C に揃えた値を使う。
   それに §1 の定義を**差分なし・全体やり直しで素直に書いた** `Φ` を当て、収束した全端末の
   中身と比べる。参照実装は `src/` を import しない
2. **決定性の直接の検査（補助）**: 同じ事実の集合に行き着く2つの列（同期の挿し方だけが違う）の
   収束先を比べる

いまの `src/` に当てると、`--tables tags+tag_notes --ids 2 --keys 2 --depth 5` 程度で実験1の形が
反例として出るはずである【推測】。これが出ることを、段階4以降の「直った」の根拠にする。

## 付録A —— 実験の記録

作業ツリーを `$(mktemp -d)` の下へ複製し（`node_modules` はリンク）、`__tests__/helpers/sync-fixtures.ts`
の足場と本物の `performSync` で確かめた。複製は確認後に消した。

### A.1 実験1・実験2（いまの実装）

`n1` は `g1` の子（`tag_notes`）として足した。round-robin（a, b を3巡）で同期した。

```
実験1  a,b 共通:
  tags       [{g2, t2, 00:03}]
  tag_notes  [{n1 → g2}]
  _tombstone [{g1, deletedAt 00:02, mergedInto g2, revokedAt null}]
  _id_merge  [{tags, g1 → g2, mergedAt 00:02}]

実験2  a,b 共通:
  tags       [{g1, t1, 00:01}, {g2, t2, 00:03}]
  tag_notes  [{n1 → g1}]
  _tombstone []
  _id_merge  []
```

実験1の同期が `g1` の削除の版（00:02、畳み先 `g2`）を作っていることが、結果の違いの原因である（§4.1）。

### A.2 SQLite の振る舞い

- 本体の表に付けたトリガーの `WHEN` から TEMP 表を参照すると、`no such table: main.tf` になる
- 本体の表に置いた旗（`_flag`）を `WHEN NOT EXISTS` で見ると、親の DELETE によるカスケードで
  消えた子のトリガーも止まる。子は消える（カスケードの動作そのものは止まらない）

### A.3 成分の局所性（§4.3）

候補2〜7個、ユニークキー2本、値3種、NULL あり、時刻4種の無作為な集合で、2万回試した。
1つの候補を変えたり足したり消したりしたあと、全体をやり直した貪欲と、前後の成分だけをやり直した
結果は、**2万回とも一致した**。衝突が無いこと・極大であることも、毎回成り立った。

  `fields: [id]`（主キーを共有する 1:1）は見当たらない

  （`score-at-once-electron` の文書とコメントにだけ名前が出る）
