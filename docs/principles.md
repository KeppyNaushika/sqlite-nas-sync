# 同期の仕様

この文書は、同期が何を保証するかを定める。どう実現しているかは、リポジトリの [`docs/rows-table-design.md`](https://github.com/KeppyNaushika/sqlite-nas-sync/blob/main/docs/rows-table-design.md) にある。

## 目的

変更を LWW で統合する。

変更が止まれば、各クライアントが互いのコピーを読む同期を2周するだけで、全てのクライアントの結果が一致する。

一致する先の中身は、同期をいつ挟んだかによって変わる。単調化が、書いた時点で何を取り込んでいたかに依存するためである。

## 用語

- **アプリケーション** —— このライブラリを組み込むプログラム。ユーザーテーブルを定義し、読み書きする。
- **クライアント** —— 同期に参加する1つのローカル DB と、それを開くプロセス。`clientId` で識別し、NAS 上にコピーを1つ持つ。
- **ユーザーテーブル** —— アプリケーションが定義し、読み書きするテーブル。このうち主キー列と時刻列を持つものが同期の対象になる。`excludeTables` で外せる。
- **時刻列** —— 同期するユーザーテーブルで、アプリケーションが変更のたびに現在時刻を書く列。値は ISO-8601 の文字列に限る。付則2 で定める。
- **内部テーブル** —— このライブラリが作り、ライブラリだけが読み書きするテーブル。名前は `_` で始まる。
- **変更** —— ユーザーテーブルの行に対する `INSERT` / `UPDATE` / `DELETE`。クライアント間で複製されるのはこれだけで、内部テーブルへの書き込みは変更ではない。
- **子行** —— 外部キーで他の行を参照する行。参照される側を親行と呼ぶ。
- **先行**（happened-before）—— 変更 A のあとに同じクライアントで実行された変更、および A を同期で取り込んだ後に実行された変更に対して、A は先行するという。どちらも相手に先行しない2つの変更を**並行**という。
- **バージョン** —— 1回の変更が作る、その行の内容と順序用の3列 `_sns_ts` / `_sns_lamport` / `_sns_instance` の組。`_sns_rows_<表>` に主キーごとに最新の1つが入り、`DELETE` のバージョンは `_tombstone` に入る。
- **統合** —— `UNIQUE` が衝突した主キーの違う2行を、ユーザーテーブルでは1行として扱うこと。
- **併合** —— 2つのバージョンの集合を、主キーごとに LWW で1つに決めて、1つの集合にすること。同期の取り込みが行う。
- **単調化** —— 書き込むとき、順序に使う値を「アプリケーションが書いた値」と「取り込んだ最大値」の大きい方にすること。`_sns_ts` と `_sns_lamport` の両方に行う。Lamport クロックと hybrid logical clock の更新規則と同じ。
- **LWW**（last-write-wins）—— 競合する変更の勝ちを次の順で決める。
  1. 一方が他方に先行していれば、後の方が勝つ。
  2. 並行なら、アプリケーションが書いた時刻の新しい方が勝つ。
  3. 時刻も同じなら、付則1で決める。

  2 の「新しい」はアプリケーションが書いた時刻の比較であって、本当にどちらが後だったかは分からない。並行な変更に実行順は無いからである。保証するのは、どのクライアントで比べても同じ答えになることだけ。

## 原則

1. 変更の発生源はアプリケーションだけ。同期は、他のクライアントで発生した変更を適用する。
2. 同じ主キーへの複数の変更は LWW で決める。`DELETE` も1つの変更として、同じように比べる。
3. 主キーの異なる2行が `UNIQUE` で衝突したときも、LWW で統合する。統合した行を `DELETE` したときは、統合されていた両方の主キーが削除される。
4. 子行は、アプリケーションが宣言した外部キーに従う。親行が原則3で統合されたときは、統合された親行の子行になる。親行が削除されたときは、宣言された `ON DELETE` に従う。`CASCADE` なら、あとから届いた子行も、親行が削除されている間は、その時刻によらずユーザーテーブルに入らない。この理由でユーザーテーブルに入らなくなった子行と、再び入った子行は、アプリケーションに知らせる。

## 付則

1. **バージョンの順序。** `(_sns_ts, _sns_lamport, _sns_instance)` の辞書順で、大きい方が勝つ。 LWW の 1〜3 はすべてこの1本の順序で決まる。1 は単調化によって、2 は `_sns_ts` によって、3 は `_sns_instance` によって決まる。

   付則2 により時刻列には ISO-8601 の文字列だけが入るので、`_sns_ts` はふつう ISO-8601 の文字列どうしを時刻として比べる。

   ライブラリは、どんな値の組でも順序が決まるように、`_sns_ts` の比較をまず値の種類で決める。順序は NULL ＜ 数値 ＜ ISO-8601 でない文字列 ＜ ISO-8601 の文字列 ＜ BLOB。同じ種類なら値で比べ、ISO-8601 の文字列は時刻として比べ、それ以外の文字列はバイトで比べる。NULL は、時刻の分からないバージョンに使う。以前のバージョンから移した削除で、記録された時刻が ISO-8601 の文字列でないものがこれにあたる。

   `_sns_instance` は `setupSync` のたびに作る16バイトの乱数なので、ここまで来た場合の勝敗に意味はない。どのクライアントで比べても同じ答えになることだけを保証する。

2. **時刻列の値。** 時刻列には ISO-8601 の文字列だけを書く。日付と時刻を `T` またはスペースで区切った形、日付だけの形、末尾に `Z` や `+00:00` のような時差を付けた形はどれも ISO-8601 の文字列として扱う。

   原則2 で `DELETE` と比べる時刻は、`DELETE` を実行した時刻を ISO-8601 の文字列にした値である。時刻列の値がすべて ISO-8601 の文字列なら、`DELETE` の時刻と他の変更の時刻をそのまま比べられる。数値や NULL の時刻とは比べられないので、この前提が破れると原則2 が成り立たない。`setupSync` は時刻列に ISO-8601 の文字列でない値がある行を見つけると例外にする。導入したあとにそのような値を書く `INSERT` と `UPDATE` は失敗する。

3. **親行が削除されているとき。** 親行が削除されているとは、全てのクライアントのバージョンを合わせたとき、親行の主キーで勝っているのが `DELETE` のバージョンであることをいう。親行が同じ主キーで書き直され、その書き直しが勝てば、親行は削除されていない。

   原則4 の「宣言された `ON DELETE` に従う」は、子行を次のどちらかで扱う。親行を `DELETE` したクライアントにその時点であった子行は、SQLite が `ON DELETE` に従って削除または更新し、その変更は他の変更と同じく複製される。それ以外の子行、つまり親行の削除と並行に他のクライアントで書かれた子行は、どのアプリケーションも削除していないので削除しない。このような子行は、親行が削除されている間だけ、次の `ON DELETE` の種類に従って扱う。親行が書き直されれば、元の形でユーザーテーブルに入る。

   - `CASCADE` では、子行はユーザーテーブルに入らない。
   - `RESTRICT` と `NO ACTION` では、ローカルでは SQLite が親行の削除を止める。他のクライアントから親行の削除が届いたときにはもう止められないので、`CASCADE` と同じく子行はユーザーテーブルに入らない。`ON DELETE` を書かない外部キーは `NO ACTION` である。
   - `SET NULL` では、その列が NULL を許せば、列を NULL にした形で入る。許さなければ入らない。
   - `SET DEFAULT` では、既定値が定数で、その値が指す親行があれば、列を既定値にした形で入る。そうでなければ入らない。

4. **外部キーが参照する列。** 同期するテーブルを親とする外部キーは、親の主キーを参照する。子が同期しないテーブルでも同じである。主キー以外の `UNIQUE` 列を参照すると、子行の親行が削除されたのか、まだ届いていないのかを区別できず、原則4 に従えない。`setupSync` はそのような外部キーを見つけると例外にする。
