# 同期の仕様

## 目的

変更を LWW で統合する。

変更が止まれば、各クライアントが互いのコピーを読む同期を2周するだけで、全てのクライアントの結果が一致する。

一致する先の中身は、同期をいつ挟んだかによって変わる。単調化が、書いた時点で何を取り込んでいたかに依存するためである。

## 用語

- **アプリケーション** —— このライブラリを組み込むプログラム。ユーザーテーブルを定義し、読み書きする。
- **クライアント** —— 同期に参加する1つのローカル DB と、それを開くプロセス。`clientId` で識別し、NAS 上にコピーを1つ持つ。
- **ユーザーテーブル** —— アプリケーションが定義し、読み書きするテーブル。このうち主キー列と時刻列を持つものが同期の対象になる。`excludeTables` で外せる。
- **内部テーブル** —— このライブラリが作り、ライブラリだけが読み書きするテーブル。名前は `_` で始まる。
- **変更** —— ユーザーテーブルの行に対する `INSERT` / `UPDATE` / `DELETE`。クライアント間で複製されるのはこれだけで、内部テーブルへの書き込みは変更ではない。
- **子行** —— 外部キーで他の行を参照する行。参照される側を親行と呼ぶ。
- **先行**（happened-before）—— 変更 A のあとに同じクライアントで実行された変更、および A を同期で取り込んだ後に実行された変更に対して、A は先行するという。どちらも相手に先行しない2つの変更を**並行**という。
- **バージョン** —— 1回の変更が作る、その行の内容と順序用の3列 `_sns_ts` / `_sns_lamport` / `_sns_instance` の組。`_sns_rows_<表>` に主キーごとに最新の1つが入り、`DELETE` のバージョンは `_tombstone` に入る。
- **統合** —— `UNIQUE` が衝突した主キーの違う2行を、ユーザーテーブルでは1行として扱うこと。
- **併合** —— 2つのバージョンの集合を、主キーごとに LWW で1つに決めて、1つの集合にすること。同期の取り込みが行う。
- **単調化** —— 書き込むとき、順序に使う値を「アプリケーションが書いた値」と「取り込んだ最大値」の大きい方にすること。`_sns_ts` と `_sns_lamport` の両方に行う。Lamport クロックと hybrid logical clock の更新規則と同じ。
- **LWW**（last-write-wins）—— 競合する変更の勝ちを次の順で決める。
  1. 一方が他方に先行していれば、後の方が勝つ。
  2. 並行なら、アプリケーションが書いた時刻の新しい方が勝つ。
  3. 時刻も同じなら、付則1で決める。

  2 の「新しい」はアプリケーションが書いた時刻の比較であって、本当にどちらが後だったかは分からない。並行な変更に実行順は無いからである。保証するのは、どのクライアントで比べても同じ答えになることだけ。

## 原則

1. 変更の発生源はアプリケーションだけ。同期は、他のクライアントで発生した変更を適用する。
2. 同じ主キーへの複数の変更は LWW で決める。`DELETE` も1つの変更として、同じように比べる。
3. 主キーの異なる2行が `UNIQUE` で衝突したときも、LWW で統合する。統合した行を `DELETE` したときは、統合されていた両方の主キーが削除される。
4. 子行は、アプリケーションが宣言した外部キーに従う。親行が原則3で統合されたときは、統合された親行の子行になる。親行が削除されたときは、宣言された `ON DELETE` に従う。`CASCADE` なら、あとから届いた子行も、その時刻によらず削除される。

## 手段

原則を満たすための実装。同じ原則を満たせるなら置き換えてよい。内部テーブルはすべてここに現れる。 **「一致」以外は、外しても2周での一致は保たれる。**

### 一致のため

| 手段                                                                                    | 何のために                                                         |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 主キーごとに最新の1バージョンを持つ `_sns_rows_<表>` と `_tombstone` だけをやり取りする | 併合の結果が順序に依らない                                         |
| ユーザーテーブルは毎回その2つから再構築する                                             | 適用漏れが積み上がらない                                           |
| 順序を付則1に固定する                                                                   | どのクライアントでも同じ向きに決まる                               |
| 再構築の適用中は `_sns_rebuilding` でトリガーを止める                                   | 同期が変更を発生させない（原則1）                                  |
| `_sns_shown` で表示上の主キーを本来の主キーへ戻す                                       | 統合で表示が変わった行への書き込みを、本来の行の変更として記録する |
| `schemaVersion` が違う相手はスキップする                                                | 同じ関数で計算できない相手を取り込まない                           |

### 喪失防止のため

| 手段                                                                   | 何のために                                  |
| ---------------------------------------------------------------------- | ------------------------------------------- |
| `_sns_ts` を単調化する。その行について取り込んだ最大値より小さくしない | 先行する変更に負けない（LWW の 1）          |
| `_sns_lamport` を単調化する。取り込んだ最大値より進める                | `_sns_ts` が同じ値になった2つの前後を決める |

**代償**: 単調化により、異常に大きい時刻が一度入ると、その行の `_sns_ts` は以後その高さに固定され、LWW の 2 が効かなくなる。行ごとに閉じている。

### 速さのため

| 手段                                                                         | 外すとどうなるか                       |
| ---------------------------------------------------------------------------- | -------------------------------------- |
| `_changelog` / `_sync_state` / `_changelog_prune` で、変わった主キーだけ読む | 毎回、相手の全体を読む                 |
| `_sns_dirty` で再構築する表を絞る                                            | 毎回、全ての表を再構築する             |
| `_sns_tick` / `_sns_clock.importTick` で、別スレッドの計算が古くないか見る   | 計算と適用を同じトランザクションで行う |

**代償**: 変わった主キーが必ず告知され、取りこぼしが隙間の検出で拾われることが要る。ここは代数では保証されず、網羅検査で支えている。

### 報告のため

| 手段               | 何のために                                                               |
| ------------------ | ------------------------------------------------------------------------ |
| `_sns_hidden`      | 統合で入らなかった主キーの一覧（`SyncResult.folds` / `restores`）        |
| `_sns_unplaceable` | 制約で入らなかった主キーと理由。同じ警告を繰り返さない                   |
| 捨てた子行の中身   | 原則4 で捨てたバージョンの中身と原因になった親（`SyncResult.discarded`） |

## 付則

1. **バージョンの順序。** `(_sns_ts, _sns_lamport, _sns_instance)` の辞書順で、大きい方が勝つ。 LWW の 1〜3 はすべてこの1本の順序で決まる。1 は単調化によって、2 は `_sns_ts` によって、3 は `_sns_instance` によって決まる。

   `_sns_ts` の比較は、まず値の種類で決める。順序は NULL ＜ 数値 ＜ ISO-8601 でない文字列 ＜ ISO-8601 の文字列 ＜ BLOB。同じ種類なら値で比べ、文字列はバイトで比べる。`COLLATE NOCASE` の時刻列でも大小が付くようにするためである。

   `_sns_instance` は `setupSync` のたびに作る16バイトの乱数なので、ここまで来た場合の勝敗に意味はない。どのクライアントで比べても同じ答えになることだけを保証する。

2. **`DELETE` を実行した時刻を使う条件。** 原則2 の LWW の 2 で `DELETE` に使うのは、実行した時刻を ISO-8601 の文字列にした値である。したがって、その行の時刻列が ISO-8601 の文字列であるときだけ比較に使う。

   時刻列が数値や ISO-8601 でない文字列のときに使うと、付則1 の値の種類の順序によって `DELETE` が必ず勝つ。さらに単調化でその行の `_sns_ts` が ISO-8601 の文字列に固定され、以後アプリケーションの書き込みが二度と勝てなくなる。比べられないときは比べない。そのバージョンの順序は、その行が持っていたバージョンの時刻で決まる。

## 0.20.0 との差

0.20.0 は原則2・原則3・原則4 から外れていた。次の版で直した。

- **原則2** —— `DELETE` を、削除された行の `updatedAt` で比べていた。実行した時刻は `_tombstone.deletedAt` に記録してあるのに、比較に使っていなかった。このため、消したあとに届いた古い編集で行が戻った。いまは実行した時刻をバージョンの順序に使う。条件は付則2。
- **原則3** —— 統合した行を `DELETE` しても、`_tombstone` に入るのは片方の主キーだけだった。統合が崩れ、もう片方が中身の違う行として現れた。いまは統合されていた両方の主キーに削除のバージョンを書き、両方を `_changelog` で告げる。
- **原則4** —— 親行に削除のバージョンがあっても、あとから届いた子行のバージョンを捨てなかった。その子行はユーザーテーブルに入らないまま `_sns_rows_<表>` に残り続けた。入らず、消えもしない。いまは宣言された `ON DELETE` に従って捨てる。`SET NULL` / `SET DEFAULT` で残せる子は残る。孫にも連鎖する。

あわせて直したもの。

- 捨てた子行は、**中身と原因になった親を `SyncResult.discarded` に載せる**。ライブラリは保持しないので、必要ならアプリケーションが退避する。
- `setupSync` の前提の確認に `PRAGMA foreign_key_check` を足した。違反があれば警告する。親のいない子は前提 P5 の破れであり、同期を1回回す前に知らせる。実測で 473MB・100万行の DB で 0.33 秒。
- `_heartbeat` を廃止した。`_changelog` が空でも `_changelog_prune.prunedThroughId` で隙間を正しく判定できることを実測で確認した。無変更時の転送が完全に止まる。
